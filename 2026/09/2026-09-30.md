## 1. 시뮬레이터와 ROS 가 서로 다른 우분투를 요구한다

OT 의 첫 절반이 거의 전부 환경 이야기였는데, 처음엔 왜 이렇게 오래 끄는지 몰랐다. 정리하고
나니 이유가 하나였다. **같은 과제를 위해 쓰는 두 도구가 서로 다른 우분투 LTS 를 기준으로
삼고 있다.**

| 쪽 | 기준으로 삼는 우분투 |
|---|---|
| Isaac Sim / Isaac ROS | 24.04 |
| ROS 2 Lyrical 바이너리 | 26.04 |

한쪽에 맞추면 다른 쪽이 안 돌아간다. 그래서 수업이 택한 답은 **한 대를 고르는 게 아니라
역할을 쪼개는 것**이었다. Windows 에 Isaac Sim 을 두고 headless 로 돌리고, 리눅스 쪽에는
ROS 와 관측 처리·기구학·제어를 두고, 둘을 SSH 로 잇는다.

여기서 내가 오해하고 있던 게 하나 드러났다. SSH 로 붙으면 ROS 노드끼리도 알아서 통한다고
막연히 생각했는데, **SSH 는 실행과 파일 전송의 경로일 뿐이고 DDS 통신이 따라오는 게 아니다.**
원격에서 명령을 던져 시뮬레이터를 띄우는 것과, 그 시뮬레이터가 내는 토픽을 이쪽에서 받는
것은 별개로 뚫어야 하는 두 개의 길이다.

## 2. 그래서 통과 기준이 "설치했다"가 아니었다

환경이 두 대로 갈리면 "깔았다"는 말이 아무 정보도 주지 않는다. OT 가 제시한 검증 순서를
내 말로 다시 쓰면 이렇게 된다.

```text
1단계  호환성 검사 → headless 로 초기화하고 정상 종료까지 확인
2단계  같은 기계 안에서 talker / listener 로 로컬 통신 확인
3단계  원격으로 붙어서 clock · 관절 상태 · 센서 · 명령이 실제로 오가는지 확인
```

1단계가 통과라고 2단계가 되는 게 아니고, 2단계가 통과라고 3단계가 되는 게 아니다. 세 단계가
각각 다른 것을 재기 때문이다. 1단계는 **프로세스가 뜨는가**, 2단계는 **메시지가 도는가**,
3단계는 **다른 기계의 물리가 여기까지 오는가** 를 본다.

9월 22일에 "접속은 한 번에 됐는데 받아오는 것마다 실패한 이유는 시계였다"고 적었는데, 그때
겪은 게 정확히 2단계와 3단계 사이에서 나는 사고였다. 오늘 자료에도 같은 자리에 못이 박혀
있었다. 물리 진행 횟수와 센서 수집 횟수를 따로 세고, 렌더 앞뒤로 sim time 이 같아야 "물리
시간이 멈춘 상태에서 관측했다"고 말할 수 있으며, 관측 시각이 행동 시각보다 나중일 수 없다.

## 3. 픽셀에서 카메라 좌표로 — 손으로 다시 세웠다

OT 에서 역투영 예시가 나왔는데 식만 보고 넘기면 남는 게 없을 것 같아서 직접 계산해봤다.
내부 파라미터가 $f_x = f_y = 600$, 주점이 $(c_x, c_y) = (320, 240)$ 이고 깊이가
$Z = 0.8\thinspace\mathrm{m}$ 일 때,

```math
X = \frac{(u - c_x)\,Z}{f_x}, \qquad Y = \frac{(v - c_y)\,Z}{f_y}
```

```text
(u, v) = (380, 210)
  X = (380 - 320) × 0.8 / 600 =  48 / 600 =  0.08 m
  Y = (210 - 240) × 0.8 / 600 = -24 / 600 = -0.04 m
  → (0.08, -0.04, 0.80) m
```

여기서 두 가지가 눈에 들어왔다.

첫째, **$Z$ 가 곱해져 있으니 깊이가 틀리면 가로세로가 같은 비율로 통째로 틀린다.** 같은
픽셀이라도 $Z$ 를 $0.8$ 에서 $1.6\thinspace\mathrm{m}$ 로 잘못 읽으면 $X$ 도 $0.08$ 에서
$0.16\thinspace\mathrm{m}$ 으로 간다. 픽셀 검출이 아무리 정확해도 깊이 한 칸이 위치 전체를
끌고 간다는 뜻이다.

둘째, 이 값들이 **카메라 화각을 이미 품고 있다.** 가로 $640$픽셀에 $f_x = 600$ 이면 반화각이
$\arctan(320/600)$ 이니 가로 화각은

```text
2 × arctan(320 / 600) = 2 × 28.07° = 56.14°
```

즉 $f$ 와 해상도만 알면 화각이 따라 나온다. 화각을 따로 외울 게 아니라 $K$ 에서 꺼내면
되는 값이었다. 그리고 이 때문에 영상을 리사이즈하면 $K$ 도 같이 고쳐야 한다는 말이 그냥
규칙이 아니라 산수의 결과로 보였다.

관측 시각의 변환 $p_W = T_{WC}(t_{obs})\thinspace p_C$ 는 9월 2일에 동차변환을 정리하면서
봤던 형태 그대로다. 달라진 건 $T_{WC}$ 가 고정이 아니라 **팔의 FK 체인을 타고 매 순간
바뀐다**는 점이고, 그래서 시각 $t_{obs}$ 가 식 안에 들어와 있다. 9월 4일에 "회전행렬이
회전행렬이기를 그만두는 지점들"을 적었는데, 쿼터니언을 쓸 때 $xyzw$ 와 $wxyz$ 순서를
확인하고 정규화를 챙기라는 주의가 오늘 또 나왔다. 같은 함정이 표현만 바꿔 계속 따라온다.

## 4. 리얼센스를 여는 순서 — 화면으로 따라 읽었다

오후 실습은 파이썬으로 D435 를 여는 것이었다. 내 장비는 아직 준비가 안 돼서 오늘은 공유된
화면을 따라 읽기만 했다. 순서를 내 말로 정리하면 이렇다.

1. `rs.context().query_devices()` 로 **꽂혀 있는 장치를 먼저 열거한다.** 시리얼을 코드에
   박아두지 않는 게 핵심이다.
2. 장치가 $0$개면 즉시 반환한다.
3. 장치가 $2$개 이상인데 `--serial` 을 안 줬으면 **거부한다.** 둘 중 어느 쪽을 쓸지 코드가
   모르기 때문이다.
4. `rs.config()` → `enable_device(serial)` → `enable_stream(...)` 으로 무엇을 어떤 해상도와
   포맷과 프레임레이트로 받을지 정한다.
5. `rs.pipeline()` 을 만들고 `start(config)`, 끝에 `stop()`.

실행 결과로 화면에 뜬 것은 이랬다.

```text
camera_info.name: RealSense D435
camera_info.usb_type_descriptor: 3.2
Color frame shape: (1080, 1920, 3)
```

$2$번과 $3$번을 처음엔 군더더기로 봤는데, 팀 프로젝트에서 카메라를 두 대 쓰기 시작하면
이게 바로 갈리는 지점이다. 장치가 없을 때와 **너무 많을 때**가 서로 다른 실패라는 걸
구분해서 처리해야 한다. 앞의 것은 "못 찾았다"고 말하면 되지만, 뒤의 것은 "네가 골라줘야
한다"고 말해야 한다.

`pipeline` 이라는 이름도 처음엔 장식인 줄 알았는데, `start` 와 `stop` 사이에서 **스트림이
살아 있는지 관리하는 주체**가 필요해서 있는 물건이었다. 그래서 `started` 플래그를 두고
`try` 에서 켜고 `finally` 에서 켜졌을 때만 끄는 모양이 된다. 중간에 끊겨도 장치가 붙잡힌
채로 남지 않게 하려는 것이다.

## 5. depth 로 열어놓고 color 를 달라고 했다

실습 중에 제일 오래 붙잡은 건 아주 단순한 어긋남이었다. 스트림은 이렇게 열어놓고,

```python
config.enable_stream(rs.stream.depth, 640, 480, rs.format.z16, 30)
```

받는 쪽에서는 컬러 프레임을 달라고 했다.

```python
color = pipeline.wait_for_frames().get_color_frame()
```

에러가 안 난다. **컬러 프레임이 그냥 안 들어올 뿐이다.** 열지 않은 스트림을 달라고 했으니
빈 값이 오고, 그러면 미리 넣어둔 `if not color: raise` 에 걸린다. 파이프라인은 정상이고
장치도 정상인데 결과만 비어 있는, 제일 헷갈리는 종류의 실패다.

고친 건 두 군데였다. `rs.stream.depth` → `rs.stream.color`, 그리고 `rs.format.z16` →
`rs.format.bgr8`. 포맷까지 같이 바꿔야 하는 게 중요했다. `z16` 은 $16$비트 한 채널짜리
깊이 포맷이라 컬러 스트림에는 애초에 맞지 않는다.

여기서 배운 건 **요청과 수신이 짝을 이루는지 코드가 대신 확인해주지 않는다**는 것이다.
`enable_stream` 에 쓴 것과 `get_*_frame` 에 쓴 것이 같은 종류인지는 사람이 맞춰야 한다.

## 6. shape 이 찍혔는데 화면은 없었다

여기가 오늘의 축이다. 위까지 하고 나면 터미널에 `Color frame shape: (1080, 1920, 3)` 이
찍힌다. 나는 화면을 보면서 "됐네" 하고 있었는데, 아무 창도 뜨지 않았다. 당연했다.
**출력한 것은 배열의 모양 한 줄뿐이었다.**

생각해보면 카메라가 컴퓨터에 넘기는 건 영상이 아니다. $1920 \times 1080$ 을
$30\thinspace\mathrm{fps}$ 로 받는다는 건 **$1$초에 사진 $30$장이 따로따로 온다**는 뜻이고,
그걸 모아 연속으로 보여주는 일은 아무도 안 해준다. 그 역할이 OpenCV 의 `imshow` 다.

```python
frame = np.asanyarray(color.get_data())
cv2.imshow("RealSense", frame)
```

그래서 코드를 통째로 다시 짜는 걸 봤다. 한 장만 받고 끝내던 구조를 루프로 바꾸고, 매
바퀴마다 프레임을 배열로 만들어 `imshow` 에 넘기는 모양이다. `np.asanyarray` 로 굳이
배열로 바꾸는 이유도 이때 붙었다. 카메라 데이터는 결국 **행렬**이고, OpenCV 도 넘파이
배열을 받는다.

이게 오늘 제목이 된 이유다. 1절에서 본 "명령 전송이 아니라 관측된 결과로 판정한다"가
정확히 이 일이었다. 파이프라인이 열렸다는 것, 프레임이 왔다는 것, 화면에 보인다는 것은
세 개의 서로 다른 사실이고, 앞의 것이 뒤의 것을 보장하지 않는다.

마지막에 다음 단계 예제도 잠깐 지나갔다. HSV 로 바꾸고 → 범위 마스크를 만들고 → 열림과
닫힘으로 잡티를 정리하고 → 바깥 윤곽만 찾아 → 면적이 일정 이상인 것만 후보로 남기는
순서였다. OT 슬라이드의 인식 워크플로우와 같은 모양인데, 거기에는 **색으로 찾은 다음에도
유효한 깊이를 골라 역투영해야 위치가 나온다**는 단계가 더 붙어 있었다. 색 검출은 시작이지
끝이 아니다.

## 7. 경로 추종 두 방식은 기준점부터 다르다

따로 정리해둔 Pure Pursuit 와 Stanley 비교를 다시 봤다. 외형은 둘 다 "조향각 하나를
내놓는 기하 제어기"인데, **차의 어디를 기준점으로 잡느냐**가 갈린다.

| | Pure Pursuit | Stanley |
|---|---|---|
| 기준점 | 뒷바퀴 축 중심 | 앞바퀴 축 중심 |
| 보는 것 | 앞쪽 목표점 | 지금의 횡방향 오차와 헤딩 오차 |

Pure Pursuit 는 경로 위에 전방주시거리 $L_d$ 만큼 앞선 목표점을 잡고, 거기까지 **원호로
가는 조향각**을 낸다. 축거 $L$ 인 자전거 모델에서

```math
\delta = \arctan\!\left(\frac{2L\sin\alpha}{L_d}\right), \qquad \kappa = \frac{2\sin\alpha}{L_d}
```

$L = 2.7$, $\alpha = 20$°로 두고 $L_d$ 만 바꿔봤다.

```text
L_d =  3 m  →  δ = 31.62°   (R =  4.39 m)
L_d =  6 m  →  δ = 17.11°   (R =  8.77 m)
L_d = 12 m  →  δ =  8.75°   (R = 17.54 m)
```

$L_d$ 가 분모에 있으니 **멀리 볼수록 덜 꺾는다.** 부드럽지만 코너를 안쪽으로 잘라 먹고,
가깝게 보면 경로를 잘 따라가지만 흔들린다. $L_d$ 는 정확도와 안정성을 맞바꾸는 손잡이다.

Stanley 는 목표점을 안 잡는다. 헤딩 오차 $\psi$ 를 그대로 더하고, 횡방향 오차 $e$ 는 속도로
나눠서 넣는다.

```math
\delta = \psi + \arctan\!\left(\frac{k\,e}{v}\right)
```

$k = 1.0$, $e = 0.5\thinspace\mathrm{m}$, $\psi = 5$°로 놓고 속도만 바꾸면

```text
v = 5.0 m/s  →  δ = 10.71°
v = 2.0 m/s  →  δ = 19.04°
v = 1.0 m/s  →  δ = 31.57°
v = 0.5 m/s  →  δ = 50.00°
```

$v$ 가 분모에 있어서 **느려질수록 같은 오차에 더 세게 꺾는다.** 원래 의도는 "빠를 땐
부드럽게"인데, 속도가 $0$ 으로 가면 발산한다. 그래서 실제로는 분모에 완화 상수 $k_s$ 를
더해 $\arctan(k e / (k_s + v))$ 로 쓴다. $k_s = 0.5$ 를 넣으면 $v = 0.5$ 에서 $50$°가
$31.57$°로 내려온다. 공식만 보고는 몰랐는데 숫자를 넣어보니 그 항이 왜 붙어 있는지가
바로 보였다.

## 8. 카메라를 잘 보이게 놓으면 팔이 모자랐다

로봇 배치를 그려보다가 걸린 게 있다. 집게 머리를 위·뒤로 옮기면 카메라가 뒤쪽 수평에서
아래까지 보게 되어 **뒤에서 오는 물체가 화면에 들어온다.** 그런데 같은 배치에서 집게 머리가
받침에 앉지 못하고, 기둥까지 $29\thinspace\mathrm{mm}$ 이상 모자랐다.

여기서 오해했다가 고친 게 있다. 처음엔 이 $29\thinspace\mathrm{mm}$ 를 "시야가 모자라다"는
뜻으로 읽었는데, 그게 아니라 **팔이 닿지 않는다**는 뜻이다. 즉 센서를 잘 보이게 두려고 옮긴
자리가 기구의 도달 범위를 깨뜨린 것이고, 이건 시야 문제가 아니라 **시야와 도달 가능성이
같은 자유도를 놓고 다투는** 문제다. OT 자료에서 이동 제어를 다루며 "IK 와 관절 제한으로
도달 가능성을 먼저 확인한다"고 해둔 이유가 이런 자리겠다 싶었다.

시야 쪽도 따로 따져봤다. 카메라가 바닥에서 높이 $h$ 에 있고 아래로 $\theta$ 만큼 숙였으며
세로 화각의 절반이 $\varphi$ 라면, 화면 아래 끝이 바닥에 닿는 지점까지의 수평 거리는

```math
d_{\min} = \frac{h}{\tan(\theta + \varphi)}
```

이다. 내가 잡은 값 $h = 0.30\thinspace\mathrm{m}$, 세로 화각 $42$°(즉 $\varphi = 21$°)로
두고 숙임각만 바꿔봤다.

```text
θ = 10°  →  d_min = 0.499 m
θ = 20°  →  d_min = 0.345 m
θ = 30°  →  d_min = 0.243 m
```

발밑을 보려면 더 숙여야 하고, 더 숙이면 먼 쪽이 화면 밖으로 나간다. 둘을 동시에 만족시키는
각도는 없고, **무엇을 포기할지 고르는 문제**다. 도달 범위와 시야, 둘 다 같은 결론이었다.

OT 자료에도 비슷한 말이 다른 자리에 있었다. 장애물 여유 거리를 잴 때 본체만이 아니라 팔과
지금 들고 있는 물체의 크기까지 포함해야 한다는 것. 로봇의 "크기"는 고정된 숫자가 아니라
**지금 무엇을 하고 있느냐에 따라 바뀌는 값**이다.

## 10. 막혔던 지점 / 메모

- **오늘 남길 게 계산밖에 없는 이유를 적어둔다.** 장비와 환경이 준비가 안 돼서 실습을
  구경만 했다. 보고 이해한 것과 손으로 해본 것은 다르고, 9절을 그 선에서 갈라놨다.
  내일 제일 먼저 할 일은 가상환경부터 만드는 것이다.
- **에러 없이 비는 게 제일 안 좋다.** `depth` 로 열고 `get_color_frame()` 을 부르면 예외가
  아니라 빈 값이 온다. `if not color` 같은 검사가 없었으면 그 다음 `np.asanyarray(...)`
  에서 훨씬 엉뚱한 자리의 에러를 봤을 것이다. **예외 처리는 에러를 잡으려고 쓰는 게 아니라
  실패가 난 자리를 표시하려고 쓴다.**
- **`args.serial[1:]` 에서 `TypeError: 'NoneType' object is not subscriptable`.** 선택 인자로
  만들어놓고 안 줬을 때 빈 값이 오는 걸 잊고 슬라이싱하면 난다. 선택 인자는 **없을 때의 값이
  기본값이고, 그 기본값도 코드가 감당해야 한다.**
- **`args is not defined`.** `parse_args()` 가 `main()` 바깥에 있는데 안에서 쓰면 난다.
  스코프 문제인데 메시지가 위치를 정확히 짚어줘서 오히려 빨리 잡혔다.
- **카메라를 다른 프로그램이 이미 잡고 있으면 프레임이 안 온다.** 장치는 열거되는데 스트림만
  비는 또 하나의 경우다. 이것도 에러가 안 난다. 열거되는 것과 쓸 수 있는 것은 다르다.
- **한글 출력이 깨지는 건 코드 문제가 아니다.** 파이썬 $3$ 의 기본 인코딩은 UTF-8 인데
  윈도우 콘솔은 CP949 라서 나는 현상이다. 코드가 아니라 콘솔 인코딩을 맞춰야 한다. 리눅스
  쪽으로 옮기면 안 나올 문제라는 것도 같이 알아뒀다.
- **가상환경을 지금부터 쓰라는 이유.** 이 컴퓨터에 나중에 ROS 를 올릴 거라서, 지금 전역에
  깔아두면 그때 버전이 엉킨다. 패키지가 두세 개뿐일 때가 습관 들이기 제일 쉬운 시점이다.
