## 1. 가상 소멸자 하나가 64바이트와 40바이트를 가른다

부모 포인터로 자식 객체를 지울 때 부모 소멸자가 `virtual` 이 아니면 안 된다 — 규칙으로는 알고 있었는데, 실제로 뭐가 잘못되는지는 몰랐다. 그래서 가상 소멸자를 뺀 실행 파일을 따로 만들어 AddressSanitizer로 돌렸다.

```text
ERROR: AddressSanitizer: new-delete-type-mismatch
object passed to delete has wrong type:
  size of the allocated type:   64 bytes;
  size of the deallocated type: 40 bytes.
```

**만든 건 64바이트짜리 `Lidar` 인데 지울 때는 40바이트짜리 `Sensor` 로 지우고 있었다.** 차이 24바이트가 자식이 들고 있던 부분이고, 그게 통째로 정리되지 않은 채 남는다. "부모 소멸자를 가상으로 선언하라"는 문장이 이 숫자 두 개로 바뀌니 훨씬 분명해졌다.

무서운 건 이게 **정상 실행에서는 아무 표시도 나지 않는다**는 점이다. ASAN을 붙이지 않으면 프로그램은 그냥 잘 도는 것처럼 보인다. 컴파일러가 주는 `-Wnon-virtual-dtor` 경고가 유일한 사전 신호였다.

## 2. 누수도 조용하다 — 176바이트에서 0으로

같은 방식으로 `new` 만 하고 `delete` 를 생략한 버전을 돌렸다.

```text
ERROR: LeakSanitizer: detected memory leaks
SUMMARY: AddressSanitizer: 176 byte(s) leaked in 4 allocation(s).
```

객체 자체뿐 아니라 그 객체가 안에서 들고 있던 메모리까지 4건으로 잡혔다. 그리고 같은 코드를 `make_unique` 로 바꾼 뒤 다시 돌렸다.

```text
=== Fixed version using make_unique ===
Program exit: unique_ptr releases every sensor automatically.
[destroy] Lidar: managed_lidar_0
[destroy] Sensor base: managed_lidar_0
...
```

소멸자가 전부 호출되고 LeakSanitizer 오류가 사라졌다. **같은 바이너리에 플래그만 바꿔 전후를 나란히 본 게 좋았다.** "스마트 포인터를 쓰세요"를 읽는 것과, 안 썼을 때 176바이트가 뜨고 쓰면 0이 되는 걸 보는 건 다른 일이다.

여기서 `delete` 를 직접 부르지 않는다는 게 게으름이 아니라는 것도 정리됐다. 예외가 튀거나 중간에 `return` 하면 손으로 쓴 `delete` 는 건너뛰어진다. 소멸자는 어떤 경로로 범위를 벗어나든 실행된다 — 그게 RAII 다.

## 3. 스택과 힙, 그리고 소멸 순서

소멸 시점을 눈으로 보려고 생성자·소멸자마다 로그를 찍었다.

```text
=== 3. Stack lifetime ===
[create] Sensor base: stack_lidar
[create] Lidar: stack_lidar
End of stack scope -> destructor runs now.
[destroy] Lidar: stack_lidar
[destroy] Sensor base: stack_lidar
```

- 생성은 **부모 → 자식**, 소멸은 **자식 → 부모**. 자식이 자기 자원을 정리한 뒤에야 부모가 정리되어야 하니 당연한 순서인데, 로그로 보니 확실해졌다.
- 스택 객체는 중괄호를 벗어나는 순간, 힙 객체는 `unique_ptr` 가 범위를 벗어나는 순간 소멸했다. **`unique_ptr` 는 힙 객체의 수명을 스택 규칙에 얹는 도구**라고 이해하면 맞는 것 같다.

다형성 루프는 `std::vector<std::unique_ptr<Sensor>>` 에 담아 돌렸다. 담긴 건 부모 타입 포인터인데 호출되는 건 `Lidar::read()` 와 `Imu::read()` 였다.

STL 쪽에서 하나 걸린 게 `count_if` 였다. 거리 기록 `1.20, 0.49, 0.50, 0.51, 0.10, 0.90` 에 `distance <= 0.5` 를 적용했다.

```text
1.20  x
0.49  o
0.50  o   <- 경계값, <= 라서 들어간다
0.51  x
0.10  o
0.90  x
      --> 3
```

`<` 였으면 2가 나온다. 센서 임계값 판정에서 등호를 넣느냐 마느냐가 그대로 개수를 바꾸는 자리라, 조건을 쓸 때 경계값을 한 번은 대입해봐야겠다고 생각했다.

## 4. 경고 0이 정상이 아니었다 — QoS 비호환

오늘 제일 뒤통수를 맞은 부분. Best Effort 로 발행하는 노드에 Reliable 구독자를 붙였더니 **아무 일도 일어나지 않았다.**

```text
QoS mismatch  RELIABLE   subscriber warnings: 0
QoS fixed     BEST_EFFORT subscriber warnings: 14
```

같은 구간, 같은 발행자인데 구독자 QoS만 맞추자 14개가 들어왔다. **경고 0개를 "문제 없음"으로 읽고 넘어갈 뻔했다.** QoS 가 어긋나면 연결 자체가 성립하지 않아서, 에러가 아니라 침묵으로 나타난다. `ros2 topic info --verbose` 로 발행자 쪽 QoS 를 먼저 확인하는 게 순서였다.

Durability 와 History 도 실험했다.

| 실험 | 결과 |
|---|---|
| 발행 후 늦게 붙은 Transient Local 구독자 | 보관된 메시지 **1개** 수신 |
| 같은 조건의 Volatile 구독자 | **0개** |
| 100 Hz 발행 · Depth 1 · 느린 구독자 4초 | 약 400개 중 콜백 **12번** |

마지막 줄이 특히 인상적이었다. 388개가 조용히 덮어써진 것인데, 이것도 에러가 아니다. **큐가 깊이 1이면 처리 못 한 값은 사라지는 게 설계대로 동작한 것**이다. 고주기 상태값이면 그게 맞고(최신 값이 중요), 명령이면 큰일 난다.

그래서 토픽별로 기준을 세워봤다 — pose 처럼 계속 흐르는 값은 Best Effort / Volatile, cmd_vel 같은 명령은 Reliable, 경유점 목록이나 진단처럼 늦게 붙은 쪽도 봐야 하는 건 Transient Local.

## 5. 통신 패턴을 고르는 기준, 그리고 단일 스레드 데드락

Topic / Service / Action 을 언제 쓰는지 표로 정리했는데, 기준이 두 개로 좁혀졌다. **응답이 필요한가**, 그리고 **시간이 걸리는가.**

- 응답이 필요 없고 계속 흐른다 → Topic (pose)
- 한 번 요청하고 즉시 결과 → Service (순간이동, 펜 설정, 거북이 생성)
- 오래 걸리고 중간 상태와 취소가 필요 → Action (목표 각도까지 회전)

그리고 데드락 하나를 배웠다. **단일 스레드 Executor 의 콜백 안에서 서비스 응답을 동기 대기하면 멈춘다.** 응답 콜백을 실행해줄 주체가 지금 그 콜백에 붙잡혀 있는 바로 그 Executor 이기 때문이다. 자기가 자기를 기다리는 구조다. 해결은 `call_async()` 로 Future 만 받고 콜백에서 빠져나오거나, `MultiThreadedExecutor` 와 재진입 가능한 콜백 그룹을 쓰는 것.

## 6. `source` 한 줄이 패키지를 보이게 한다

빌드했는데 `ros2 run` 이 패키지를 못 찾는 상황을 재현해봤다.

```text
Before: AMENT_PREFIX_PATH=/opt/ros/humble
        ros2 pkg prefix turtle_py  ->  Package not found

After:  AMENT_PREFIX_PATH=.../install/turtle_py:.../turtle_interfaces:
                          .../turtle_cpp:/opt/ros/humble
        ros2 pkg prefix turtle_py  ->  .../ros2_ws/install/turtle_py
```

`source install/setup.bash` 가 하는 일은 **지금 이 쉘의 탐색 경로 앞에 내 워크스페이스를 끼워 넣는 것**뿐이다. 빌드가 실패한 게 아니라 찾는 곳에 없었던 것이고, 그래서 터미널을 새로 열 때마다 다시 해줘야 한다. 8월 25일에 `PATH` 를 몰라 헤맸던 것과 같은 종류의 문제였다.

`colcon build` 가 만드는 네 디렉터리 중 제출하는 건 `src/` 하나다. `build/` `install/` `log/` 는 전부 재생성 가능한 산출물이라 제외한다.

## 7. 오전 강의 — 회전행렬에서 축과 각 되찾기

같은 날 오전 수업은 모듈 3 쪽이었다. $R$ 하나가 주어졌을 때 "무슨 축으로 몇 도 돌았나"를 거꾸로 푸는 문제다.

**축은 고유값 1의 고유벡터다.** 회전축 위의 벡터는 그 축으로 돌려도 제자리이니 $R\mathbf{k} = 1\cdot\mathbf{k}$, 그대로 고유벡터의 정의다. 8월 24일에 고유값을 개념으로만 봤는데 계산 도구로 돌아왔다. 고유값은 항상 $\{1,\ e^{i\theta},\ e^{-i\theta}\}$ 이고 나머지 둘은 켤레 복소수라 실수 방향을 못 주므로 축 후보는 하나뿐이다.

**각은 대각합이 알고 있다.** $\mathrm{tr}(R) = 1 + 2\cos\theta$ 에서 오늘 값은

```text
tr(R) = 0.642788  ->  theta = 1.750366 rad = 100.288584 deg
```

막힌 건 **부호**였다. `eig` 가 주는 고유벡터는 부호가 보장되지 않는데($\mathbf{k}$ 가 되면 $-\mathbf{k}$ 도 된다), $\arccos$ 은 항상 $[0,\pi]$ 만 준다. 각이 늘 양수인데 축 부호가 운이면 절반은 반대로 도는 회전을 복원한다. 로드리게스 식에서 대칭항을 지우면 부호가 딸려 나온다.

```math
R - R^{\mathsf{T}} = 2\sin\theta\,[\mathbf{k}]_\times
```

$\theta \in (0,\pi)$ 면 $\sin\theta > 0$ 이라 이 벡터의 방향이 곧 축의 방향이다. 다만 $\theta$ 가 0이나 $\pi$ 근처면 $\sin\theta \to 0$ 이라 무너진다 — 축·각 표현에도 자기만의 특이점이 있는 셈이다.

마지막으로 **쿼터니언은 같은 회전을 두 번 센다.** $q$ 와 $-q$ 가 같은 자세다. 축을 뒤집고 남은 각 $2\pi-\theta$ 만큼 돌려도 도착점이 같기 때문인데, 대수로도 확인된다.

```text
R(-k, 2pi-theta) = I + (-sin)(-[k]x) + (1-cos)[k]x^2 = R(k, theta)
q(-k, 2pi-theta) = -q(k, theta)
```

행렬로는 하나인 회전이 쿼터니언으로는 둘이라 이걸 이중 덮개라 부른다. 8월 24일에 SLERP 하며 "부호를 맞춰야 짧은 쪽으로 돈다"고 적어둔 게 왜 그런지 오늘 붙었다. 보간이나 필터에 넣기 전에 $w \ge 0$ 쪽으로 부호를 통일해두는 게 안전하다.

## 9. 막혔던 지점 / 메모

- **`mkdir sensor.hpp` 로 파일 대신 디렉터리를 또 만들었다.** `lidar.hpp` `imu.hpp` `main.cpp` `CMakeLists.txt` 까지 다섯 개를 그렇게 만들어놓고 왜 안 열리나 했다. 8월 25일에 `mkdir sungjin.txt` 로 똑같은 실수를 하고 메모까지 해뒀는데 또 했다. 빈 파일은 `touch`.
- **경고 0개를 성공으로 읽으면 안 된다.** QoS 불일치는 에러가 아니라 침묵으로 나타난다. 구독이 안 붙는 것 같으면 `ros2 topic info --verbose` 로 양쪽 QoS 부터 맞춰본다.
- **누수와 잘못된 소멸자는 정상 실행에서 안 보인다.** ASAN 을 붙여야 나온다. 반대로 말하면 붙이지 않는 한 계속 모르고 지나간다는 뜻이다.
- **Depth 1 에서 값이 사라지는 건 고장이 아니다.** 설계대로 최신 값만 남긴 것이다. 상태값이면 맞고 명령이면 위험하다 — 토픽 성격에 따라 정해야 한다.
- **`source install/setup.bash` 는 쉘마다 다시 해야 한다.** 빌드 결과가 아니라 이 쉘의 탐색 경로 문제다.
- **동기 대기가 데드락을 만드는 구조를 처음 이해했다.** 단일 스레드 Executor 안에서 자기가 처리해야 할 응답을 기다리면 영원히 안 온다.
- 축·각 복원에서 `eig` 의 고유벡터 부호는 신뢰할 수 없다. $R - R^{\mathsf{T}}$ 로 부호를 따로 정해야 한다.
