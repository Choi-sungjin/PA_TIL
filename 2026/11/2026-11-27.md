## 1. "들렸다"의 증거는 명령이 아니라 다음 관측이다

슬라이드 2는 세 단어를 나눈다.

| 용어 | 뜻 | 예 |
|---|---|---|
| 관측(observation) | 한 시점에 센서로 얻은 값 | 카메라 밝기·색, 관절 각도 |
| 상태(state) | 로봇과 환경의 상황을 수치로 | 같은 영상이라도 팔 시작각이 다르면 필요한 움직임이 다르다 |
| 행동(action) | 제어기에 보낼 명령 | 집게를 닫아라 |

확인 문제는 "집게 목표값과 블록 높이 중 어느 쪽이 실제로 들렸다는 증거인가"였다. 답은 **블록 높이 변화**다. 목표값은 내가 보낸 값이라서 아무것도 증명하지 못한다. 이전 관측과 비교한 높이 차이만이 증거가 된다. 오늘 Action 실험에서도 같은 구도가 반복됐다(7절). `status=4`(성공)는 제어기가 보낸 보고이고, 관절이 실제로 어디 있는지는 `joint_states`를 따로 봐야 했다.

## 5. 월드 좌표와 관절각은 다른 숫자다

슬라이드 12.

- 좌표계(frame)는 원점과 축 방향을 정한다. `world`는 장면에 고정된 기준이라 로봇이 돌아도 같은 물체의 world 좌표는 그대로일 수 있다.
- 자유도(DOF)는 독립적으로 움직이는 축이다. 팔 관절 4개가 각각 회전한다.
- 라디안: π rad = 180°. 오늘 Action 실험의 목표 0.12 rad는 **6.88°**다. 생각보다 작은 움직임이다.
- `FollowJointTrajectory`는 이름 붙은 관절들이 언제까지 어느 각도로 갈지를 보내는 액션이다.

이 강의에는 검사 대상이 두 개 있다. `lab.py`의 `contract()`는 **월드 좌표 요청**(`xyz`, m)을 검사하고, `action_client.py`는 **관절 목표각**(rad)을 직접 정해 모의 제어기에 보낸다. 같은 "목표"라도 단위와 기준이 다르다.

## 6. 명령 계약: `contract()`에 26가지 입력을 넣어 봤다

슬라이드 13의 계약은 네 가지를 본다. 스키마 버전(`command.v1`), 좌표계(`world`), 단위(`m`), 관측 나이(`age_s` 0~0.4초)다. 코드는 짧다.

```python
def contract(goal):
    if goal["version"] != "command.v1" or goal["frame"] != "world" or goal["unit"] != "m":
        raise Reject("contract.frame_unit_version")
    if not goal["request_id"] or not all(math.isfinite(v) for v in goal["xyz"]):
        raise Reject("contract.fields")
    if len(goal["xyz"]) != 3 or not all(abs(x) < 1 for x in goal["xyz"]):
        raise Reject("contract.workspace")
    if not 0 <= goal["age_s"] <= .4:
        raise Reject("contract.stale")
```

`python3 lab.py 14`는 `xyz=[0.254, 0.008, 0.051]`, `age_s=0.1`로 통과하고 `"next": "action_client.py"`를 출력했다(저장소의 기록 파일과 같다). 이 기본값에서 한 가지씩 바꿨다.

| 바꾼 입력 | 결과 |
|---|---|
| `age_s` 0.4 | 통과 |
| `age_s` 0.401 | `contract.stale` |
| `age_s` 0.0 | 통과 |
| `age_s` −0.01 (시계가 거꾸로) | `contract.stale` |
| `age_s` NaN | `contract.stale` |
| `age_s` 100 (ms로 착각) | `contract.stale` |
| `age_s` `"0.1"` (문자열) | **`TypeError`** |
| `unit` "mm" (숫자는 그대로) | `contract.frame_unit_version` |
| `unit` "M" (대문자) | `contract.frame_unit_version` |
| `frame` "base_link" | `contract.frame_unit_version` |
| `version` "command.v2" | `contract.frame_unit_version` |
| `unit`은 "m", 숫자만 mm `[254, 8, 51]` | `contract.workspace` |
| `xyz`에 NaN / inf | `contract.fields` |
| `request_id` "" | `contract.fields` |
| `xyz` `[1, 0]` (길이 2) | `contract.workspace` |
| `xyz` `[]` | `contract.workspace` |
| `x` = 1.0 | `contract.workspace` |
| `x` = 0.999 | 통과 |
| `xyz`에 문자열 `"0.254"` | **`TypeError`** |
| `unit` mm + `xyz` NaN + `age_s` 1.2 | `contract.frame_unit_version` 하나만 |
| `xyz` NaN + `age_s` 1.2 | `contract.fields` 하나만 |

슬라이드 13의 경계 실험(0.400 통과, 0.401 거부)과 17쪽 예고(m→mm면 `contract.frame_unit_version`)는 그대로 나왔다. 표를 채우면서 새로 본 것들:

- **단위가 틀리는 방식이 두 가지이고, 잡는 검사가 다르다.** 라벨만 "mm"로 바뀌면 첫 줄(`frame_unit_version`)이 잡는다. 라벨은 "m"인데 숫자가 mm로 들어오면(254) 라벨 검사는 통과하고 작업 공간 검사(`|x| < 1`)가 잡는다. 1 m 상자가 단위 실수의 마지막 그물 역할을 한다.
- **계약은 라벨만 본다.** `base_link` 기준 상대 이동값에 `frame="world"`라고 적어 보내면 숫자가 같으니 그대로 통과한다. 17쪽에서 말하는 "같은 [1, 0]도 지도 기준과 로봇 기준은 의미가 다르다"를 이 함수는 확인할 수 없다. 라벨을 정직하게 붙이는 건 보내는 쪽 책임이다.
- **NaN 관측 나이는 `fields`가 아니라 `stale`로 기록된다.** NaN과의 비교는 항상 거짓이라서 `0 <= nan <= .4`가 False가 된다. 거부는 되지만 사유가 "오래됐다"로 남는다. 실제로는 "시각을 모른다"인데 로그만 보면 구별이 안 된다. 음수(시계 역전)도 같은 `stale`이다.
- **경계 포함 여부가 검사마다 다르다.** 관측 나이는 `<= .4`라서 0.4를 포함하고, 작업 공간은 `< 1`이라서 1.0을 뺀다.
- **빈 좌표 `[]`는 `fields` 검사를 통과한다.** `all()`에 빈 목록을 넣으면 True라서다. 바로 다음 줄의 길이 검사에서 `workspace`로 잡힌다. 검사 순서가 서로를 받쳐 주고 있었다.
- **타입이 틀리면 `Reject`가 아니라 `TypeError`가 난다.** 슬라이드 7은 `raise Reject(...)`로 멈추고 `except`로 받아 결과에 기록한다고 설명한다. 그런데 `benchmark()`는 `except Reject`만 받는다. 코드를 읽어 보면 문자열 좌표가 하나 섞인 사례는 사유가 기록되지 않고 평가 루프 전체를 멈춘다(이 부분은 실행하지 않고 코드로만 확인했다).
- **첫 번째 거부만 남는다.** 세 가지가 동시에 틀려도 `frame_unit_version` 하나만 나온다. 보고된 사유가 유일한 문제라는 보장은 없다.

### 0.4초 경계는 뺄셈 방법에 따라 흔들린다

`contract()`는 `age_s`를 받기만 하고, 경과 시간은 부르는 쪽이 계산한다. 그래서 계산 방법을 바꿔 봤다.

```
>>> 12.5 - 12.1
0.40000000000000036      # 0 <= age <= 0.4 → False → contract.stale
>>> (12*10**9 + 500_000_000) - (12*10**9 + 100_000_000)
400000000                # ns 정수 → 0.4 → 통과
```

10 ms 단위로 찍힌 시각 쌍 2000개(시작 0.00~19.99 s, 실제 간격 정확히 0.40 s)를 float로 빼 봤다. **1127쌍이 0.4를 아주 조금 넘어서 거부됐다.** 0.4초 경계는 슬라이드가 실험하라고 한 바로 그 지점이다. ROS 메시지의 `stamp`는 `sec`과 `nanosec` 정수 두 개로 오니까, 정수 나노초로 뺀 뒤 마지막에 초로 바꾸면 경계가 흔들리지 않는다. 0.4초라는 기준이 실제로 이 정도 정밀도를 요구하는 건 아니다. 다만 "0.400 통과"를 테스트로 박아 두려면 계산 경로까지 같이 정해야 한다.

## 7. Action: 수락·피드백·취소·종료를 모의 제어기에서 따로 쟀다

슬라이드 14의 용어를 먼저 정리했다.

| 용어 | 뜻 | `action_client.py`에서 |
|---|---|---|
| Goal / handle | 서버가 실행할 목표 / 수락 후 받는, 그 목표를 가리키는 손잡이 | `handle = wait(node, client.send_goal_async(goal, ...), 5)` |
| Future | 나중에 채워질 결과 | `done = handle.get_result_async()` — 취소 전에 만들어 두고 나중에 읽음 |
| 콜백 | 피드백이 올 때 실행되는 함수 | `feedback_callback=record` |
| status | 목표의 생애주기 | 4 = SUCCEEDED, 5 = CANCELED, 6 = ABORTED |
| error_code | 제어기의 결과 코드 | 0 = SUCCESSFUL, −1 = INVALID_GOAL … |
| timeout | 기다릴 시간을 넘김 | `wait()`가 `TimeoutError("result.unknown")` |

`action_msgs`의 상태 상수는 0 UNKNOWN, 1 ACCEPTED, 2 EXECUTING, 3 CANCELING, 4 SUCCEEDED, 5 CANCELED, 6 ABORTED다.

### 7-1. 수업 실습 그대로

README의 터미널 A·B 구성대로 `robot.launch.py mode:=mock`을 띄우고 `action_client.py`를 실행했다. 처음에는 제어기 노드가 라이브러리 심볼 오류(`undefined symbol: has_buffer_fields_...`)로 바로 죽었다. 기본 미들웨어가 문제였고, `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp`로 바꾸니 떴다.

| 실행 | status | 피드백 수 | 시작 → 목표 (joint1) | 결과 수신 시 joint1 | error_code |
|---|---|---|---|---|---|
| 정상 (내 실행) | 4 | 60 | −0.0020 → +0.12 | +0.1200 | 0 |
| 정상 (수업 기록) | 4 | 59 | 0.0 → +0.12 | +0.1192 | 0 |
| 취소 (내 실행) | 5 | 20 | +0.12 → −0.12 | +0.0416 | 0 |
| 취소 (수업 기록) | 5 | 20 | +0.12 → −0.12 | +0.0416 | 0 |

- 이 PC의 모의 제어기는 시작 자세가 수업 기록(전부 0)과 달랐다(joint2~4가 −2.054, 1.502, 0.128). joint1만 움직이니 결과에는 영향이 없었다.
- 피드백은 3초에 60개, 1초에 20개로 약 20 Hz였다.
- 취소 실행에서 `error_code`는 0이다. **취소를 알려 주는 건 `status`다.** `error_code`만 보는 코드라면 취소를 성공으로 읽게 된다.

### 7-2. "취소 수락 · CANCELED · 실제 정지"는 정말 다른 시각이었다

슬라이드 14는 세 시점을 각각 측정하라고 한다. `action_client.py`와 같은 목표(joint1 ±0.12 rad, 3초)를 보내고, 수락 1초 뒤 취소를 보내는 측정 스크립트를 따로 만들었다. 취소 요청을 보낸 시각을 0으로 놓고 세 번 쟀다.

| 회차 | 취소 수락 응답 | joint1 위치가 더 안 바뀜 | CANCELED 결과 수신 | 취소 직후 첫 관측 → 최종 위치 |
|---|---|---|---|---|
| 1 | +1 ms | +28 ms | +50 ms | −0.0123 → −0.0112 |
| 2 | +1 ms | +40 ms | +50 ms | +0.0334 → +0.0325 |
| 3 | +0 ms | +39 ms | +50 ms | −0.0400 → −0.0416 |

- 순서는 매번 **취소 수락(≈0 ms) → 관절 정지(28~40 ms) → CANCELED 수신(50 ms)**이었다. "취소가 수락됐다"는 응답은 팔이 멈추기 전에 온다. 수락만 보고 다음 동작을 시작하면 안 되는 이유가 숫자로 보였다.
- 세 번 모두 **취소 직후 첫 관측보다 진행 방향 반대쪽으로 0.9~1.6 mrad 되돌아가서** 멈췄다. 이 제어기는 50 Hz(`update_rate: 50`)이고 목표 속도는 0.24 rad / 3 s = 0.08 rad/s다. 한 주기(20 ms)에 1.6 mrad를 가니, 많아야 한 주기 분량만큼 뒤로 간 셈이다. 정지 위치를 어느 시점 값으로 잡는지는 제어기 코드를 안 봐서 확정하지 못했다.
- 3회차는 수업 기록 방향(+0.12 → −0.12)을 정확히 뒤집은 실행인데 최종값이 −0.0416으로 수업 기록 +0.0416과 크기가 같았다. 1초 동안 선형으로 움직였다면 0.04에 있어야 한다. 수업 기록의 0.0416도 같은 되돌림이 들어간 값으로 보인다(추정).
- 이건 모의 하드웨어라서 "위치가 더 안 바뀜"은 감속 없이 바로 멈춘 것이다. 실제 모터의 정지 시각은 이 방법으로 잴 수 없다. README도 같은 한계를 적어 두었다.

### 7-3. timeout은 실패가 아니다: 0.5초만 기다려 봤다

슬라이드 14의 마지막 문장은 "결과가 미확정이면 같은 목표를 곧바로 중복 전송할 근거가 없습니다"다. 3초짜리 목표를 보내고 결과를 0.5초만 기다리게 했다.

| 실험 | 0.5초 시점 | 그 뒤 |
|---|---|---|
| 기다리기만 함 | 결과 없음(`result.unknown`에 해당) | 목표는 계속 진행. 보낸 지 **3.05초** 뒤 status 4, joint1 = 목표값 −0.12 |
| 같은 목표를 바로 다시 보냄 (2회) | joint1 ±0.0816 (가는 중) | 첫 목표: **status 6 (ABORTED), error_code −1** / 둘째 목표: 보낸 지 3.00~3.05초 뒤 status 4 |

- 기다리기만 한 쪽은 timeout이 났는데도 팔은 멀쩡히 목표에 도착했다. **timeout은 "실패했다"가 아니라 "아직 모른다"다.**
- 다시 보낸 쪽은 제어기가 새 목표로 갈아탔다. 첫 목표의 결과는 ABORTED로 돌아왔고, `error_code`는 −1이었다. 상수 이름은 INVALID_GOAL인데 목표에는 아무 문제가 없었다. 로그만 보면 **멀쩡히 가던 목표가 "잘못된 목표로 중단"된 것처럼 남는다.**
- 둘째 목표는 자기 3초를 처음부터 다시 셌다. 첫 전송부터 도착까지 3.55초(1회차 3.50초)가 걸려서 **기다린 0.5초만큼 늦어졌다.** 같은 목표라 최종 위치는 같았다.
- 두 목표의 결과를 각각의 handle로 따로 읽을 수 있었다. 슬라이드의 "여러 목표가 오가도 이 핸들로 원하는 요청의 결과를 조회한다"가 이 장면이다.

결과를 모를 때 할 일은 다시 보내는 게 아니라 **미확정과 마지막 관측 시각을 기록하고, handle로 상태를 다시 묻는 것**이다.
