## 1. 지시문에서 먼저 뽑을 건 대상, 도착 장소, 완료 조건이다

로봇 앞에 상자가 두 개라면 무엇을 집을지, 충전기에 도착만 하면 끝인지가 지시문에는 없다. 자료는 수업에서 정한 완료 조건을 이렇게 적었다.

| 지시의 일부 | 수업에서 정한 완료 조건 | 확인할 때 |
|---|---|---|
| B에 놓아 | 선택한 상자가 B에 있고 손은 비어 있음 | 놓은 직후 |
| 충전해 | 충전기 D에 연결되고 충전 중 신호가 켜짐 | 도킹 후 |
| 놓고 충전해 | 상자를 놓은 뒤에 충전을 시작함 | 두 사건의 시각 비교 |

세 번째 줄이 오늘 가장 걸린 부분이다. 최종 상태(상자는 B에 있고 충전 중)만 보면 **먼저 충전하고 나중에 상자를 옮긴 기록**도 통과한다. "놓고"에는 순서 조건이 들어 있어서, 두 사건이 일어난 시각을 비교해야 잡힌다. 완충을 요구하는 요청이라면 충전 시작 신호만으로 끝낼 수 없고, 배터리 잔량 기준이나 충전 완료 이벤트를 사용자와 정해서 목표 검사를 바꿔야 한다.

## 2. 같은 설명에 후보가 둘이면 ID가 아니라 눈으로 구분되는 위치로 되묻는다

작업대 A에 빨간 상자 box_01(입구 쪽), box_02(창가 쪽)가 있으면 색만으로는 하나가 안 정해진다. 시스템 내부 ID를 사용자에게 외우게 하지 않고 "입구 쪽과 창가 쪽 중 어느 쪽인가요?"라고 묻는다. "창가 쪽"이라는 답은 **현재 관측과 대조해서** box_02로 확정한다. 그 사이에 물체가 움직였다면 이전 배치로 답을 해석하지 말고 다시 관측한다.

오류 종류가 다르면 응답도 달라야 한다.

| 상황 | 오류 | 되물을 내용 |
|---|---|---|
| 같은 설명에 후보 둘 | `clarification_required` | 어느 상자인가 (위치로 구분) |
| 지도에 없는 `Z` | `unknown_target` | 어느 장소를 말하는가 |

같은 질문을 돌려주면 사용자가 이미 알려 준 정보를 반복해서 묻게 된다.

## 3. 작업 하나는 JSON 하나이고, 실행 전에 세 군데를 본다

```json
{"id": "t2", "op": "pick", "object_id": "box_02", "after": ["t1"]}
```

| 필드 | 실행 전에 확인할 것 |
|---|---|
| `id` | 이 계획에서 한 번만 쓰였는가 |
| `op` | 허용 목록에 있는가 |
| `object_id` | 관측 목록에 있는가 |
| `after` | 실제로 등록한 선행 작업인가 |

t1을 정의하지 않고 이 명세를 보내면 `after` 검사에서 걸린다. `op`가 `carry_and_charge`처럼 허용 목록에 없으면 기능을 추측해서 실행하지 않고 계획을 돌려보낸다. JSON을 읽을 수 있는 것과 실행할 수 있는 것은 별개의 검사다.

## 4. 명령을 보낸 것과 성공한 것은 다르고, "관측 못 함"은 false가 아니다

집기 예시에서 시각별로 확인할 것이 달랐다.

| 시각 | 사건 | 상태 |
|---|---|---|
| 12:00:00 | 집기 직전 | box_02가 작업 범위 안, 손은 비어 있음 |
| 12:00:01 | `pick(box_02)` 전송 | 파지 상태 **미확인** |
| 12:00:02 | 결과 관측 | 그리퍼는 닫혔는데 상자는 작업대에 그대로 → B로 출발하면 안 됨 |

예상한 효과는 `holding(box_02)`이지만, 다음 작업의 사전조건에는 **실제로 확인한 결과**를 넘긴다. 제어기가 명령을 받았다는 확인과 작업이 성공했다는 확인을 구별해야 한다.

B가 비었는지도 값이 두 개로는 부족하다.

| 관측 | 기록 | 놓기 전에 할 일 |
|---|---|---|
| 선반이 비어 있는 게 보임 | `free(B) = true` | 관측이 아직 유효한지 확인 |
| 다른 물체가 차지함 | `free(B) = false` | 공간이 생길 때까지 대기하거나 목적지 문의 |
| 카메라가 가려짐 | `free(B) = unknown` | 시야를 확보하고 다시 관측 |

관측이 끊겼을 때 false를 넣으면 "가려졌다"는 정보가 사라진다. `free` 대신 `occupied`를 써도 같은 세 값이 필요하다. 카메라가 비어 있음을 확인한 뒤 사람이 물체를 뒀을 수 있으니, 내려놓기 직전에 한 번 더 본다.

## 5. 두 갈래가 "놓기"로 모이는 그래프를 손으로 정렬하고, 파이썬 출력과 맞춰 봤다

상자를 B까지 가져가는 경로(A 이동 → 집기 → B 이동)와 B가 비었는지 확인하는 경로(`check`)는 서로 기다릴 필요가 없다. 그 둘이 `place`에서 합쳐진다. 화살표는 먼저 끝나야 하는 작업에서 그 결과를 기다리는 작업으로 향한다.

| 작업 | 의미 | 선행 |
|---|---|---|
| A / check | A로 이동 / B의 공간 조회 | 각각 없음 |
| pick / B | 상자 집기 / B로 이동 | 각각 A / pick |
| place | 상자 놓기 | B와 check 모두 |
| D / charge | 충전기로 이동 / 충전 시작 | 각각 place / D |

슬라이드 코드를 3.13에서 그대로 돌렸다.

```python
from graphlib import TopologicalSorter
plan = {'A': (), 'check': (), 'pick': ('A',), 'B': ('pick',), 'place': ('B', 'check')}
print(tuple(TopologicalSorter(plan).static_order()))
```

| 실행 | 출력 |
|---|---|
| 기본 계획 | `('A', 'check', 'pick', 'B', 'place')` (자료의 예상 출력과 일치) |
| `D=('place',)`, `charge=('D',)` 추가 | `('A', 'check', 'pick', 'B', 'place', 'D', 'charge')` |
| `prepare()` 후 `get_ready()` 반복 | 1차 `['A', 'check']` → `['pick']` → `['B']` → `['place']` |

세 번째 줄이 슬라이드 10의 손계산 표와 같다. 처음에 A와 check가 같이 준비되고, pick과 B가 끝나는 동안 place의 남은 선행 수가 2 → 1 → 0으로 줄어든다. 중요한 건 **check가 끝났다는 사건과 `free(B) = true`라는 값은 다르다**는 점이다. check가 끝났어도 값이 false이면 `place`의 사전조건은 충족되지 않는다. 가능한 순서도 하나뿐이 아니라서, A와 check 중 무엇을 먼저 골라도 유효하다.

## 6. 순환은 CycleError로 잡히고, 오타 t9는 정렬이 못 잡는다

정상 계획에서 `A`의 선행에 `place`를 하나 넣었다(`broken = dict(plan, A=('place',))`).

| 실행 | 출력 |
|---|---|
| 순환 입력 | `CycleError`, `err.args[1]` = `['A', 'pick', 'B', 'place', 'A']` |
| `A=()`로 되돌림 | 정상 결과와 같음 (`True`) |

고리는 처음과 끝이 같은 노드로 닫힌다. 고치려면 잘못 추가한 `place → A` 간선, 즉 A의 선행 목록에서 `place`를 지운다. `pick`이나 `B`를 지우면 운반에 필요한 조건까지 같이 사라진다. 순환이 있어도 `check`처럼 독립된 작업은 시작할 수 있으니, 일부가 시작됐다는 사실이 계획 전체가 정상이라는 보장은 아니다. 자료 설명대로 `CycleError`는 고리 하나만 보여 주므로, 고친 뒤에도 같은 검사를 다시 돌려야 한다.

오타는 다른 방식으로 샌다. `pick`의 선행에 존재하지 않는 `t9`를 넣고 돌렸더니 **에러 없이** 이렇게 나왔다.

```
정렬: ('A', 'check', 't9', 'pick', 'B', 'place')
missing: {'t9'}
```

`TopologicalSorter`는 선행 목록에만 있는 ID도 노드로 받아들여서 `t9`가 계획에 끼어들었다. 별도 검사식 `{x for deps in plan.values() for x in deps} - set(plan)`이 비어 있지 않을 때 정렬 전에 오류를 내야 한다. 정렬이 성공했다는 것은 **구조에 고리가 없다**는 뜻일 뿐이다.

## 7. 구조가 맞아도 상태와 자원은 따로 검사한다

| 일부러 넣은 오류 | 검사할 것 | 진단 |
|---|---|---|
| `pick`이 없는 `t9`를 기다림 | 모든 선행 ID가 명세에 있는가 | 미등록 노드 |
| 손이 빈 상태에서 `place` 제안 | 현재 상태가 사전조건을 만족하는가 | 파지 조건 불충족 |
| A와 D로 동시에 이동 | 같은 시간에 차체를 몇 작업이 쓰는가 | 자원 충돌 |

선후 관계와 장비 사용 시간은 따로 본다. 고정 카메라의 B 조회는 차체 이동과 겹쳐도 되지만, A 이동과 B 이동은 차체 하나를 쓰므로 같은 시간에 못 한다. 고정 카메라를 손목 카메라로 바꾸면 관측 위치와 자세까지 고려해야 해서 기존 일정을 그대로 못 쓴다.

## 8. 막혔을 때는 어디서 멈추고, 어디서부터 다시 하고, 무엇을 사용자에게 묻는가

- **상태 공간 탐색 vs 작업 분해**: 손에 다른 상자가 들려 있으면 전자는 `pick`을 후보에서 빼고 임시 보관대 사용을 검사한다. 후자는 "접근 → 집기 → 이송 → 놓기"에서 집기의 사전조건이 막히고 보관 하위 작업이 필요한지 본다. 임시 보관대나 이동 권한이 없으면 둘 다 사용자 확인이 필요하다.
- **재시작 지점**: 집기가 실패했어도 "A에 도착했다"는 관측은 아직 유효하다. 바뀐 사실은 상자 자세와 파지 상태이니 거기서부터 다시 계산한다. 같은 명령을 원인 확인 없이 되풀이하면 안 되고, 재시도 횟수와 관측 유효 시간은 운영자가 정한다.
- **목표 변경과 경로 변경**: B가 막혔고 옆 선반 C가 비어 있을 때, C에 놓는 건 같은 목표로 가는 다른 길이 아니라 **목표 자체를 바꾸는 판단**이다. "C에 놓아도 될까요?"라고 묻고 승인받으면 종료 검사의 대상 위치도 C로 바뀌어야 한다.

## 9. SayCan과 Inner Monologue는 이 검사들이 연구에서 어디에 대응하는지 보여 줬다

- **SayCan** (Ahn 외, 2022): 후보 행동마다 지시와의 관련성(언어 점수)과 현재 상태에서의 실행 가능성을 함께 반영해 결합 점수를 낸다. 수업의 사전조건 검사와 닮았지만, 점수가 성공을 보장하지는 않고 이 그림이 의존성 그래프를 출력하지도 않는다고 자료가 짚었다.
- **Inner Monologue** (Huang 외, 2022): 서랍 열기와 캔 넣기에서 실패가 나면 `[success: no]` 피드백 뒤에 로봇이 같은 행동을 다시 고른다. 서랍 열기가 실패한 뒤에는 서랍 열기가, 캔 넣기가 실패한 뒤에는 캔 넣기가 다시 등장한다. 이미 유효한 단계를 유지한 채 실패한 지점에서 다시 시도할 수 있는지는 8번의 재시작 지점과 같은 질문이다.
