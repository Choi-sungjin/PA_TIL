# 2026-11-17 TIL — CRAFT 저장소를 정리하면서, 코드를 모으는 것과 실행 방법을 남기는 것은 다르다는 걸 알았다

> 오늘은 CRAFT 프로젝트의 GitHub 저장소와 설명 문서를 정리했다. 센서·인지·미션·계획·제어가 맡는 일을 구분하고, 소스에서 빌드하는 방법과 설치된 실행 패키지를 사용하는 방법을 나눠 적었다. `home` 명령은 별도 변경으로 정리했고, README 충돌을 해결한 뒤 통합 내용을 `main`에 병합했다. 코드가 저장소에 있다는 것만으로는 다른 환경에서 바로 실행할 수 있는 게 아니라는 점을 다시 확인했다.

---

## 1. 폴더 목록보다 먼저, 각 노드가 맡은 일을 정리했다

저장소를 설명할 때 파일 이름만 나열하면 어디부터 봐야 하는지 알기 어렵다. 입력을 받는 곳, 판단하는 곳, 실제 모터를 움직이는 곳을 기준으로 구성을 정리했다.

| 구성 | 문서에 정리한 역할 |
|---|---|
| 센서 | 위쪽·그리퍼 카메라와 앞뒤 라이다 입력 |
| 인지 | 물체·퍽·신호등·바코드 및 라이다 관측 처리 |
| 미션 | 한 판의 작업 순서와 다음 단계 조건 관리 |
| 계획 | 주행 경로, 상자 접근·이탈, 팔 작업 단계 계획 |
| 제어 | 바퀴·팔·그리퍼·회전판 명령 실행과 보드 통신 |
| 로봇 모델·통합 실행 | 로봇의 형태·좌표계와 함께 실행할 노드 구성 |
| 음성 | 상태·인지 결과를 읽어 상황을 안내하고 질문에 응답 |

특히 미션과 계획을 한 덩어리로 적지 않으려고 했다. **미션은 무엇을 할지, 계획은 어떻게 움직일지, 제어는 받은 명령을 실제로 실행하는 일**을 맡는다. 음성은 이 흐름의 상태를 읽는 별도 기능이다.

## 2. 소스 배포와 실행 패키지는 준비해야 할 것이 다르다

소스 배포에는 코드뿐 아니라 메시지 정의, 외부 의존성, 모델, 티칭값과 카메라 보정값도 필요하다. 반대로 실행 패키지는 설치된 자원만으로 필요한 파일을 찾을 수 있어야 한다.

| 구분 | 정리한 내용 |
|---|---|
| 소스 빌드 | `craft.repos`로 외부 라이다 드라이버의 버전을 고정하고, ROS 의존성과 별도 네이티브 라이브러리를 준비 |
| 전체 빌드 | `tools/build_workspace.sh`에서 ROS 패키지와 집기에 필요한 카메라 도구를 빌드 |
| 실행 패키지 | `tools/build_runtime.sh`에서 별도 설치 경로를 만들고 `dist/craft-runtime.tar.gz`로 묶음 |
| 실행 자원 | 설치된 패키지에서 모델·티칭·보정값·로봇 메시를 찾도록 구성 |
| 사용자 데이터 | 기본 파일과 실행 중 사용하는 사본을 나누고, 기존 티칭·보정 사본은 자동으로 덮어쓰지 않음 |

모델 파일도 같은 이름이라고 어느 장치에서나 바로 쓸 수 있는 것은 아니다. TensorRT(텐서알티) 엔진은 GPU와 라이브러리 버전의 영향을 받으므로, 환경이 달라지면 ONNX(오닉스) 원본에서 다시 만드는 조건을 적어 두었다.

배포 문서에는 **9개 패키지의 빌드·설치 자원 확인 결과**와 **실물 동작 확인 범위**를 따로 남겼다. 아카이브가 만들어지고 파일 경로가 맞는 것과, 로봇이 전체 미션을 끝내는 것은 다른 확인이다. ObservePucks·PlacePuck·VerifyLocation의 미구현 상태와 `drive_only: true`도 함께 명시했다.

## 3. home은 등록하는 순간과 실행하는 순간을 구분했다

Jetson의 `.bashrc`에서 쓰던 `home` 함수를 `tools/shell/home.bash`로 정리했다. 기존 `tools/go_home.py`를 호출하는 방식이고, 등록 파일을 읽는 것만으로는 로봇이 움직이지 않는다.

- 등록 파일을 읽으면 `home` 함수를 사용할 수 있게 된다.
- `home`을 호출할 때 ROS와 작업 공간의 환경을 읽고 복귀 도구를 실행한다.
- 환경 파일이나 복귀 도구가 없으면 실행을 중단한다.
- 전달한 인자와 실행 결과의 종료 코드를 유지하고, 호출한 터미널의 환경은 별도로 보존한다.

가짜 환경과 실행파일로 확인한 등록 테스트는 **10개 통과**였다. 이 결과는 명령 연결과 오류 처리가 맞다는 뜻이고, 실제 시작 위치까지 주행했다는 뜻은 아니다.

## 4. 변경 목적을 나누고, 병합 대상도 확인했다

PR(풀 리퀘스트)은 파일을 묶어 보내는 단위이면서 검토할 범위를 정하는 단위이기도 했다. 음성 기능과 `home` 등록은 목적이 다르므로 한 번에 묶지 않고 구분했다.

- [`home` 등록 PR](https://github.com/Choi-sungjin/pa_craft/pull/23)은 `arm-teached`에 병합됐다.
- [통합 PR](https://github.com/Choi-sungjin/pa_craft/pull/24)은 `arm-teached`의 내용을 `main`으로 합쳤다.

`home` PR이 병합됐다는 것만으로 곧바로 `main`에도 들어간 것은 아니었다. **어느 브랜치에 병합됐는지**까지 봐야 현재 기준 코드에 반영됐는지 판단할 수 있었다.

## 5. README 충돌은 표시를 지우는 것보다 내용 선택이 먼저였다

통합 PR에서는 `README.md` 한 파일에 충돌 구간이 두 군데 있었다. 최신 노드 구성과 설치 설명을 담은 `arm-teached` 내용과, `main`의 기존 설명이 겹친 부분이었다.

GitHub 충돌 편집 화면에서 `Current change`는 `arm-teached`, `Incoming change`는 `main`이었다. 최신 구조를 유지하되 음성패키지 안내처럼 남겨야 할 내용도 확인하면서 정리했다. 충돌 해결 내용을 먼저 `arm-teached`에 저장한 뒤, 통합 PR을 `main`에 병합했다.

병합된 README를 다시 보니 `craft_voice` 안내 한 줄은 패키지 표가 아니라 실행 설명 아래에 남아 있었다. 충돌 표시를 없애는 작업과 문서의 최종 모양을 확인하는 작업도 나눠 봐야겠다.

## 7. 막혔던 지점 / 메모

- **검토할 목적이 다르면 PR도 나눈다.** 파일 수보다 한 번에 무엇을 판단해야 하는지가 중요했다.
- **승인과 병합은 다르다.** 리뷰가 승인돼도 충돌이 남으면 병합할 수 없다.
- **설명 문서도 최종 화면을 확인한다.** 충돌 구분선을 지운 뒤 표·코드 블록·링크가 제자리에 있는지 봐야 한다.
- **완료 범위를 작게 적는다.** 저장소 정리, 빌드·설치 확인, 실제 주행, 전체 미션 완주는 각각 다른 결과다.
