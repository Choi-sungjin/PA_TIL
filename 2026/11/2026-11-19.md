# 2026-11-19 TIL — JSON 검사를 통과한 로봇 명령도 지도에 목적지가 없으면 보류한다

> 「AI·LLM 응용 베이스」 강의 자료로 정리. 어제 OT에서 요청을 받은 시점과 작업이 끝난 시점을 구분했다. 오늘 자료에서는 그 사이에 어떤 검사가 필요한지 봤다. `navigate`가 허용된 동작이고 제한 시간도 맞는데, 목적지 `A`가 지도에 없으면 그 명령은 보류해야 한다. 모델이 다음 토큰을 잘 고르는 일, 명령이 정해진 형식을 따르는 일, 로봇이 현장에서 움직일 수 있는 일이 각각 다른 문제였다.

---

## 1. 다음 토큰을 고르는 데 쓰는 확률이다

LLM은 지시문을 토큰 ID로 바꾸고, 각 ID에 해당하는 임베딩 벡터를 가져온다. Attention으로 문맥의 정보를 결합해 다음 토큰의 분포를 계산하고, 선택한 토큰을 문맥에 붙여 같은 과정을 반복한다. 토큰 하나가 단어 하나와 꼭 대응하는 것은 아니다.

자료에 나온 `P(옮겨 | 상자를) = 0.6`은 생성 과정을 설명하는 예시다. 이 값이 높아도 상자가 현장에 있는지, 집을 수 있는 상태인지는 따로 확인해야 한다. temperature를 낮춰 출력의 변동을 줄이는 것과 센서나 지도에서 근거를 확인하는 것도 별개다.

## 2. 같은 지시문도 관측이 달라지면 처리 결과가 달라진다

예제 지시문은 `빨간 상자를 A로 옮겨`였다. 지시문에는 색과 장소 이름이 있지만, 상자가 몇 개 보이는지와 `A`가 지도에 등록됐는지는 관측과 지도에서 가져와야 한다. `object_id`, `location_id`, `observed_at` 같은 값을 별도로 두면 무엇을 보고 판단했는지 남길 수 있다.

| 관측·지도 조건 | 기대 처리 |
|---|---|
| 빨간 상자 1개, `A` 등록 | 운반 명령 후보 생성 |
| 빨간 상자 2개, `A` 등록 | 어느 상자인지 확인 요청 |
| 빨간 상자 1개, `A` 미등록 | 실행 보류 |

이 경우 모델 평가에서도 보류가 정답일 수 있다. 정상 명령을 잘 만드는지와 함께, 애매한 입력을 확인 없이 실행하려 했는지도 봐야 한다.

## 3. JSON 해석 → 스키마 검사 → 현장 검사

```json
{"action": "navigate", "target": "A", "timeout_s": 20}
```

| 검사 단계 | 보는 것 | 실패 예시 |
|---|---|---|
| JSON 해석 | 문자열을 JSON 값으로 읽을 수 있는가 | 닫는 중괄호 누락 |
| 스키마 검사 | 필수 키·타입·허용 값·숫자 범위가 맞는가 | `target` 누락, `navigate` 오타 |
| 현장 검사 | 지도·관측 시각·현재 상태·권한에 비춰 실행할 수 있는가 | `A` 미등록, 오래된 관측 |

`required`는 필수 키, `enum`은 허용 값, `additionalProperties: false`는 정의하지 않은 키를 제한하는 데 쓴다. 예제처럼 스키마가 목적지를 문자열로 받으면 `A`의 실제 등록 여부는 지도를 조회해서 판정한다. 오류 코드도 검사 단계별로 나눠 두면 출력 형식을 고칠 일인지, 현장 정보를 갱신할 일인지 알 수 있다.

## 4. 집기 실패를 넣었을 때 이동 명령이 0건이어야 한다

운반을 `대상 확인 → 접근 → 집기 → 이동 → 놓기 → 결과 확인`으로 나눴다. 각 단계에 들어가기 전에 필요한 조건을 두고, 그 단계가 끝났는지는 관측이나 Action 결과로 판단한다.

집기 단계에서 성공 결과가 오면 이동으로 넘어간다. 실패 결과를 주입한 시험에서는 실패 원인이 기록되고 **이동 명령이 0건**이어야 한다. 여기서 0건은 강의 자료의 통과 기준이다. 모델이 계획에 “집고 이동한다”고 썼더라도, 이동 단계가 열리는 조건은 집기의 실제 결과다.

API 재요청에도 같은 구분이 필요했다. 모델 응답이 시간 초과되면 정해진 범위에서 모델 호출을 다시 할 수 있다. 물리 동작을 다시 실행할지는 `command_id`와 이미 기록된 실행 상태를 확인해서 결정한다.

## 5. 프롬프트 예시를 늘릴 때는 보류를 제대로 했는지 본다

실습 설계는 정상 8개, 대상이 모호한 요청 4개, 없는 장소 요청 4개, 금지 동작 4개로 총 20개였다. 각 입력의 기대 처리를 미리 적어 두고, 같은 모델·입력·스키마·생성 설정에서 프롬프트 예시만 0개·1개·3개로 바꾼다. 평가 문장은 프롬프트 예시와 분리한다.

예시를 넣었을 때 전체 점수만 보면 정상 명령이 더 잘 나온 것인지, 잘못된 실행을 더 잘 막은 것인지 알기 어렵다. 유형별 실패 건수와 함께 입력 토큰 수, 응답 시간도 남겨야 비교할 수 있다. 형식 통과율, 기대 처리 일치율, 실제 작업 완료율은 각각 따로 적기로 했다.

## 6. 시각 모델과 행동 모델도 출력에 맞춰 확인한다

| 모델·과제 | 출력 | 로봇에 연결할 때 확인할 것 |
|---|---|---|
| CNN 이미지 분류 | 이미지의 클래스 | 집기에 쓸 위치와 깊이는 별도 관측에서 확인 |
| CLIP | 이미지와 후보 문장의 유사도 | 후보 문장을 어떻게 구성했는지, 빈 작업대에서도 선택하는지 확인 |
| BLIP | 이미지 캡션 또는 질문에 대한 답변 | 언급한 물체가 실제 영상에 있는지 대조 |
| VLA | 관측과 지시에 따른 행동 표현 | 단위·좌표계·제어 주기·정규화 방식을 확인하고 로봇 명령으로 변환 |

로컬 LLM도 같은 흐름에 들어간다. 자료의 Ollama 예제에서는 `/api/chat`에 출력 스키마를 넘겨도, 응답 본문의 `message.content`를 해석한 다음 기존 명령 검증기에 전달한다. 모델을 실행하는 장소가 바뀌어도 지도와 로봇 상태를 확인하는 단계는 필요하다.
