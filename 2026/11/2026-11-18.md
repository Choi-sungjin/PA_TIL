## 2. Physical AI 시스템은 한 방향 파이프라인이 아니라 폐루프다

예시 작업은 "상자를 인지해서 작업대로 옮기기"였다. 대상은 상자, 목적지는 작업대, 완료 조건은 지정 위치 도달.

| 단계 | 하는 일 |
|---|---|
| 인지 | 영상·깊이 → 대상과 위치 |
| 계획·검증 | 명령을 쪼개고, 실행해도 되는 조건인지 검사 |
| 실행 | 이동·집기·운반 |
| 관측·복구 | 완료 판정, 실패 원인 기록 |

마지막 칸이 다시 계획으로 돌아간다. 상태 피드백을 보고 재계획하고, 실패하면 보류하고 원인을 남긴다. 토론 주제로 나온 질문이 "오검출을 어느 지점에서 발견할 수 있는가, 실행 전에 무엇을 검사해야 하는가"였다.

같은 얘기가 대시보드 슬라이드에도 다시 나왔다.

- 제어 요청의 **접수 상태**와 **실제 실행 결과**를 화면에서 분리한다.
- 웹에서 누르는 정지 요청과 물리적 비상정지는 다른 것이다.
- 실제 제어를 연결하려면 권한, 상태 검사, 실행 결과 확인이 있어야 한다.

11/16에 "완료 신호가 어디까지의 완료인지 확인한다"고 적었는데, 과정 설계 자체가 그 구분을 기본 전제로 깔고 있었다.

## 3. LLM·VLM·VLA는 입력과 출력으로 구분한다

| 구분 | 입력 | 출력 | 적용 과제 |
|---|---|---|---|
| LLM | 문장·작업 상태 | 문장·구조화 명령 | 작업 분해 |
| VLM | 영상·문장 | 설명·대응 관계 | 장면 이해 |
| VLA | 영상·언어·상태 | 행동 표현 | 행동 후보 생성 |

- 세 모델을 성능 순위로 보지 않고 **무엇을 받아서 무엇을 내놓는지**로 나눴다. 과정 목표의 첫 번째 성취 역량도 "LLM·VLM·VLA의 입력·출력·적용 한계 비교"였다.
- VLA가 행동을 직접 내놓는다고 해서 바로 로봇에 꽂히는 건 아니다. 행동 단위, 좌표계, 정규화 방식이 모델마다 다르기 때문에 **로봇별 어댑터와 실행 검증**이 필요하다.
- 출력 이름이 "행동"이라도 그게 관절 각도인지, 끝점 위치인지, 어떤 범위로 정규화된 값인지 먼저 확인해야 한다는 뜻으로 읽었다(내 해석).

## 4. 수업 방법: 한 번에 한 조건만 바꾼다

실습은 **개념·입출력 해석 → 최소 예제 구현 → 조건 변경 실험 → 실패 분석·수정** 순서로 돈다.

| 통제 항목 | 관찰 항목 |
|---|---|
| 동일 입력·데이터 분할 | 출력·성공률·지연 |
| 모델·코드 버전 고정 | 정상 및 실패 사례 |
| 한 번에 한 조건 변경 | 변경 전후의 차이 |

논문은 **문제 → 방법 → 실험 조건 → 결과 → 한계** 순으로 읽는다. 결과 숫자보다 "어떤 조건에서 나온 숫자인지"를 먼저 보라는 쪽에 무게가 있었다.

## 5. 프로젝트 두 개: 통합 시연과 정책 학습

### 프로젝트(3) — 물체 인지·조작·운반

카메라 관측으로 목표 물체의 3D 위치를 구하고, 작업대 A에서 로봇팔로 집어 이동 로봇으로 작업대 B까지 옮긴 뒤 완료 판정을 한다.

- 검증 시나리오: **정상 운반 / 미검출 / 집기 실패 / 경로 장애물**
- 시험 전에 통과 기준과 반복 횟수를 먼저 적는다.
- 제출: 통합 시연, 코드·설정, 성공률·처리시간, 실패 로그, rosbag(로스백) 재현 절차

정상 장면 하나만 성공하는 것으로는 인수 시험이 안 된다. 실패 장면 세 개가 같이 들어가 있다.

### 프로젝트(4) — 정책 학습과 독립 평가

**트윈 설계 → 시연 수집 → 에피소드 단위 분할 → BC 기준선 → 선택 정책 비교 → 독립 평가**

- 시연 데이터의 기록 단위는 에피소드다. 관측 o(t)(영상·로봇 상태·시각), 행동 a(t)(조작 명령·그리퍼 상태), 그리고 시작 상태·종료·성공 여부를 같이 남긴다.
- 데이터는 **에피소드 단위로** 학습/평가를 나눈다. 같은 에피소드의 프레임이 양쪽에 섞이면 안 된다. 10/29에 val 1000장 중 818장이 train에 있던 장면이었던 일이 바로 이 경우다.
- BC(Behavior Cloning, 비헤이비어 클로닝)는 사람 시연을 그대로 따라 하게 학습하는 방식이고, 여기서는 기준선 역할이다. GAIL(게일)이나 최신 행동 정책은 장비·데이터·학습 비용을 보고 골라서 비교한다. 모든 모델의 학습 재현은 필수 범위가 아니다.
- 평가 항목: 성공률, 실패 유형, 지연, 위치 오차
- 데이터 확장(Isaac Lab Mimic)은 물체 기준 좌표로 시연 동작을 변환해 새 배치의 데이터를 만든다. 충돌하거나 실패한 궤적은 성공 데이터에서 뺀다.
- 일반화 평가는 학습과 **다른 배치·다른 에피소드**에서 성공률과 실패 유형을 비교하는 것이다.

슬라이드에 나온 Isaac Lab 화면과 BC-RNN 시연 영상은 공식 자료이고, 우리 장비에서 나온 성능 증거가 아니라고 매번 따로 적혀 있었다.

## 6. 다중 로봇·디지털 트윈·RobotOps

| 과목 | 설계 항목 | 비교·운영 지표 |
|---|---|---|
| 다중 로봇 협업 | 작업 할당(능력·거리·잔여 배터리·대기시간), 공유 통로 예약, 상태 동기화, 장애 시 재할당 | 충돌·근접 상황, 처리량, 대기시간, 혼잡도 |
| 디지털 트윈 대시보드 | 위치·경로·작업 구역, 배터리·작업 단계·오류, 데이터 시각 | 정상 / 지연 / 연결 끊김 구분 |
| RobotOps | 장애 발생 → 탐지 → 조치 → 복구 확인 | 성공률, P95 지연, 작업당 비용, 실패 사유 |

- 로봇 수가 늘수록 혼잡과 통신 비용이 어떻게 늘어나는지도 분석 대상이다.
- 대시보드는 값만 보여 주는 게 아니라 **그 값이 언제 받은 데이터인지**를 같이 보여 줘야 한다. 오래된 값이 정상처럼 보이면 안 된다.
- RobotOps에서는 연결 끊김, 노드 종료 같은 장애를 일부러 넣고, 발생·탐지·조치·복구 시각을 기록한다. 제출물은 장애 타임라인, 복구 절차서, 승인·변경 이력, 운영 리포트.
- P95 지연은 요청 100개 중 느린 쪽 5개를 뺀 나머지 중 가장 느린 값이다. 평균은 괜찮은데 가끔 크게 튀는 지연을 잡으려고 본다.

## 7. 평가와 팀 구성

| 영역 | 배점안 | 판정 기준 |
|---|---|---|
| 개념·설계 | 20 | 입출력·제약·선택 이유의 타당성 |
| 구현 | 30 | 정상·실패 시험 |
| 검증·복구 | 30 | 재실행·복구 가능성 |
| 정리·협업 | 20 | 문서·출처·인계의 완결성 |

화면에는 "구현·검증 60"으로 묶여 있는데, 구현 30 + 검증·복구 30을 합친 숫자다. 돌아가는 것만큼 **다시 돌릴 수 있는지와 실패에서 복구되는지**에 같은 비중이 걸려 있다. 공식 성적·출석 규정은 운영기관 안내 기준이고, 이건 교육용 배점안이다.

팀 역할은 인지·계획 / 제어·통합 / 대시보드·운영으로 권장됐다. 역할보다 먼저 정해야 하는 게 **경계의 약속**이었다.

- 인지·계획 ↔ 제어: 좌표계, 단위, 명령 스키마
- 제어·통합 ↔ 운영: Action 상태, 오류 코드, 취소 처리
- 대시보드·운영: 갱신 주기, 지연 기준, 승인 절차
- 공통 기록: 코드 버전, 입력, seed, 결과, 실행 방법. 동료가 재현하고 교차 검토한다.

통합은 최소 정상 시나리오부터 연결하고, 그다음에 실패 시험으로 넓힌다.

## 헷갈리기 쉬운 지점 / 메모

- **요청 접수 ≠ 실제 완료.** 명령이 받아들여졌다는 상태와 로봇이 실제로 끝냈다는 결과는 다른 신호로 다룬다.
- **웹 정지 요청 ≠ 물리적 비상정지.** 화면의 정지 버튼은 요청일 뿐이다.
- **VLA의 "행동"은 바로 쓸 수 있는 명령이 아니다.** 단위·좌표계·정규화를 확인하고 어댑터를 거친다.
- **프레임 단위가 아니라 에피소드 단위로 나눈다.** 같은 에피소드가 학습과 평가에 같이 있으면 평가가 아니다.
- **공식 시연 화면 ≠ 우리 장비의 성능.** 자료에 나온 Isaac Lab 화면과 영상은 장비 확정이나 자체 실험 결과가 아니다.
- **구현·검증 60점의 절반은 검증·복구다.** 한 번 성공한 영상보다 재실행 절차와 실패 기록이 같은 무게다.
- 날짜, 일일 수업 시간, 강사, 장비, GPU/API 비용 지원은 OT 자료 기준으로 미확정이다. 운영기관 확정 공지를 따른다.
