# ONNX 읽기와 ONNX Runtime 기준선

## 1. ONNX 그래프는 노드와 이름 붙은 텐서의 연결이다

공식 문서의 선형 회귀 예시 `Y = X × A + B`로 시작한다. 입력 X → 행렬 곱(MatMul) → 덧셈(Add, B) → 출력 Y, 노드 두 개짜리 그래프다.

- **노드 이름과 텐서 이름은 별개다.** 코드에서 입출력을 찾을 때 둘을 섞으면 안 된다.
- A·B는 학습으로 정해져 파일에 저장된 값(initializer)이고, 프레임마다 바뀌는 건 X뿐이다. 추론은 저장된 A·B로 계산만 하는 일이지, 매번 A·B를 다시 학습하는 게 아니다.
- 강의 질문: *A의 행과 X의 마지막 차원이 다르면 왜 실행이 실패할까?* → 행렬 곱은 안쪽 차원이 같아야 정의되기 때문이다. (… × K) · (K × N)에서 K가 안 맞으면 곱 자체가 안 된다.
- initializer가 그래프 **입력**으로도 나타나는 모델은 덮어쓸 수 있는 initializer(overridable)일 수 있다. 모델 정의를 직접 확인한다.
- 그래프 안에 전처리가 없으면, 입력을 만드는 별도 코드가 그 계약을 맞춰 줘야 한다.

## 2. 입출력 계약을 표로 고정한다 (YOLO 퍽 검출 예)

| 고정할 것 | YOLO 퍽 검출 기준 값 | 어긋나면 |
|---|---|---|
| 입력 이름·shape | `images`, 1×3×640×640 | shape 불일치로 실행 실패 |
| 자료형·채널 순서 | float32, RGB, NCHW | 색이나 축을 잘못 읽음 |
| 전처리 | letterbox 후 0~1로 정규화 | 박스 좌표가 한쪽으로 쏠림 |
| 출력 | **ONNX 메타데이터에서 읽어 온다** | 디코더 차원이 안 맞음 |
| 후처리 | conf·IoU·NMS·좌표 복원을 고정 | 모델끼리 mAP 비교가 불공정 |

- 640은 실습용 고정 해상도일 뿐이고, 모델을 학습·검증한 조건에 맞춰 바꿀 수 있다.
- 출력 차원은 YOLO 버전과 export 설정마다 달라진다. 추측하지 말고 내보낸 그래프의 메타데이터를 보고 ROS 쪽 디코더를 연결한다.
- 클래스가 4개라고 COCO 80클래스용 디코더 설정을 그대로 가져다 쓰면 안 된다.

## 3. 내 ONNX 구조를 직접 출력해 보기

```python
import onnx

m = onnx.load("model.onnx")
onnx.checker.check_model(m)                      # 형식이 유효한지만 본다
print("IR", m.ir_version)
print("opset", [(o.domain, o.version) for o in m.opset_import])
print("inputs", [i.name for i in m.graph.input])
print("weights", len(m.graph.initializer))
for n in m.graph.node[:10]:                      # 앞쪽 노드 몇 개만
    print(n.op_type, list(n.input), list(n.output))
```

- `onnx.checker`가 보는 건 **모델 형식이 유효한가**까지다. TensorRT가 모든 연산을 지원한다거나 정확도가 원본과 같다는 보장은 아니다.
- 가중치가 외부 데이터 파일로 빠져 있으면 ONNX 파일 옆에 같이 보관한다.
- 학습 때 쓴 채널 순서, 정규화, 클래스 이름, 후처리 설정은 ONNX 안에 없으니 **별도 배포 설정에 남긴다.**
- 이 검사를 통과한 뒤에, 같은 입력으로 원본 모델과 출력값을 비교한다.

## 4. 연산 융합은 메모리 왕복을 줄인다

Conv → BatchNorm → ReLU를 따로 돌리면 연산마다 중간 결과를 메모리에 쓰고 다시 읽는다. 하나의 융합 커널로 묶으면 그 왕복이 줄어든다.

- 추론 모드에서 BatchNorm 통계가 상수면 Conv에 흡수할 수 있다.
- 상수 접기(constant folding): 입력과 무관한 계산은 미리 해 둔다.
- 불필요한 transpose를 지우면 레이아웃 변환 비용이 준다.
- 융합이 되는지는 EP·연산·shape에 달려 있다. **커널 수가 줄었다고 전체 지연이 그만큼 준 건 아니다.** 측정해야 안다.

## 5. ONNX Runtime과 실행 제공자(EP)

EP는 Execution Provider다. 하나의 ORT API 아래에서 하드웨어별 계산을 EP가 맡는다.

- **CUDA EP**: GPU 연산 커널을 실행한다.
- **TensorRT EP**: 지원되는 부분 그래프를 TensorRT로 최적화한다.
- EP를 등록한 **우선순위**와 노드가 실제로 **배치**된 곳은 다르다.
- Arm64용 라이브러리는 CUDA·cuDNN·TensorRT 버전 호환을 따로 검사해야 한다.

강의 질문은 "이 도구를 빼면 그 일을 다른 누가 맡나"였다. ORT를 빼면 변환 검증과 EP별 배치 확인을 맡을 곳이 없다는 게 내 대답이다. 쓰임새는 넷이다.

- **일단 돌아가는지**: CPU EP로 먼저 돌려서 입력·출력 쪽 오류를 GPU 문제와 분리한다.
- **원본과 변환본 비교**: 같은 퍽 이미지를 넣어 수치와 검출 결과가 맞는지 본다.
- **GPU 실행 분석**: CUDA·TensorRT EP별로 노드가 어디 배치되는지, 지연이 얼마인지 잰다.
- 최종 배포를 TensorRT로 직접 하더라도, ORT는 변환이 맞는지 보는 **기준선**으로 남는다.

## 6. EP 경계에서 복사가 생길 수 있다

```
CUDA EP (지원 연산) → CPU fallback (미지원 연산) → CUDA EP (다음 연산) → 복사 + 대기
```

GPU가 EP 목록에 있다는 사실만으로 모든 연산이 GPU에서 도는 건 아니다.

- `ort.get_available_providers()`는 **쓸 수 있는** EP 목록이고, 세션의 `get_providers()`는 이 세션에 **등록된** EP다. 노드가 실제로 어디 배정됐는지는 둘 다 알려 주지 않아서 **ORT 프로파일링**으로 본다.
- 미지원 노드가 CPU로 넘어가면 GPU와 CPU 사이에 텐서 전송과 동기화가 끼어들 수 있다.
- 반대로, 기본 CPU EP가 목록에 남아 있다는 이유만으로 "성능 문제가 있다"고 단정하지도 않는다. 프로파일 로그로 확인한다.
- Jetson용 wheel은 Arm64, Python, CUDA, cuDNN 조합이 맞아야 한다. PC에서 쓰던 wheel을 복사하지 않는다.
- I/O Binding은 불필요한 복사를 줄이는 수단이지, 모든 노드의 복사가 사라진다는 보장은 아니다.

## 7. ORT 기준선 만들기

```python
import onnxruntime as ort

so = ort.SessionOptions()
so.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
so.enable_profiling = True
sess = ort.InferenceSession(
    "model.onnx", so,
    providers=["CUDAExecutionProvider", "CPUExecutionProvider"],
)
print(sess.get_inputs()[0].name, sess.get_inputs()[0].shape)
print(sess.get_providers())          # 실제로 등록된 EP
# 같은 입력 x로 워밍업 → 반복 측정 → sess.end_profiling()
```

지킬 것:

- 사전 조건은 **그 환경에서 CUDA EP가 실제로 로드되는 호환 ORT**다. `get_available_providers`로 확인해서 없으면 GPU 성능 수치는 적지 않는다.
- 워밍업과 반복 횟수를 기록한다.
- 원본 · ORT CPU · ORT CUDA를 **같은 입력, 같은 후처리**로 비교하고, 전·후처리를 지연에 넣는지 여부도 통일한다.

## 8. 최적화 전후의 구간별 지연을 읽는 법

강의 그림은 총 지연이 20 → 17 → 14 ms로 줄어드는 **교육용 예시**였다(Jetson 실측이 아니다). 숫자보다 읽는 방법이 요점이었다.

- 추론 구간만 줄여서는 전체 이득이 제한된다.
- 그래프 최적화는 **추론 구간**을, 복사 감소는 **전달 구간**을 줄인다. 어느 구간이 줄었는지 나눠서 본다.
- 비교는 같은 프레임에서 합산한 지연으로 한다.
- 실습 제출물은 반복 실행의 **원시 지연 CSV**와 **EP 프로파일**이다.

## 9. 정합을 통과해야 다음 단계로 간다

다음 단계로 넘어가는 문턱을 다섯 개로 이해했다.

- **구조**: `onnx.checker`와 입출력 메타데이터가 계약과 맞는가.
- **수치**: 같은 입력에서 절대/상대 오차가 허용치 안인가. 허용치는 돌리기 **전에** 모델별로 정해 둔다.
- **과제 지표**: 같은 test 세트에서 mAP나 성공률이 기준 성능을 유지하는가.
- **실행**: EP 프로파일과 복사 구간에서 예상 못 한 fallback이 보이면 이유를 설명할 수 있는가.
- **제출물**: ONNX, 해시, 환경, 로그를 남겨서 다른 사람이 그대로 재실행할 수 있는가.

퀴즈: *출력 숫자는 비슷한데 박스 위치가 어긋난다면?* → letterbox 복원부터 확인한다. 네트워크 출력 숫자만 비교하면 후처리 버그가 가려진다.

- 모든 모델에 `atol=1e-4`를 일괄 적용하지 않는다. 출력의 크기와 과제가 허용하는 오차를 보고 정한다.
- 동적 shape는 필요한 범위만 열고, 범위의 **경계값**도 검사한다.

#   TensorRT (앞부분)

## 1. 엔진은 대상 GPU에서 만든다

```
ONNX → 그래프 최적화 → tactic 탐색 · 작업 공간 선택 → 엔진(.plan) → 대상 장비에서 실행
```

- 엔진은 **TensorRT 버전과 GPU/플랫폼에 의존**한다. 호환 옵션이 있어도 x86에서 만든 엔진이 Arm(Jetson)에서 자동으로 돈다고 믿으면 안 된다.
- 그래서 기본 배포 경로는 "엔진 파일을 복사"가 아니라 **ONNX와 전처리 설정을 Jetson으로 옮기고, Jetson에서 엔진을 빌드**하는 것이다.
- 빌드 시간과 추론 시간은 분리해서 기록한다.
- TensorRT는 일반 명칭이 아니라 NVIDIA 추론 최적화 SDK의 제품명이다. 학습된 가중치를 받아 실행을 최적화하는 것이고, 엔진 빌드가 모델 재학습은 아니다.

## 2. 빌더와 런타임 — 한 번 만들고 계속 쓴다

| | 빌드 (배포 준비 때) | 실행 (프레임마다) |
|---|---|---|
| 하는 일 | 대상 GPU용 실행 계획을 만든다 | 입력으로 예측을 계산한다 |
| 받는 것 | ONNX, shape 범위, 빌드 설정 | 저장해 둔 엔진, 입력 텐서 |
| 쓰는 객체 | Parser, Network, BuilderConfig | Runtime, Engine, Context |
| 나오는 것 | 직렬화된 엔진 (`.plan` / `.engine`) | 출력 텐서 → 후처리 |

빌드에서는 융합·tactic 탐색·메모리 계획을, 실행에서는 버퍼 연결과 GPU 작업 제출을 한다. 빌드는 배포 준비 단계에서 한 번 하고, 엔진은 **프로세스가 시작될 때 로드해서 재사용**한다. 카메라 프레임마다 엔진을 빌드하는 건 절대 안 된다.

## 3. 우리 로봇에 TensorRT가 필요한 이유

우리 상황에 대 보면 이렇다.

- 카메라 프레임마다 추론해야 한다 → 대상 GPU에 맞춘 커널과 연산 융합으로 추론 비용을 줄인다.
- 8 GB 메모리를 여러 노드가 나눠 쓴다 → 정밀도와 실행 메모리를 비교해서 배포 구성을 고른다.
- 인식이 늦으면 집는 위치가 어긋난다 → 실측 지연을 줄여 인식 결과가 낡지 않게 한다.
- **채택 조건**: 같은 평가 세트에서 정확도와 중심 오차는 유지하고, 지연 목표는 달성할 것.

TensorRT는 목적이 아니라 **수단**이다. 실제 Jetson에서 전·후처리까지 포함해 효과를 재 보고, 이득이 확인될 때 채택한다. 세 번째 항목이 지연을 줄여야 하는 이유를 가장 구체적으로 보여 줬다. 늦은 인식은 그냥 느린 게 아니라 틀린 위치로 집는 것이다.

## 4. 엔진이 만들어지는 내부 단계

1. **ONNX Parser** — 연산을 지원하는지, 입출력 이름이 무엇인지 확인한다.
2. **NetworkDefinition** — 텐서 연결, dtype, 동적 차원을 정의한다.
3. **BuilderConfig** — workspace 상한, profile, 플러그인을 설정한다.
4. **그래프 최적화와 tactic 탐색** — 레이어를 융합하고 실제 GPU 커널을 고른다.
5. **직렬화해서 엔진 저장** — 만든 GPU·TensorRT·CUDA 버전과 모델 해시를 같이 기록한다.

- **tactic**은 같은 계산을 수행하는 여러 구현 중에서 골라낸 실행 방식이다. 빌더가 허용된 설정 안에서 후보들의 성능을 직접 돌려 보고 고른다.
- workspace 제한은 후보 선택에 영향을 준다. 빌드할 때와 실행할 때의 메모리 사용량도 다르다.
- timing cache는 반복 빌드 시간을 줄이는 데 도움이 되지만, 모델 엔진 자체와는 별개다.
- 5번에서 "버전과 해시를 기록"하는 이유가 1절의 의존성 때문이다. 나중에 엔진이 안 읽힐 때 어떤 조합으로 만들었는지 남겨 둬야 한다.

## 5. 카메라 한 프레임이 실행되는 단계

TensorRT가 하는 일과, 그때 내 애플리케이션이 맡아야 하는 일을 짝지어 봤다.

- **시작할 때 한 번**
  1. Runtime이 엔진 파일을 역직렬화한다 → 앱은 엔진 호환과 해시부터 검사한다.
  2. Engine에서 Context를 만든다 → 앱은 버퍼와 CUDA stream을 준비한다.
- **프레임마다**
  3. 입력 shape와 tensor 주소를 설정한다 → 앱은 전처리 결과가 살아 있게 유지한다.
  4. `execute_async_v3` (C++은 `enqueueV3`)로 실행을 제출한다 → 앱은 맞는 stream에 제출한다.
- **끝난 뒤**
  5. 출력 텐서를 쓴다 → 앱은 완료 동기화, 후처리, 결과의 나이(age) 검사를 한다.

- **Engine**은 최적화된 계획을 담고, **Context**는 동적 shape 같은 실행 상태를 관리한다.
- 하나의 Context를 여러 스레드가 동시에 쓰지 않는다.
- 입출력 메모리는 GPU 작업이 끝날 때까지 살아 있어야 한다.
- 비동기 실행이라서 **GPU에 작업을 제출한 시점과 계산이 끝난 시점은 다르다.** 출력을 읽기 전에 완료 동기화가 필요하고, 5번의 "결과 age 검사"는 3절의 신선도 문제와 이어진다.

## 6. 객체의 수명과 동시 추론

- 수명 도식은 **build phase**와 **runtime phase**를 나눠서 본다. ONNX Parser가 가중치 메모리를 소유하는 경로에서는 빌드가 끝나기 전에 parser를 해제하면 안 된다.
- 실행 중에는 Engine, Context, 메모리의 수명을 함께 관리한다.
- 동시 추론에서는 **Engine은 공유**할 수 있어도 **Context는 동시에 같이 쓰면 안 된다**는 구분이 핵심이었다.
- stream을 여러 개 만든다고 항상 빨라지지 않는다. Nano에서는 GPU와 공유 메모리를 놓고 경쟁하게 되므로, 입력 복사와 CPU 전처리까지 같이 측정한다.
- "thread-safe하다"와 "deadline을 지킨다"는 다른 말이다.

## 7. 동적 shape와 최적화 프로파일

- 범위는 **min / opt / max** 셋으로 준다. 예시는 1×3×320×320 / 1×3×640×640 / 1×3×960×960이고, 각각 허용할 가장 작은 입력, 최적화의 대표 입력, 허용할 가장 큰 입력이다.
- 단순하게 가려면 전 범위를 640 하나로 **고정**할 수도 있다. 메모리와 검증 경로가 단순해진다.
- 어느 쪽이든 경계값과 실제로 쓰는 해상도에서 정확도·지연·메모리를 확인한다.

- 동적 shape로 내보낸 ONNX라고 해서 무제한 해상도가 실행되는 게 아니다. TensorRT 엔진의 **optimization profile 범위 안에서** 입력 shape를 설정한다.
- min/opt/max를 넓게 잡으면 메모리와 tactic 선택에 영향이 있을 수 있다.
- YOLO 전·후처리도 입력 해상도에 따라 일관되게 바꿔야 한다. 이 표는 설계 설명용 예시고, 실제로는 모델이 지원하는 해상도와 stride를 확인한다.

## 8. 정밀도를 줄이면 무엇을 잃고 얻는가

- **FP32**: 범위가 넓고 정밀하다. 비교 기준이자 민감한 연산용이라, 기준 mAP와 중심 오차를 저장해 둔다.
- **FP16**: 16비트 부동소수점. 메모리·대역폭·계산 비용을 줄일 수 있지만 범위를 넘거나 작은 값이 사라지지 않는지 본다. 우리 과제에서는 작은 퍽, 멀리 있는 태그 주변의 오차가 확인점이다.
- **INT8**: 정수에 scale/zero point를 붙여 표현한다. 보정에 쓴 데이터가 실제 분포를 대표하는지, 클리핑이 심하지 않은지 본다. 어둠·반사·가림이 있는 데이터를 포함해야 한다.
- **혼합 정밀도**: 연산마다 dtype을 다르게 둔다(QDQ 포함). 민감한 층만 높은 정밀도로 남긴다.

세부 규칙은 이렇다.

- FP16이 표현할 수 있는 최대 유한값은 65504다. 이걸 넘는 값은 범위 초과로 문제가 된다.
- INT8은 저장·대역폭과, 지원되는 커널에서의 연산 이득을 기대할 수 있다. 다만 모델이 메모리 병목인지 연산 병목인지에 따라 달라진다.
- **비트 수가 줄었다고 정확도가 유지되거나 일정한 배속 향상이 보장되지 않는다.** 엔진 파일 크기가 정확히 1/2, 1/4가 된다는 식의 말도 하지 않는다.
- 정밀도를 낮추는 목적은 제한된 자원에서 **필요한 제어 주기를 확보**하는 것이다. 그래서 정확도 손실에 허용선을 먼저 정한다.
- 선택 기준: 빠른 정밀도 중에서 허용 정확도를 만족하는 것. 속도만 좋아지고 집기 실패가 늘면 채택하지 않는다.

## 9. TensorRT의 주요 최적화 기능은 배속을 약속하지 않는다

제품 개요 그림에는 융합, 정밀도 선택, 커널 튜닝이 나온다. 각각 어떤 비용을 줄이는지(메모리 왕복, 연산량·대역폭, 커널 실행 효율)를 구분해서 보는 용도다. 제품 페이지에 적힌 배속 수치를 우리 퍽 모델의 기대 배속으로 쓰지 않는다. 성능은 모델, shape, GPU, 정밀도, 전·후처리 조건에 따라 **직접 재서** 정한다.

---

# 두 강을 한 줄로 이으면

```
계약 고정 (입력 shape·dtype·전처리·후처리)
  → ONNX 구조 검사 (checker + 메타데이터)
  → ORT CPU 기준선 → ORT CUDA (프로파일로 fallback 확인)
  → Jetson에서 TensorRT 엔진 빌드 (버전·해시 기록)
  → FP32 → FP16 → INT8, 단계마다 같은 평가 세트로 정확도·지연 비교
  → 정확도가 허용선 안이고 지연 목표를 지켰을 때만 채택
```

## 헷갈리기 쉬운 지점 / 메모

- **`get_available_providers`와 `get_providers`를 같은 걸로 읽기 쉽다.** 앞은 이 설치본이 쓸 수 있는 EP, 뒤는 이 세션에 등록된 EP다. 둘 다 노드 배치를 알려 주지는 않는다.
- **EP 등록 순서 ≠ 노드 배치.** `["CUDA", "CPU"]`로 줬다고 모든 노드가 CUDA에서 도는 게 아니다.
- **`onnx.checker` 통과 ≠ 쓸 수 있는 모델.** 형식이 맞다는 뜻까지다. 정확도 일치도, TensorRT 지원도 따로 확인한다.
- **Engine과 Context를 같은 것으로 보기 쉽다.** 계획은 Engine에 있고 실행 상태는 Context에 있어서, 공유할 수 있는 건 Engine 쪽이다.
- **thread-safe는 deadline을 지킨다는 말이 아니다.** 동시에 써도 안전한 것과 제때 끝나는 것은 별개다.
- 공식 도식 중 2021년 자료는 프레임워크 로고가 지금 버전과 호환된다는 뜻이 아니라 역할 관계를 보여 주는 용도다.
- 이번 내용은 강의 자료로 정리한 것이고, 위 지연 숫자(20 → 17 → 14 ms)는 개념 설명용 예시다. 아직 내 Jetson에서 잰 값이 아니다.
