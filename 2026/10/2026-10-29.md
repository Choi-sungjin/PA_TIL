# 2026-10-29 TIL — 8000장으로 늘렸더니 val 1000장 중 818장이 train에 있던 장면이었다

> YOLOv8 실습 저장소의 가이드를 따라 Isaac Sim으로 태그 붙은 퍽 사진을 만들고 YOLO를 학습시켰다. 처음엔 흐름만 보려고 24장으로 돌렸다. 터미널의 mAP50 0.5만 보면 반쯤 된 것 같았는데, 결과 폴더를 열어 보니 아무것도 못 찾고 있었다. 8000:1000:1000으로 늘리자 이번엔 1 epoch 만에 val mAP50-95가 0.988이 나왔다. 너무 좋아서 이상했고, 원인은 생성기의 seed 범위였다.

## 2. GitHub에서 받은 저장소에는 모델이 없다

가이드 1단계는 데이터·모델 파일 세 개가 있는지 `ls`로 확인하는 것이다. 받아서 바로 해 보면 셋 다 없다고 나온다. 저장소는 코드만 올려 두었고, 데이터와 모델은 Git에서 제외되어 있다. 새 컴퓨터에서는 4단계(Sim 생성 → 학습)를 거쳐야 이 파일들이 생긴다. 가이드의 순서(1 → 2 → 3 → 4)는 이미 모델이 있는 컴퓨터 기준이다.

## 3. Isaac Sim 6.1에서 첫 캡처가 비어 있었다

생성 스크립트가 바로 멈췄다.

```
RuntimeError: Unexpected RGB shape (0,)
```

렌더러가 준비되기 전에 RGB 버퍼를 읽어서 빈 배열이 온 것이다. 원래 스크립트는 6.0 기준이라 그때는 문제가 없었던 것 같다. 640×640 영상이 올 때까지 몇 번 더 렌더하게 고쳤다.

```python
for _ in range(10):
    rep.orchestrator.step(rt_subframes=4)
    pixels = np.asarray(rgb.get_data())
    if pixels.shape[:2] == (640, 640):
        break
```

더 헷갈렸던 건 **실패했는데도 종료 코드가 0**이었다는 점이다. Kit이 파이썬 예외를 로그로만 찍고 정상 종료해 버린다. 그래서 종료 코드 대신 생성이 끝나면 만들어지는 `COMPLETE` 파일이 있는지로 성공 여부를 판단해야 한다.

ROS를 자동으로 source하는 터미널에서는 Isaac Sim 파이썬과 ROS 환경 변수가 섞일 수 있다. 그래서 `ROS_DISTRO`, `AMENT_PREFIX_PATH`, `PYTHONPATH`, `LD_LIBRARY_PATH` 등을 `env -u`로 빼고 실행했다.

## 4. 라벨 한 줄 = 상자 하나

```
0 0.68593750 0.39609375 0.10312500 0.16406250
2 0.36171875 0.39140625 0.09843750 0.16093750
```

`클래스 cx cy w h` 순서이고, 좌표는 사진 너비와 높이를 1로 본 비율이다. 사진 `images/train/0001.png`의 짝은 같은 이름의 `labels/train/0001.txt`다. 물체가 없는 배경 사진은 빈 txt 파일이다.

라벨 검사기의 PASS는 숫자 형식과 범위가 맞다는 뜻일 뿐이다. 상자가 실제로 물체에 붙어 있는지는 라벨 좌표로 사진 위에 직접 상자를 그려서 확인했다. 4개 모두 물체에 딱 맞았고, 일부러 넣은 파란 공과 베이지 공에는 라벨이 없었다.

## 5. mAP50 0.5인데 아무것도 못 찾았다

흐름만 확인하려고 train 24, val 8, test 8장으로 10 epoch를 돌렸다.

| 어디서 봤나 | 보인 것 |
|---|---|
| 터미널 마지막 줄 | mAP50 0.50, mAP50-95 0.46 |
| `val_batch0_labels.jpg` | 정답 상자 있음 |
| `val_batch0_pred.jpg` | 상자 **0개** |
| `confusion_matrix.png` | 28개 전부 background 칸 |
| 한 장 추론 `perception.json` | `objects` 0개, `tags` 4개 |

최고 신뢰도가 0.024였는데, 추론 코드는 0.25 미만을 버린다. mAP는 신뢰도가 아주 낮은 예측까지 모두 순위에 넣어서 계산하니까 0.5가 나올 수 있다. 반면 confusion matrix와 예측 그림은 기준 신뢰도를 넘은 것만 그린다. **숫자 하나만 보지 말고 `val_batch0_pred.jpg`와 confusion matrix를 같이 열어야 한다**는 게 오늘의 첫 번째 교훈이다.

AprilTag는 같은 사진에서 태그 4개를 다 찾았다. 학습이 필요 없는 검출기라서 YOLO가 실패해도 혼자 동작한다.

덤으로 하나. 같은 `--name`으로 YOLO를 다시 돌리면 폴더 뒤에 `2`, `3`을 붙여 새로 만든다. 반면 CenterPose 스크립트는 덮어쓰지 않으려고 `FileExistsError`로 멈춘다. 둘 다 기존 결과를 지키려는 동작이고, 출력 이름만 새로 주면 된다.

## 6. train / val / test는 하는 일이 다르다

| | 비율 예 | 하는 일 |
|---|---|---|
| train | 70 % | 보고, 틀리고, 가중치를 고친다 |
| val | 15 % | epoch마다 채점해서 `best.pt`를 고른다. epoch 수나 설정을 정하는 데도 쓰인다 |
| test | 15 % | 끝에 **한 번만** 열어 최종 점수를 낸다 |

- `best.pt`는 val 점수가 가장 높았던 epoch이고, `last.pt`는 마지막 epoch이다. train만 외운 모델은 뒤로 갈수록 val 점수가 다시 떨어질 수 있어서 best를 쓴다.
- val도 결과적으로는 학습에 간접적으로 쓰인다. 그래서 test가 따로 있어야 한다. test 점수를 보고 다시 튜닝하면 그 test도 사실상 val이 된다.
- 실물 사진은 **촬영 장면 단위로** 나눠야 한다. 비슷한 연속 프레임이 train과 test로 갈라지면 test에 이미 본 장면이 섞여서 점수가 부풀려진다.
- 비율은 따로 지정하는 옵션이 없다. 생성할 때 `--train 8000 --val 1000 --test 1000`처럼 장 수로 정한다.

## 7. 8000 : 1000 : 1000으로 다시

| 단계 | 걸린 시간 / 결과 |
|---|---|
| Sim 생성 10,000장 + 영상 120프레임 | 29분 (초당 약 5.8장), 약 2 GB |
| 라벨 검사 | PASS, 10,000개 |
| YOLO 학습 (yolov8n, batch 4, 640, 50 epoch) | 1.1시간 (epoch당 약 80초) |

| epoch | box loss | val P | val R | mAP50 | mAP50-95 |
|---|---|---|---|---|---|
| 1 | 0.374 | 0.9996 | 0.9965 | 0.995 | 0.988 |
| 2 | 0.314 | 0.9995 | 0.9961 | 0.995 | 0.992 |
| 23 | 0.199 | 0.9999 | 0.9976 | 0.995 | 0.995 |
| 50 | 0.107 | 0.9997 | 0.9994 | 0.995 | 0.995 |

24장으로는 10 epoch를 돌려도 신뢰도 0.024였는데, 8000장으로는 **1 epoch 만에** mAP50-95가 0.988이 나왔다. 처음엔 데이터 양 덕분이라고 생각했다. 그런데 한 번도 틀리지 않는 수준이 너무 빨리 나와서 val 사진을 의심했다.

## 8. val과 test가 train의 복사본이었다

생성기는 장면마다 seed 하나로 물체 배치, 카메라 높이, 조명, 태그 ID를 전부 정한다. seed는 split마다 시작값을 다르게 준다.

```python
for split, count, base in [('train', a.train, 1000), ('val', a.val, 3000), ('test', a.test, 5000)]:
    for i in range(count):
        seed = base + i
```

시작값을 2000씩 띄워 놨으니 train이 2000장 이하면 겹치지 않는다. 그런데 train을 8000장으로 늘리면 seed가 1000부터 8999까지 가서 val(3000~3999)과 test(5000~5999)를 통째로 덮는다.

| | 개수 |
|---|---|
| train seed와 겹치는 val seed | 1000 / 1000 |
| train seed와 겹치는 test seed | 1000 / 1000 |
| 그중 배치·상자가 완전히 같은 장면 | val 818, test 818 |

나머지 182장은 같은 seed라도 배경 사진 여부(`i % 11 == 0`)가 달라서 내용이 갈렸다. 같은 장면끼리 픽셀 평균 차이는 약 1(0~255 기준)로, 렌더 노이즈 수준이었다. 관련 없는 두 사진은 54였다. 파일 해시는 전부 달라서 **파일 중복 검사로는 못 잡는다.** seed나 장면 ID를 비교해야 보인다.

이대로면 val mAP 0.995는 처음 보는 사진에서 낸 점수라고 말할 수 없다. `best.pt`를 고른 기준도, test 평가도 믿을 근거가 없어진다. 장 수만 바꿨을 뿐인데 6절에서 적은 "장면 단위로 나눠야 한다"가 생성기 안에서 깨져 있었다.

생성기에 `--seed-start`를 추가하고, split 사이의 seed 범위가 장 수에 따라 늘어나게 고쳤다.

```python
train_base = a.seed_start                                   # 기본 1000
val_base   = max(train_base + 2000, train_base + a.train)
test_base  = max(val_base + 2000, val_base + a.val)
```

split이 2000장 이하면 기존과 똑같이 1000 / 3000 / 5000이 된다. 그래서 예전에 만든 데이터와도 맞는다.

모델은 다시 학습하지 않았다. train 8000장 자체는 깨끗하기 때문이다. 대신 `--train 0 --seed-start 9000`으로 val(seed 11000~11999)과 test(13000~13999)만 1000장씩 새로 만들었다. 생성에 6분 걸렸다. seed 겹침은 train과 0, val과 test 사이도 0이다.

| 평가 데이터 | P | R | mAP50 | mAP50-95 |
|---|---|---|---|---|
| 겹친 test (818장이 train 장면) | 0.998 | 1.000 | 0.995 | 0.995 |
| 새 val 1000장 | 0.998 | 1.000 | 0.995 | 0.995 |
| 새 test 1000장 | 1.000 | 0.999 | 0.995 | 0.995 |

깨끗한 test에서도 점수가 그대로였다. 퍽 3,625개 중 confusion matrix에서 틀린 건 9개다. 빨간 원기둥을 각기둥으로 본 것 1개, 빨간 각기둥을 놓친 것 2개, 빈 곳에 빨간 퍽이 있다고 한 것 6개였다. 초록은 하나도 틀리지 않았다. 퍽끼리 가린 사진과 물체 없는 배경 사진도 예측 그림에서 제대로 처리했다.

그러니까 이번에는 누출이 점수를 부풀린 게 아니었다. 이 Sim 분포에서는 문제 자체가 쉬웠다. 하지만 이건 **새 test로 다시 재 보고 나서야** 할 수 있는 말이다. 겹친 상태의 0.995만으로는 "잘 배웠다"와 "외웠다"를 구분할 수 없었다.

교훈:

- 점수가 너무 빨리, 너무 높게 나오면 모델보다 **데이터 분할**부터 의심한다.
- 비율을 바꾸는 것도 생성기의 가정(여기서는 split당 2000장 이하)을 건드릴 수 있다.
- 누출을 찾았으면 고친 데이터로 **다시 재서** 영향이 얼마였는지 확인한다. 이번처럼 0일 수도 있다.
- 깨끗한 test의 0.995도 같은 생성기, 같은 조명 범위에서 나온 사진에 대한 점수다. 실제 카메라 성능은 아니다.

## 9. CenterPose 시간 예측: 첫 측정은 버려야 한다

CenterPose 학습에 몇 시간이 걸릴지 알고 싶어서 직접 재 봤다. CenterPose는 사진 단위가 아니라 **물체마다 128×128로 잘라서** 학습한다. 8000장이면 한 epoch에 train 약 29,000개, val 약 3,600개다.

처음에는 물체 하나를 준비하는 데 12 ms가 나와서 CPU가 병목이라고 생각했다. 같은 측정을 세 번 반복하니 8.7 ms → 0.5 ms → 0.6 ms였다. 첫 번째 값만 시작 지연이 섞여 있었다. **벤치마크는 첫 회를 버리고 반복해서 본다.**

DataLoader의 `num_workers`를 바꿔 가며 초당 준비 개수를 쟀다(CPU만 사용, batch 128).

| num_workers | 초당 준비 개수 | 워커 메모리 |
|---|---|---|
| 0 | 553 | 0 |
| 2 | 4,209 | 0.14 GB |
| 4 | 8,797 | 0.15 GB |
| 8 | 13,532 | 0.37 GB |
| 16 | 23,257 | 0.60 GB |

GPU가 빈 상태에서 batch별 학습 시간도 쟀다. 앞의 3번은 버리고 10번을 평균했다.

| batch | ms/step | 물체당 ms | GPU 메모리 |
|---|---|---|---|
| 16 | 34 | 2.14 | 0.75 GB |
| 32 | 73 | 2.27 | 1.19 GB |
| 64 | 166 | 2.60 | 2.06 GB |
| 128 | 300 | 2.34 | 3.70 GB |
| 192 | 419 | 2.18 | 5.39 GB |
| 224 | 메모리 부족 | | |

**batch를 키워도 물체당 시간은 2.1~2.6 ms로 거의 그대로다.** 128×128 crop은 작아서 batch 16만으로도 GPU가 이미 꽉 찬다. 메모리를 최대로 쓴다고 빨라지지 않는다. 오히려 batch가 크면 한 epoch에 가중치를 고치는 횟수가 줄어든다.

워커 0개면 준비(물체당 1.8 ms)와 학습(2.1 ms)이 번갈아 돌고, 워커 4개면 준비가 학습 뒤에서 동시에 돈다. 8000장 기준 crop 수는 train 29,012개, val 3,630개다.

| 설정 | epoch당 | 40 epoch | 100 epoch |
|---|---|---|---|
| num_workers 0, batch 16 (원래 코드) | 약 2.1분 | 약 1.4시간 | 약 3.4시간 |
| num_workers 4, batch 16 | 약 1.1분 | 약 45분 | 약 1.8시간 |
| num_workers 4, batch 192 | 약 1.1분 | 약 45분 | 약 1.8시간 |

처음 사진 9,000장을 RAM에 올리는 시간(약 11 GB)은 빠져 있다. 처음 "CPU가 병목이라 13시간"이라고 어림했던 게, 측정을 두 번 고치고 나니 1.8시간이 됐다.
