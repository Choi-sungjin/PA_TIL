## 2. 로봇 파일은 하나가 아니라 넷이다

| 파일 | 맡는 일 | 읽는 쪽 |
|---|---|---|
| URDF | 링크·관절·축·한계 (기구) | 모두의 출발점 |
| SRDF | 계획 그룹(arm, gripper), TCP, 충돌 검사 제외 쌍 | MoveIt |
| XRDF | 충돌 구(sphere) 등 GPU 계획기용 구성 | cuMotion |
| USD | 물리·센서·장면 | Isaac Sim / Lab |

로봇 모양을 하나 만들었다고 계획·학습·실기 설정이 다 끝나지 않는다. 네 파일 사이에서 **관절 이름과 TCP 링크가 같아야** 한다.

- 순기구학(FK): 관절값 q를 받아 링크 변환을 차례로 곱하면 TCP 자세가 나온다. URDF 축과 원점이 맞는지는 관절을 하나씩 양의 방향으로 움직여 보면 바로 보인다.
- 역기구학(IK): 같은 TCP 위치에도 관절 해가 여러 개일 수 있고, 작업 공간 밖이면 해가 없다. **자유도가 모자란 팔에 6D 자세를 요구하면 안 된다.** 실습 데모 팔이 바로 이 경우였다. 관절이 3개라서 Reach 태스크에서 방향 보상을 아예 빼고, 목표 roll·pitch·yaw 범위를 0으로 고정해 두었다.
- 충돌 검사 제외 목록은 자동 생성 결과를 그대로 믿지 않는다. 제외 쌍을 늘리면 경로는 쉽게 나오지만, 실제로는 지나갈 수 없는 경로가 된다. 뺀 이유를 적어 둔다.
- XRDF 충돌 구는 너무 작으면 충돌을 놓치고, 너무 크면 좁은 통로를 막는다.
- TCP는 손목 링크와 다를 수 있다. 목표 좌표가 어느 링크 기준인지 확인한다.

## 3. 계획기 · 제어기 · 정책은 하는 일이 다르다

| 역할 | 하는 일 | 오늘 본 도구 |
|---|---|---|
| 계획기 | 충돌·한계를 고려해 관절 궤적을 만든다 | MoveIt 2 (OMPL), cuMotion |
| 제어기 | 현재 상태를 읽고 구동기에 명령을 쓴다 | ros2_control |
| 정책 | 관측을 받아 행동을 고른다 | Isaac Lab + RSL-RL PPO |

- **ros2_control에서 명령(command interface)과 상태(state interface)는 다른 통로다.** 명령값을 측정값처럼 되돌려 보내면, 로봇이 안 움직여도 "잘 따라갔다"고 보인다. 8절이 이 착각을 시뮬레이터 안에서 그대로 겪은 경우였다.
- command interface는 position / velocity / effort 중 실제 구동기가 지원하는 것으로 정한다.
- 계획 궤적 추종과 정책 추론은 다른 실행 모드다. 한 관절에 노드 두 개가 동시에 명령하지 않도록 선택기를 두고, 제어권은 항상 하나만 갖는다.
- MoveIt Servo는 카메라로 본 마지막 오차를 작은 속도 명령으로 줄이는 용도다. 장애물을 크게 돌아가는 계획을 대신하지 않는다. 전역 이동은 계획기, 마지막 보정은 Servo로 나눈다.
- cuMotion은 MoveIt에 붙는 GPU 계획기이고, cuRobo는 GPU 운동 생성 연구 도구다. GPU로 계획한다는 점은 같지만 구현은 따로 본다. 기본 실습은 cuMotion 플러그인 경로로 간다.
- 시연 영상에 나오는 계획 계산 시간과 시스템 전체 지연은 다른 숫자다.
- 힘 제어에서 임피던스는 위치 오차 → 힘, 어드미턴스는 측정한 힘 → 운동의 관계를 설계한다. 모터 전류만으로 손목 외력을 정확히 안다고 가정하지 않는다.
- 집기 작업은 목표 자세 하나로 설명이 안 된다. 접근 → 집게 닫힘 확인 → 물체 유지 확인 → 놓고 손 떼기처럼 단계마다 조건이 다르고, 실패하면 어느 단계로 돌아갈지도 정해 둬야 한다.

## 4. 정책학습: 관측 → 행동 → 보상

정책은 관측 o를 받아 행동 a를 고르는 함수이고, 학습은 신경망 가중치 θ를 바꾸는 일이다. 추론할 때는 θ를 고정한다.

```math
a_t \sim \pi_\theta(a \mid o_t)
```

**PPO는 알고리즘이고 RSL-RL은 그걸 돌리는 라이브러리다.** (RCL이 아니라 RSL이다.) PPO는 새 정책이 옛 정책에서 한 번에 너무 멀리 가지 않도록 확률비를 자른다. 10/23에 적은 ε = 0.2가 바로 이 자르는 폭이다.

```math
L^{clip} = \mathbb{E}\left[\min\left(r_t \hat{A}_t,\ \mathrm{clip}(r_t, 1-\epsilon, 1+\epsilon)\hat{A}_t\right)\right],\qquad r_t = \frac{\pi_\theta(a_t \mid o_t)}{\pi_{old}(a_t \mid o_t)}
```

환경을 만들 때 정하는 다섯 가지를 실습 데모 팔에 대입해 봤다.

| 항목 | 정할 것 | 데모 팔 Reach |
|---|---|---|
| 관측 | 이름·순서·단위·좌표계 | 관절 위치 3, 관절 속도 3, 목표 자세 7, 이전 행동 3 = 16 |
| 행동 | 위치 / 증분 / 속도 / 토크 중 무엇인지 | 관절 위치 목표, scale 0.6 |
| 보상 | 접근·성공·충돌·움직임 비용을 항목별로 | 아래 표 |
| 리셋 | 다음 시도의 초기 조건 | home 자세 `[0, -0.5, 1.0]`에서 시작 |
| 종료 | 성공 / 실패 / 시간 초과를 구분 | TCP가 목표 3 cm 안이면 success, 아니면 time_out |

행동 함수는 정책 출력 숫자를 모터 목표로 바꾼다.

```math
q_{target} = \mathrm{clip}\left(q_{ref} + s \cdot a,\ q_{min},\ q_{max}\right)
```

여기서 q_ref가 **현재 관절값인지 고정 기준(home)인지**를 반드시 적어야 한다. 실습 코드는 `use_default_offset=True`라서 기준이 home 자세다. 그리고 Lab은 scale과 offset을 적용한 **뒤에** clip하므로, clip 범위는 라디안 단위로 넣는다. 실습 코드는 "home ± 0.6 rad"와 관절 한계 중 좁은 쪽을 썼다.

보상은 항목을 나눠서 더한다.

```math
r = -w_d\, d - w_a \lVert \Delta a \rVert^2 - w_c\, c + w_s\, s
```

| 데모 팔 보상 항목 | 가중치 |
|---|---|
| end_effector_position_tracking (거리) | −0.2 |
| success | +10 |
| action_magnitude | −0.005 |
| action_rate | −0.0001 |
| joint_vel | −0.0001 |

거리만 줄이고 정작 작업은 못 하는 편법을 막으려고 성공 판정을 따로 둔다.

그 밖에 정리한 것:

- **Actor–Critic**: Critic에는 시뮬레이터만 아는 정답(물체의 정확한 자세 같은 것)을 줘도 된다. 하지만 Actor 입력은 실기에서 얻을 수 있는 값이어야 한다. 배포되는 건 Actor다.
- **종료 두 종류**: terminated(성공·낙하·충돌처럼 상태 때문에 끝남)와 truncated(시간 제한)를 따로 기록한다. 섞으면 "시간이 다 돼서 끝났다"와 "떨어뜨려서 끝났다"를 구분하지 못한다.
- **실행 순서**: 무행동(zero agent) → 작은 임의 행동 → 짧은 PPO → checkpoint 재생 → 그다음에 환경 수를 늘린다. 처음부터 수천 개 환경을 켜면 원인이 숨는다.
- **평가**: 학습 보상이 아니라, 학습에 쓰지 않은 초기 조건에서 성공 횟수/시도, 위치 오차, 충돌, 완료 시간, 추론 지연을 잰다. 계획기 · PPO · 모방학습을 같은 조건으로 비교하는 표를 채우는 게 최종 결과물이다. 공개 영상의 숫자는 옮기지 않는다.
- **Sim-to-real**: 질량·마찰·지연·센서 잡음이 다르다. 먼저 관절 하나, 접촉 하나로 모델을 맞춘 뒤, 측정한 범위 안에서 변동(domain randomization)을 준다.

## 5. 시연으로 배우는 쪽: BC · ACT · Diffusion · VLA

| 방법 | 내가 이해한 한 줄 |
|---|---|
| BC | 시연의 (관측, 행동) 쌍을 지도학습으로 맞춘다 |
| ACT | 한 스텝이 아니라 행동 묶음(chunk)을 한꺼번에 예측한다 |
| Diffusion Policy | 학습 때는 정답 행동에 넣은 잡음을 맞히고, 실행 때는 잡음에서 행동 시퀀스를 복원한다 |
| Mimic | 사람 시연 몇 개를 물체 기준 좌표로 옮겨 새 배치의 시연을 만든다. 옮긴 궤적이 실패하면 버린다 |
| GR00T (VLA) | 영상·언어·로봇 상태를 받아 행동을 낸다. 새 로봇에는 modality 설정과 자체 데이터가 필요하다 |

- ACT와 Diffusion은 설치 옵션만 다른 같은 알고리즘이 아니다.
- Diffusion은 추론이 여러 단계라 지연이 있다. 미래 행동을 길게 실행할수록 최신 관측이 늦게 반영된다.
- 시연 데이터도 어제 배운 것과 똑같다. **에피소드·촬영 세션 단위로** train / val / test를 나눈다. 연속 프레임이 갈라지면 점수가 부풀려진다.
- 내 로봇으로 VLA를 학습하려면 modality key, 단위, 상대/절대 행동, 집게 범위, 주기를 맞춰야 한다. GR00T는 별도 venv에 고정 revision으로 깔고, VLA에 강화학습을 더하는 후처리는 버전 고정이 또 달라서 확장 연구로 분리한다.

## 6. 데모 팔로 PPO 한 바퀴: 돌긴 돌았는데 숫자는 아직 아무것도 말하지 않는다

실습 저장소의 데모 팔(링크 5개, 회전 관절 3개, TCP `tool0`)로 처음부터 끝까지 한 번 돌렸다.

```bash
# URDF → USD
bash scripts/convert_urdf.sh assets/demo_arm.urdf models/demo_arm.usd

# 짧은 학습
bash scripts/lab.sh train --rl_library rsl_rl --task Practice-Reach-OwnArm \
  --num_envs 16 --max_iterations 10 physics=isaacsim_physx

# 마지막 checkpoint 재생
bash scripts/lab.sh play --rl_library rsl_rl --task Practice-Reach-OwnArm \
  --num_envs 1 --checkpoint "$CHECKPOINT" physics=isaacsim_physx
```

- 변환: 종료 코드 0. 그런데 EA 변환기는 `models/demo_arm.usd`를 **파일이 아니라 폴더**로 만들고, 실제 파일은 `demo_arm.usd/demo_arm/demo_arm.usda`에 둔다. 설정 JSON의 `usd_path`를 이 경로로 바꾼 사본을 따로 만들었다.
- 학습: 16 환경 × 24 스텝 × 10 iteration = 3,840 스텝, 9.96초.
- 재생: `model_9.pt`를 불러와 정책 재생이 시작되는 것까지 확인했다.

| | iteration 0 | iteration 9 |
|---|---|---|
| Mean reward | 0.21 | 0.12 |
| Mean episode length | 13.67 | 66.06 |
| Mean action std | 1.00 | 0.99 |
| `Episode_Termination/success` | 0.15 | 0.44 |
| `Metrics/success_rate` | 0.00 | 0.00 |

처음엔 보상이 떨어져서 학습이 거꾸로 가나 싶었다. 하나씩 따져 보니 다르게 읽어야 했다.

1. **정책은 거의 안 바뀌었다.** 행동 표준편차가 1.00 → 0.99다. 이 실행이 증명한 건 "변환 → 학습 → 저장 → 재생" 파이프라인이 끊기지 않는다는 것뿐이다.
2. **앞쪽 iteration의 보상·길이는 원래 치우쳐 있다.** 첫 iteration은 24스텝만 모으니까, 그 안에 끝난 짧은 에피소드만 평균에 들어간다. 평균 길이 13.67이 24보다 작은 게 그 증거다. 이 구간에서 보상이 줄고 길이가 늘었다고 나빠졌다고 말할 수 없다.
3. **success_rate 0과 success 종료 44%는 서로 모순이 아니었다.** 처음엔 둘 중 하나가 틀린 줄 알았다. Lab의 `Metrics/success_rate`는 목표 명령 설정에 `position_success_threshold`를 줘야 켜지고, 안 주면 항상 0을 찍는다. 실습 태스크는 그 값을 주지 않고 **자기 종료 조건(TCP가 목표 3 cm 안)** 으로 성공을 판정한다. `Episode_Termination/success`는 환경마다 직전 에피소드가 success로 끝났는지를 평균한 값이라, 0.44면 16개 중 7개꼴이다. **0이 "실패"가 아니라 "재지 않음"일 수 있다.**
4. **여기서 success는 "한 순간이라도 3 cm 안에 들어옴"이다.** 들어가는 순간 에피소드가 끝나므로, 그 자리에 머무는지 지나쳐 가는지는 보지 않는다. 집기나 접촉 안전성도 포함하지 않는다. 평가표의 "성공률" 칸에 쓰려면 이 정의를 같이 적어야 한다.

## 7. 내 로봇 V175: 화면에는 떴는데 관절이 전부 잠겨 있었다

V175 패키지(파일 1,452개, 무결성 검사 PASS)를 Isaac Lab에서 미리보기로 띄웠다.

첫 시도는 장면을 다 불러온 뒤에 멈췄다.

```
AttributeError: 'SimulationContext' object has no attribute 'is_running'
```

스크립트는 Lab main 문서를 보고 `sim.is_running`을 썼는데, EA의 `SimulationContext`에는 `is_playing` / `is_stopped` / `is_rendering`만 있다. 버전 문자열로 분기하지 않고 **그 기능이 있는지로 판단**하게 고쳤다.

```python
def app_running(sim, kit_app=None):
    running = getattr(sim, "is_running", None)
    if callable(running):
        return running
    if kit_app is None:
        import omni.kit.app
        kit_app = omni.kit.app.get_app()
    return kit_app.is_running
```

이러면 EA에서도, 이후 버전에서도 돈다. 덤으로, 로그를 파일로 보내면 `[REVIEW]` 줄이 끝날 때까지 안 보였다. stdout이 파일이면 파이썬이 블록 버퍼링을 하기 때문이라 `print(..., flush=True)`로 바꿨다.

고친 뒤에는 창 없이 300 프레임을 정상 종료했고, 창 모드에서도 로봇 표시와 웹캠 카메라 생성까지 확인했다. 창이 뜨기까지 첫 실행은 셰이더 캐시를 만드느라 수 분, 두 번째부터는 약 36초였다.

그런데 이 URDF를 실습의 `inspect_urdf.py`에 넣으니 `lm_slide: invalid effort/velocity`로 거부됐다. 열어 보니 모든 관절이 `lower=upper=0, effort=0, velocity=0`으로 잠겨 있었다. 기구학 확인용으로 일부러 잠가 둔 파일이었다. 동역학 입력 검사도 종료 코드 2, 누락 85개가 나왔다.

채워야 하는 값:

- 링크 14개: 질량, 질량중심, 관성 텐서
- 관절 8개(`lm_slide`, `shoulder`, `elbow`, `wrist_pitch`, `tool_roll`, `carousel`, 앞바퀴 2개): 위치 범위, 토크/힘 한계, 속도 한계, stiffness, damping
- 접촉: 정지·동마찰계수, 반발계수

URDF 변환기의 기본 밀도·관성으로 채우면 일단 돌아는 간다. 하지만 그건 내 로봇이 아니다. 수업에서 말한 "URDF를 불러오는 단계와 작업 성공을 구분한다"가 이거였다. **화면에 보인다는 건 1단계 통과일 뿐이다.**

## 8. V183 주행: 바퀴는 돌았는데 차체는 0 mm

V183은 V175에 앞바퀴 트레드 두 개를 붙인 버전이다. 패키지 실행기로 5초(1,200 스텝, 240 Hz)짜리 시험 세 개를 돌렸다.

| 시험 | 본 값 | 판정 |
|---|---|---|
| settle | 루트 z 9.2 mm → −0.2 mm에서 멈춤, 마지막 1초 관절속도 최대 0.074 rad/s | 정지 상태 도달 |
| drive | 앞바퀴 1.002 rad/s 추종, **평면 이동 0.000 m** (미끄럼이 없으면 0.137 m) | **주행 안 됨** |
| gripper (고정) | 턱 −3.25 ~ +2.78 mm 왕복, 두 턱 차이 최대 0.235 mm | 명령 추종 |

drive를 관절 로그로만 판정했으면 통과였다. 바퀴 속도는 명령과 0.2 % 차이였다. 그런데 차체 위치를 보니 1 mm도 가지 않았다. **관절이 명령을 따른 것과 로봇이 일을 한 것은 서로 다른 측정이다.**

### 원인 찾기

Lab은 속도 때문에 접촉 보고를 기본으로 꺼 둔다. CPU 물리에서 PhysX 접촉 보고를 켜고 다시 쟀다.

- 정지 후 최저점: 앞바퀴 −1.27 mm(바닥 속), 뒷바퀴 0.00 mm, 몸체 받침 −0.17 mm
- 주행 2초 동안 앞바퀴–바닥 접촉 **0건**. 받침과 뒷바퀴는 매 스텝 접촉했다
- 앞바퀴 접촉은 처음 1~2 스텝, 바닥과 0.2~0.5 mm 떨어져 있을 때만 잡히고, 바닥 안으로 들어가면 사라졌다

앞바퀴 충돌체(USD `Cylinder`)가 바닥에 살짝 박힌 뒤 접촉을 잃고 헛돈 것이다. 로봇은 앞바퀴보다 134~164 mm 앞에 있는 몸체 받침과 뒷바퀴로 서 있었다. 하중이 안 걸린 바퀴는 아무리 돌아도 차체를 밀지 못한다.

다음처럼 바꿔도 결과는 같았다 (CPU, 2초 주행).

| 바꾼 것 | 앞바퀴 접촉 충격량 | 2초 이동 |
|---|---|---|
| 원본 (Cylinder 3개) | 0 N·s | 0.00 mm |
| 바닥 위 1.2 mm에서 생성해 낙하 없앰 | 0 N·s | 0.00 mm |
| Cylinder 1개로 합침 (폭 15.2 mm) | 0 N·s | 0.01 mm |
| 재질을 뒷바퀴와 같은 rubber로 | 0 N·s | 0.01 mm |
| `collisionCylinderCustomGeometry=true` | 0 N·s | 0.00 mm |

GPU로 돌려도 같았다. 그러니까 반경·두께·재질·낙하 충격은 원인이 아니다. 원통 충돌체가 바닥에 조금 이상 박히면 접촉이 사라지는 것으로 보이는데, 정확한 조건까지는 가리지 못했다.

1.1 mm 높이 차이 자체는 설계값이다. 트레드 최저점이 받침보다 1.096 mm 낮아서, 실제 로봇은 앞바퀴로 선다.

### convex로 바꾸면 생기는 함정

원통 대신 볼록 껍질(convex hull)로 바꾸면 접촉은 잡힌다(충격량 약 75 N·s). 그런데 바퀴가 굴러가지 않았다.

- PhysX 쿠킹이 껍질 꼭짓점을 32개로 줄인다. 원기둥이 **16각 기둥**이 된다. 48각, 32각을 넣어도, `hullVertexLimit=64`를 줘도 같았다.
- 16각 바퀴는 0.2 rad 굴러 평평한 면에 앉은 뒤 멈췄다(2초에 6 mm). 구동이 속도 게인 0.15 × 1 rad/s = 0.15 N·m라서 모서리를 넘지 못한다.
- `collisionApproximateCylinders=true`도 결국 다각형이라 출발하지 못했다.

모서리 높이는 직접 계산해 봤다. 16각형이면 한 변이 22.5°라서, 꼭짓점과 면 중앙의 높이 차이는

```math
R\,(1-\cos 11.25^\circ) = 34.35 \times 0.0192 \approx 0.66\ \text{mm}
```

다. 0.15 N·m로는 이 0.66 mm 턱을 넘지 못한다.

### 고친 것

네 바퀴 충돌체를 모두 **16각 껍질 4개를 5.625°씩 돌려 겹친 것**으로 바꿨다. 22.5° / 4 = 5.625°라서 겹친 외곽선은 64각이 되고, 굴러갈 때 높이 변화는

```math
34.35 \times (1-\cos 2.8125^\circ) \approx 0.04\ \text{mm}
```

로 줄어든다. 반경·폭·재질은 패키지 값 그대로 두고, 원본 USD를 서브레이어로 깔고 바퀴 충돌체 4개만 덮어쓰는 레이어를 따로 만들었다. 패키지 원본은 건드리지 않았다.

| 실행 | 길이 | 평면 이동 | 미끄럼 없을 때 거리 | 마지막 1초 앞바퀴 |
|---|---|---|---|---|
| 원본 (GPU) | 5초 | 0.02 mm | 137.0 mm | 1.002 rad/s (헛돎) |
| 앞바퀴만 수정 (GPU) | 10초 | 114.7 mm, 약 5초에 멈춤 | — | −0.14 rad/s |
| 네 바퀴 수정 (GPU) | 10초 | **257.1 mm** | 251.5 mm | 0.83~0.89 rad/s |
| 네 바퀴 수정 (CPU) | 10초 | **251.9 mm** | 254.5 mm | 0.80 rad/s |

앞바퀴만 고쳤을 때 5초쯤에서 멈춘 건 뒷바퀴(Cylinder, 반경 33 mm)가 같은 문제에 걸려서였다. 뒷바퀴가 바닥 속 1.28 mm까지 빠지면서 차체가 뒤로 2.6° 기울고, 뒤쪽 몸체 부품이 바닥에 끌렸다. **하나를 고치면 다음으로 약한 고리가 드러난다.**

네 바퀴를 다 고친 뒤에는 1초부터 끝까지 초당 약 28 mm로 일정하게 갔다. 정지 후 루트 z는 1.09 mm로, 이제 앞바퀴로 선다. 접촉 보고를 켠 CPU 9초 주행에서 몸체가 바닥에 닿은 적은 없었다.

남은 것:

- 바퀴가 1 rad/s보다 느리다(0.80~0.89). 구동이 감쇠(0.15)만 있는 속도 제어라 하중이 걸리면 오차가 남는다.
- 주행 중에 팔 관절이 흔들린다. 마지막 1초 관절속도가 최대 0.21~0.30 rad/s로, 정지 시험의 0.07 rad/s보다 크다.
- 마찰·질량은 아직 추정값이다(PLA 트레드 0.45/0.35, 바닥 0.7/0.6).
- 창 모드로 보면 렌더링 때문에 10초 주행에 실제로 10분 넘게 걸린다.

## 9. 막혔던 지점 / 메모

| 증상 | 원인 | 한 것 |
|---|---|---|
| `list_envs` 명령이 없음 | EA의 `isaaclab` CLI에는 train / play / zero_agent / random_agent만 있다 | gym registry에 태스크 이름이 있는지 파이썬 한 줄로 확인 |
| `SimulationContext`에 `is_running` 없음 | 문서는 main 기준, 설치는 EA | 기능 유무로 분기 (7절) |
| 변환한 USD 경로가 설정과 안 맞음 | EA 변환기가 출력 경로를 폴더로 만든다 | `usd_path`를 `.../demo_arm/demo_arm.usda`로 |
| 컨테이너 안 `ros2` 명령이 전부 실패 | 호스트 bashrc의 `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp`가 컨테이너에 없는 구현이다 | bashrc를 넘기지 않고 `ROS_DOMAIN_ID`만 넘김 |
| 로그에 진행 줄이 안 찍힘 | 파일 출력일 때 블록 버퍼링 | `flush=True` |

- MoveIt 2 · Setup Assistant · Servo · ros2_control · cuMotion 예제를 미리 깔아 둔 Lyrical 이미지를 하나 만들었다(빌드 약 5분). 컨테이너를 열 때마다 apt로 까는 것보다 낫다. Setup Assistant 결과 패키지는 마운트한 워크스페이스의 `src`에 저장해야 컨테이너를 닫아도 남는다.
- Sim ↔ Lyrical을 연결할 때는 양쪽 터미널에서 `ROS_DOMAIN_ID`, `RMW_IMPLEMENTATION`, `ROS_AUTOMATIC_DISCOVERY_RANGE`를 같은 값으로 맞춘 뒤 시작한다. 호스트 터미널에는 TurtleBot 때 넣어 둔 DDS 설정이 걸려 있어서 그대로 두면 엇갈린다.
- 수업의 문제 진단 순서는 "모델 형상 → 관절 하나 → 상태 수신 → 작은 명령 → 계획 → 학습"이었다. V183은 "작은 명령" 단계에서 걸렸다. 여기서 바로 주행 정책을 학습시켰다면, 보상이 안 오르는 이유를 학습 설정에서 찾느라 시간을 버렸을 것이다. **학습 전 단계에서 실패한 걸 학습을 더 오래 돌려서 해결하려 하지 않는다.**
