## 1. bag 은 파일 하나가 아니라 폴더다

`ros2 bag record` 가 만드는 건 파일이 아니라 폴더 하나다.

```text
motion_20261008_125139/
├── metadata.yaml                                       ← 토픽·형식·메시지 수·기간 요약
└── 0_motion_20261008_125139_2026_10_08-12_56_36.mcap   ← 실제 메시지
```

`ros2 bag info` 가 보여주는 건 `metadata.yaml` 의 요약이고, 메시지 자체는 `.mcap` 안에 있다. 그래서
옮길 때도 **폴더째** 옮기고, 무결성도 두 파일 모두 해시로 본다. 공유 드라이브에는 이렇게 올라와 있었다.

| 폴더 | 장면 | 길이 | 크기 |
|---|---|---|---|
| `01_필수_문제5_bag/assignment5_success_…` | 정지 목표, 손대지 않음 | 20.7 s | 590.3 MiB |
| `01_필수_문제5_bag/assignment5_lost_…` | 손바닥으로 가렸다가 치움 | 15.2 s | 445.7 MiB |
| `02_추가_모터추적_bag/motion_…` | 원통을 들고 옮기면 팬·틸트가 따라감 | 15.5 s | 452.7 MiB |

같이 올라온 `SHA256SUMS.txt` 로 내려받은 쪽에서 한 번에 확인할 수 있다.

```bash
sha256sum -c SHA256SUMS.txt     # 파일마다 OK / FAILED 가 나온다
```

오늘 비교에 쓴 두 bag 은 숫자를 보기 전에 해시부터 맞췄다.

| 파일 | SHA-256 (앞 12자리) | 기록된 값과 일치 |
|---|---|---|
| 원본 motion `.mcap` | `a2d150242c49…` | O |
| 원본 motion `metadata.yaml` | `18f4a49e29b2…` | O |
| 재생 `.mcap` | `2d42c4091a3e…` | O |
| 재생 `metadata.yaml` | `80de7695b3f0…` | O |

해시가 맞아야 그다음 비교가 "다른 파일을 같은 방법으로 계산했다"가 아니라 "**같은 파일**에서 같은
계산을 했다"가 된다.

## 2. 파일 크기만으로 메시지 수를 검산할 수 있다

`ros2 bag info` 의 메시지 수가 맞는지, 파일을 열지 않고 크기로 맞춰볼 수 있었다. 영상 한 장의 크기는
정해져 있다.

```text
컬러  640 × 480 × 3 B (rgb8)   = 921,600 B
깊이  640 × 480 × 2 B (16UC1)  = 614,400 B
```

| bag | 컬러 장수 | 깊이 장수 | 영상만으로 계산한 크기 | 실제 `.mcap` 크기 | 비율 |
|---|---|---|---|---|---|
| success | 432 | 358 | 618,086,400 B | 618,942,046 B | 99.86 % |
| lost | 345 | 242 | 466,636,800 B | 467,371,169 B | 99.84 % |
| motion | 325 | 284 | 474,009,600 B | 474,729,902 B | 99.85 % |

**bag 크기의 99.8 % 이상이 영상**이다. `/target`, 관절 상태, 명령, 상태 문자열 같은 나머지 메시지
3,200 ~ 3,600 개와 MCAP 색인을 다 합쳐도 1 MB 가 안 된다. 메시지 수와 파일 크기가 서로 맞으니
`metadata.yaml` 의 요약도 믿을 수 있다.

같은 계산으로 하나가 더 보였다. 카메라는 30 fps 로 돌았는데 bag 에 들어간 컬러 영상은

```text
success  432 / 20.70 s = 20.9 Hz   (30 fps 의 69.6 %)
lost     345 / 15.22 s = 22.7 Hz   (75.6 %)
motion   325 / 15.52 s = 20.9 Hz   (69.8 %)
```

컬러+깊이를 30 fps 로 전부 쓰려면 $30 \times (921{,}600 + 614{,}400) \approx 46.1$ MB/s 가 필요한데,
실제로 쓰인 양은 세 bag 모두 약 30 MB/s 였다. 즉 **bag 에는 카메라가 낸 프레임이 다 들어 있지 않다.**
Pi 가 SD 카드에 쓰면서 노드도 같이 돌린 부하로 보이지만 원인은 확인하지 않았다. 중요한 건 결론이다.
bag 을 다시 틀어서 하는 재현은 **"기록된 프레임"까지만** 재현할 수 있다.

## 3. "재현" 이라고 부르는 게 네 가지였다

문제 5 자료를 읽다 보니 같은 "재현"이라는 말이 서로 다른 일을 가리키고 있었다. 무엇을 다시 실행하느냐에
따라 증명하는 범위가 다르다.

| 이름 | bag 에서 꺼내 쓰는 것 | 다시 실행하는 것 | 보여주는 것 | 보여주지 못하는 것 |
|---|---|---|---|---|
| 입력 재처리 | 컬러·CameraInfo·깊이·관절 | 검출기 (`/target_replay` 로 출력) | 같은 영상에 같은 검출이 나오는가 | 기록 안 된 프레임 |
| 결과 재분석 | `/target`·`/tracking_status`·`/pan_tilt/command` | 지표 계산만 | 실행 중 CSV 와 같은 지표가 나오는가 | 검출기 자체의 재현 |
| 실제 모터 재생 | `/pan_tilt/command` 만 | 모터 브리지 → 실제 모터 | 같은 명령에 같은 움직임이 나오는가 | 영상에 반응하는 추적 (폐루프) |
| 기록 재분석 (오늘) | 원본 bag + 재생 bag | 비교 코드만 | 보고서 숫자가 파일에서 나오는가 | 새 실물 거동 |

실제 모터 재생은 카메라·검출·제어 노드를 띄우지 않고 **기록된 속도 명령을 같은 시간 간격으로 그대로
보내는 개루프 재생**이다. 원통이 어디 있든 상관없이 기록 때 명령대로 움직인다. 오늘 한 건 맨 아래
줄이고, 모터는 건드리지 않았다.

## 4. 비교 방법 — 두 bag 의 시간 0 을 맞추기

원본은 12:56, 재생은 14:21 에 기록됐으니 시각을 그대로 겹칠 수는 없다. 비교 코드는 이렇게 맞춘다.

1. 각 bag 에서 **첫 `/pan_tilt/command` 의 기록 시각을 0** 으로 둔다. `header.stamp` 가 아니라 bag 에
   기록된 수신 시각이다.
2. 두 bag 중 짧은 쪽 명령 기간까지 **0.05 s 간격 격자**를 만든다. $15.456 / 0.05$ 라서 표본 310 개.
3. 각 격자 시각에서 관절 각도를 **선형 보간**한다.
4. 차이 = 재생 − 원본, `RMS = sqrt(mean(차이²))`, `최대 = max(|차이|)`.

```python
o0, p0 = oc[0, 0], pc[0, 0]                     # 각 bag 의 첫 명령 시각
oj[:, 0] -= o0; pj[:, 0] -= p0                  # 관절 시각을 첫 명령 기준으로
dur = min(oc[-1, 0] - o0, pc[-1, 0] - p0)       # 짧은 쪽 명령 기간
t = np.arange(0, dur, 0.05)                     # 공통 격자
op = np.interp(t, oj[:, 0], oj[:, 1])           # 원본 pan
pp = np.interp(t, pj[:, 0], pj[:, 1])           # 재생 pan
```

이 비교 코드를 기준 커밋(`db6e165`) 그대로, 한 줄도 고치지 않고 다시 돌렸다. 출발·끝 자세와 전체
RMS·최대값이 보고서 표와 **표시 자릿수까지** 같게 나왔다.

## 5. 명령은 끝까지 똑같았다

먼저 입력 쪽부터 봤다. 모터를 움직인 원인이 같다는 게 확인돼야 결과 차이를 모터 쪽 문제로 좁힐 수 있다.

```text
명령 수          원본 681  /  재생 681
순서별 값 비교   681 쌍 모두 동일 (pan·tilt 속도 최대 차이 0)
첫~끝 명령 기간  원본 15.456736 s  /  재생 15.456421 s   (차이 0.31 ms)
```

`ros2 bag play` 는 15 초 동안 명령 간격을 0.3 ms 안쪽으로 지켰고, 값은 한 개도 바뀌지 않았다.
**입력은 완벽하게 재현됐다.**

## 6. 그런데 끝 자세는 4.3° 달랐다 — 속도 명령은 차이를 적분한다

|  | 원본 | 재생 | 차이 |
|---|---|---|---|
| 출발 pan / tilt | $-10.02°$ / $26.28°$ | $-9.66°$ / $25.84°$ | $+0.36°$ / $-0.44°$ |
| 끝 pan / tilt | $-22.46°$ / $1.07°$ | $-26.77°$ / $0.53°$ | $-4.31°$ / $-0.54°$ |

구간을 나눠서 다시 집계했다.

| 구간 (첫 명령 기준) | 표본 | pan RMS / 최대 | tilt RMS / 최대 |
|---|---:|---:|---:|
| 전체 $0 \le t < 15.456$ s | 310 | $1.96°$ / $5.34°$ | $0.81°$ / $2.55°$ |
| $0 \le t \le 11.0$ s | 221 | $0.56°$ / $2.04°$ | $0.74°$ / $1.40°$ |
| $12.0 \le t < 15.4$ s | 68 | $3.68°$ / $5.08°$ | $1.02°$ / $2.55°$ |

앞 11 초는 1° 안팎으로 같이 움직였는데, 12 초 이후로는 pan 이 평균 $-3.65°$ 어긋난 채로 끝까지 갔다.
처음엔 끝에 가면 다시 맞을 줄 알았는데, 안 맞는 게 당연했다. 이 명령은 **각도가 아니라 속도**다.

```math
\theta(t) = \theta(0) + \int_0^t \omega(\tau)\, d\tau
```

같은 $\omega$ 를 보내도 $\theta(0)$ 이 다르면 그 차이는 끝까지 그대로 가고, 도중에 모터가 명령을 조금
다르게 따라간 구간이 있으면 그 차이도 적분돼서 남는다. 목표 각도가 없으니 **되돌려 놓는 힘이 어디에도
없다.**

이게 두 축에서 다르게 나타났다. 비교 코드에 출발점 차이를 빼고 "움직인 양"만 비교하는 값이 있어서
같이 봤다.

| | 그대로 비교한 RMS | 출발점 보정 RMS |
|---|---|---|
| pan | $1.96°$ | $2.14°$ (오히려 커짐) |
| tilt | $0.81°$ | $0.44°$ (절반 가까이 줄어듦) |

- **tilt** 는 출발 차이 $-0.44°$ 가 전체 평균 차이 $-0.75°$ 의 절반이 넘는다. 출발점에서 생긴 차이가
  그대로 끌려다닌 쪽이다.
- **pan** 은 출발 차이가 $+0.36°$ 인데 나중 차이는 $-3.65°$ 로 부호가 반대다. 출발점을 빼면 오히려 더
  벌어진다. 출발이 아니라 **도중에 생긴 차이가 쌓인 쪽**이다.

RMS 하나만 봤으면 "pan 2°, tilt 0.8° 정도 차이" 로 끝났을 텐데, 차이가 **어디서 생겼는지**는 출발점을
보정해 봤을 때 갈렸다.

## 7. 원본 기록에 0.9 초짜리 구멍이 있었다

그럼 12 초 근처에서 무슨 일이 있었나 보려고 원본 관절 상태의 기록 시각 간격을 봤다.

```text
관절 상태 메시지   원본 772 개 (약 50 Hz)
가장 큰 공백      11.063677 s → 11.968896 s   (0.905 s)
```

50 Hz 면 0.02 s 마다 와야 하는데 0.9 초 동안 하나도 없다. 대략 45 개가 빠진 셈이다. 팀 보고서에도
비슷한 시점에 입력 시간 초과(`input_timeout`) 상태가 기록돼 있다.

문제는 비교 코드가 이 구간을 `np.interp` 로 **직선으로 이어 버린다**는 것이다. 0.05 s 격자에서
11.10 ~ 11.95 s 의 표본 18 개는 측정값이 아니라 보간값이고, 전체 RMS $1.96°$ 에는 이 18 개가 섞여 있다.
그리고 pan 차이가 벌어지기 시작한 게 바로 이 공백 직후다. 원본 쪽 모터가 그 0.9 초 동안 실제로 어떻게
움직였는지는 **기록이 없으니 모른다.** 그래서 12 초 이후 차이의 원인은 오늘 결론 내지 않았다.

RMS 를 계산하기 전에 **시각 간격의 최댓값부터 보는 습관**이 필요하다. `np.interp` 는 구멍이 있어도
에러를 내지 않는다.

## 8. 15.4 초를 넣느냐 빼느냐

구간별 값을 보고서와 맞추다가 한 군데서 걸렸다. "12.0 ~ 15.4 s" 를 `12.0 <= t <= 15.4` 로 잡으면
표본 69 개에 pan RMS $3.69481°$, tilt RMS $1.00976°$ 가 나와서 보고서의 $3.68°$ / $1.02°$ 와 안 맞는다.
**15.4 s 표본을 빼야** (`t < 15.4`, 68 개) $3.68498°$ / $1.01664°$ 로 맞는다.

| 경계 | 표본 | pan RMS | tilt RMS | 보고서 값과 |
|---|---:|---:|---:|---|
| `12.0 <= t <= 15.4` | 69 | $3.69481°$ | $1.00976°$ | 불일치 |
| `12.0 <= t < 15.4` | 68 | $3.68498°$ | $1.01664°$ | 일치 |
| `0 <= t <= 11.0` | 221 | $0.55864°$ | $0.74001°$ | 일치 |
| `0 <= t < 11.0` | 220 | $0.55958°$ | $0.73972°$ | 일치 |

반면 "0 ~ 11 s" 는 11.0 s 를 넣든 빼든 반올림하면 $0.56°$ / $0.74°$ 라서 경계가 드러나지 않았다.
차이가 작고 고른 구간에서는 표본 하나가 숫자를 못 바꾸고, **차이가 크게 출렁이는 구간에서만 표본 하나가
셋째 자리를 바꾼다.**

"12.0 ~ 15.4 s" 라는 표기만 보고는 이걸 알 수 없다. 구간을 적을 때는 **부등호와 표본 수까지** 적어야
다른 사람이 같은 숫자를 다시 만들 수 있다.

## 10. 막혔던 지점 / 메모

- **"명령이 같다"와 "움직임이 같다"는 다른 층이다.** 파일 해시 → 메시지 값 → 시간 간격 → 실제 각도 순으로
  한 층씩 확인해야 차이가 어느 층에서 생겼는지 말할 수 있다. 오늘은 앞의 세 층이 완전히 같았기 때문에
  차이를 모터 쪽으로 좁힐 수 있었다.
- **평균 하나가 두 개의 이야기를 섞는다.** 전체 pan RMS $1.96°$ 는 앞 11 초의 $0.56°$ 와 뒤 3.4 초의
  $3.68°$ 를 섞은 값이다. 실제로는 어느 구간도 $1.96°$ 처럼 움직이지 않았다.
- **보간은 조용하다.** 0.9 초 공백을 직선으로 메운 값이 RMS 안에 들어가도 결과 표에는 아무 표시가 없다.
- **공유 드라이브 압축을 풀었더니 바깥 폴더 이름의 한글이 자모가 분리된 형태(NFD)였다.** 화면에는
  똑같이 보이는데 터미널에서 직접 친 경로(NFC)로는 `cd` 가 되지 않는다. 안쪽 폴더 이름은 정상(NFC)이라
  `**/02_추가_모터추적_bag/motion_*` 처럼 glob 으로 안쪽 이름부터 찾아 들어갔다.
- 결과를 보자마자 원인을 쓰고 싶었지만, 공백 구간의 실제 움직임은 기록이 없으니 **"원인 미확정"** 으로
  남겼다. 기록 재분석이 증명하는 건 "보고서 숫자가 이 파일에서 나온다"까지다.
