# 2026-08-11 TIL — C++ 클래스로 센서 모델링하기

> 5강 실습 코드 리뷰. 센서를 클래스로 묶어 IMU/LiDAR로 파생시키는 예제를 읽으면서 접근 지정자, 가상 함수, 스마트 포인터가 왜 필요한지를 짚었다.

---

## 1. 예제가 불러온 표준 라이브러리

코드 맨 위 `#include` 목록만 봐도 이 프로그램이 무엇을 하는지 대충 보인다.

| 헤더 | 쓰임 |
|---|---|
| `<iostream>` | `cout`, `cin` 등 입출력 스트림 |
| `<vector>` | 동적 배열 |
| `<memory>` | 스마트 포인터 |
| `<random>` | 난수 생성 |

Python에서는 import 없이도 쓰던 것들이 C++에서는 전부 명시적으로 끌어와야 한다. 반대로 말하면 헤더 목록이 그 파일의 의도를 설명하는 요약본 역할을 한다.

---

## 2. 센서를 클래스로 묶기

### 왜 묶는가

IMU와 LiDAR는 하는 일이 다르지만 "센서"라는 공통 카테고리로 묶인다. 그래서 `Sensor`를 기반 클래스로 두고 `IMU`, `LiDAR`를 여기서 파생시켰다. 공통된 성질은 위에 한 번만 쓰고, 다른 부분만 아래에서 채우는 구조다.

```
Sensor (공통 카테고리)
 ├── IMU
 └── LiDAR
```

### public과 protected

이 둘은 완전히 갈린다. 같은 `Sensor` 안에 있어도 접근 범위가 다르다.

| 지정자 | 누가 쓸 수 있나 | 이 예제에서 넣은 것 |
|---|---|---|
| `public` | 외부에서 접근·호출 가능 | 상태 조회, 데이터 읽기 |
| `protected` | 자기 클래스 + 파생 클래스만 | 데이터 배열을 실제로 채우는 동작 |

기준이 "중요한 거 / 안 중요한 거"가 아니라 **기능의 방향**이었다는 게 포인트다. 밖에서는 읽기만 되고, 값을 채워 넣는 쓰기 쪽은 센서 계열 안에서만 하도록 잘랐다. 외부가 데이터를 마음대로 덮어쓰지 못하게 막는 셈이다.

---

## 3. 가상 함수와 override

기반 클래스 쪽 함수는 아직 자기가 IMU인지 LiDAR인지 모른다. 그냥 "센서라면 이런 걸 할 수 있다"는 자리만 비워둔 상태다.

파생 클래스에서 `override`를 붙여 그 자리를 채우면, 위에서는 이름이 정해져 있지 않던 함수가 아래에서 IMU용·LiDAR용으로 각각 구현된다. 나중에 조회할 때는 기반 쪽 인터페이스 하나만 들고 있으면 되고, 실제로 어느 구현이 불릴지는 객체가 결정한다.

강사도 짚었지만 **실무 로봇 코드에서 센서를 이렇게 직접 짜는 경우는 드물다.** 대부분 이미 정의된 것을 가져다 쓴다. 이 예제는 클래스 개념을 눈으로 보라고 만든 것이라 실제보다 절차가 많다. 그 전제를 모르고 보면 "이걸 매번 이렇게 짜야 하나" 싶어 헷갈린다.

## 4. 데이터 채우고 출력하기

### 난수로 가짜 센서 값 만들기

실제 센서가 아직 없으니 `<random>`으로 범위를 정해 값을 만들어 채웠다. 범위를 지정해서 뽑는 방식은 Python의 random과 비슷하다.

개수를 다르게 준 이유가 있다.

- **LiDAR** — 8개 이상. 스캔 포인트가 많다.
- **IMU** — 보통 6개. 위치 x·y·z와 속도 x·y·z를 묶어 6축으로 들어온다.

숫자를 아무렇게나 정한 게 아니라 실제 센서가 뱉는 데이터 모양을 흉내 낸 것이다.

### 이중 for문으로 순회

출력은 범위 기반 for문을 겹쳐서 했다. 바깥쪽이 센서, 안쪽이 그 센서의 데이터 원소를 훑는다.

```cpp
for (const auto& sensor : sensors) {
    for (const auto& value : sensor.data()) {
        std::cout << value << " ";
    }
}
```

`const auto`로 받는 건 순회하면서 값을 건드리지 않겠다는 선언이다. 출력만 할 거면 굳이 복사하거나 수정 권한을 열어둘 이유가 없다.

`main`은 의외로 짧다. 선언해 둔 클래스를 불러와서 데이터를 읽는 게 전부다. 복잡한 건 전부 클래스 안으로 들어가 있다.

### 실제 IMU는 어떤 데이터를 주나

수업 중에 실물 IMU 센서 문서를 같이 봤다. 설정에 따라 들어오는 데이터가 달라지고, 각도만 오기도 하고 지자기 값만 오기도 하고 각속도가 섞여 오기도 한다. 전부 배열 형태다. 단위도 문서에 명시돼 있는데 각도는 도(degree) 단위로 나온다.

즉 센서를 붙이기 전에 **문서에서 "무엇이 몇 개, 어떤 단위로 오는가"를 먼저 확인해야** 배열 크기와 타입을 제대로 잡을 수 있다.

## 5. 스마트 포인터 — 왜 필요한지가 안 보이는 이유

C++은 동적 언어가 아니라서 타입을 미리 선언해야 하고, 그래야 메모리를 얼마나 쓸지 정할 수 있다. 그리고 다 쓴 메모리는 직접 해제해야 한다. 안 하면 누수가 쌓인다.

스마트 포인터는 이 해제를 자동으로 해준다. 개념은 간단한데, 실습에서 감이 안 잡히는 이유도 명확했다 — **메모리가 어떻게 되고 있는지가 눈에 안 보이기 때문이다.** 값 몇 개 돌리는 예제에서는 누수가 나든 말든 티가 안 난다.

체감되는 지점은 데이터가 쏟아질 때다. IMU 정도는 괜찮지만 LiDAR는 다르다. 실제 ROS 개발에서 자주 겪는 트러블슈팅 중 하나가 **데이터가 계속 누적돼서 메모리가 터지고, 결국 새 데이터가 아예 안 들어오는** 상황이라고 한다. 한 번 겪어봐야 스마트 포인터가 왜 있는지 이해된다는 말이 남았다.

---

## 6. 기본 자료형 정리

`long`을 물었다가 답이 엇갈린 장면이 있었다. LiDAR 데이터 타입을 `long`으로 말했다가 바로 `double`로 정정됐다. **거리 값은 소수점이 필요하니 정수형이 아니다.** 타입은 크기만 보는 게 아니라 "소수가 필요한가"를 먼저 봐야 한다.

| 타입 | 크기 | 성격 |
|---|---|---|
| `int` | 4바이트 | 정수 |
| `long` | 8바이트 | 정수 |
| `float` | 4바이트 | 소수 |
| `double` | 8바이트 | 소수 |
| `char` | 1바이트 | 문자 (−128 ~ 127) |

`unsigned`를 붙이면 음수가 사라지고 0부터 시작한다. 같은 크기로 양수 범위를 두 배로 쓰는 것이다.

### char가 왜 숫자 범위로 적혀 있나

문자 타입인데 표에는 `-128 ~ 127`이라고 숫자로 적혀 있어서 처음엔 이상해 보였다. 컴퓨터는 문자를 그대로 이해하지 못하고 ASCII 코드로 변환해서 저장하기 때문이다. 그 숫자 범위 안에 들어가는 것만 담을 수 있고, 그래서 `char` 하나에는 알파벳 한 글자만 들어간다.

## 8. 막혔던 지점 / 메모

- **public / protected를 "공개 여부"로만 보면 나눌 기준이 안 선다.** 읽기는 밖에 열고 쓰기는 안으로 닫는다는 식으로 **동작의 방향**을 기준으로 잡으니 정리가 됐다.
- 기반 클래스에서 이름이 안 정해진 함수를 보고 "이게 뭘 하는 함수지?" 하고 막혔는데, `override`로 파생 쪽에서 채워진다는 걸 알고 나서야 위아래가 연결됐다. 위쪽은 자리만 잡아두는 것.
- IMU 6축을 위치 3 + 속도 3으로 잡고 예제를 만들었는데, 실제 센서 문서에는 각도·각속도·지자기 값 같은 게 설정에 따라 다르게 들어온다. **예제의 6개와 실물 센서의 6개가 같은 것이라고 착각하면 안 된다.** 실제로 붙일 때는 문서를 다시 확인할 것.
- 스마트 포인터는 개념은 알겠는데 필요성이 안 느껴지는 게 정상이다. 데이터가 적은 예제에서는 누수가 보이지 않는다. LiDAR 물리고 나서 다시 볼 주제로 남긴다.
- 예제 파일에서 주석 한글이 깨져 보이는 문제가 있었다. 인코딩 문제로 보이니 코드 받을 때 확인할 것.
- 이 단계 목표는 완벽한 이해가 아니라 **"이 데이터에는 어떤 타입을 쓰나"에 바로 답할 수 있는 정도**다. 인자 순서 같은 건 나중에 찾아보면 된다.
