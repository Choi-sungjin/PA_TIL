## 1. 오늘 익힌 명령어 정리

### 상태 확인 (습관화할 것)

| 명령어 | 하는 일 | 언제 쓰나 |
|---|---|---|
| `git status` | 어떤 파일이 바뀌었는지 | add 전에 무조건 |
| `git diff` | 구체적으로 무엇이 바뀌었는지 | 커밋 내용 확정 전 |
| `git diff --staged` | 스테이징에 올라간 변경만 | commit 직전 최종 확인 |
| `git log --oneline --graph` | 이력을 그래프로 | 브랜치 모양 볼 때 |

`git log --oneline --graph --all`까지 붙이면 다른 브랜치까지 한 화면에 나온다. merge/rebase 차이를 눈으로 확인할 때 이게 핵심이었다.

### 기본 사이클

```bash
git clone https://github.com/team/repo.git   # 최초 1회
git status
git diff
git add <파일>
git commit -m "메시지"
git push origin main
```

### 브랜치

```bash
git switch -c feature/xxx   # 생성 + 이동 (한 번에)
git switch main             # 복귀
git branch                  # 목록
```

`git checkout -b` 대신 `git switch -c`를 쓰는 게 요즘 방식. `checkout`이 "브랜치 이동"과 "파일 복원" 두 가지를 다 해서 헷갈렸는데, `switch`(브랜치) / `restore`(파일)로 역할이 쪼개진 거였다.

### 합치기

```bash
# merge
git switch main
git merge feature/xxx

# rebase
git switch feature/xxx
git rebase main
git switch main
git merge feature/xxx   # fast-forward
```

## 2. Git의 4개 공간

```
작업 디렉터리  --(git add)-->  스테이징  --(git commit)-->  로컬 저장소  --(git push)-->  원격
     ^                                                                                    |
     +--------------------------------(git pull)-----------------------------------------+
```

"내 변경이 지금 **어디에** 있는가"를 이 4칸으로 놓고 보니 정리가 됐다.

**스테이징이 왜 중간에 있나?** 처음엔 add가 귀찮은 절차라고만 생각했는데, 이유가 있었다 — 수정한 것 **전부**가 아니라 **일부만 골라** 의미 있는 단위로 커밋하기 위해서다. 파일 5개를 고쳤어도 관련 있는 2개만 add해서 커밋을 쪼갤 수 있다.

## 3. merge vs rebase — 결과는 같은데 이력이 다르다

- **merge**: 병합 커밋을 하나 새로 만든다. "언제 갈라졌고 언제 합쳐졌는지"가 사실 그대로 남는다.
- **rebase**: 내 커밋들을 최신 main 끝으로 **옮겨서 다시 쌓는다**. 이력이 한 줄로 깔끔해진다.

핵심은 rebase가 "옮기는" 게 아니라 **원래 커밋을 버리고 새 커밋으로 다시 쓰는** 작업이라는 점. 커밋 해시가 바뀐다.

| 상황 | 선택 |
|---|---|
| 공유 브랜치(main)에 기능 합치기 | **merge** (이력 보존) |
| 내 로컬 브랜치를 최신 main과 동기화 | **rebase** (깔끔) |
| 이미 push한 커밋 | **rebase 금지** |

### push 한 커밋은 rebase 하지 않는다

**push해서 남이 봤을 수 있는 커밋은 rebase하지 않는다.** 이력을 다시 쓰는 순간 팀원들이 가진 이력과 어긋나서 저장소가 꼬인다. rebase는 아직 나만 가지고 있는 로컬 커밋에만.

같은 이유로 `--force` push도 금지. 이건 규칙으로 못 박아둔다.

## 4. 충돌(conflict) — 에러가 아니라 질문이다

같은 파일의 같은 줄을 양쪽에서 다르게 고치면 Git이 판단을 포기하고 사람에게 넘긴다. **오류가 아니라 "여기는 사람이 정해주세요"라는 정상적인 물음**이라는 관점이 도움이 됐다.

파일에 삽입되는 표식의 의미:

```
<<<<<<< HEAD          ← 여기부터: 현재 브랜치(내가 서 있는 쪽)의 내용
    (A 버전)
=======               ← 경계선
    (B 버전)
>>>>>>> feature/xxx   ← 여기까지: 합치려는 브랜치의 내용
```

### 해결 3단계

1. 두 버전을 읽고 **올바른 최종 코드를 직접 작성**한다. 표식 3줄(`<<<<<<<`, `=======`, `>>>>>>>`)은 **전부 지운다**.
2. `git add <파일>` — "해결했음" 표시
3. `git commit` (merge 중) 또는 `git rebase --continue` (rebase 중)

둘 중 하나를 기계적으로 고르는 게 아니라, **두 변경의 의도를 통합**하는 게 맞는 해결일 때가 많다. 예를 들어 한쪽이 "안전 위해 감속", 다른 쪽이 "테스트 위해 증속"이면 → 기본값은 안전값으로 두고 테스트 플래그로 증속을 허용하는 제3의 코드가 정답.

**예방책**: 브랜치를 작게·짧게 유지(하루~며칠), main 변경을 자주 가져와서 격차를 줄이기.

## 5. PR 사이클

```
① 브랜치 생성 → ② 작업·커밋 → ③ 푸시 → ④ PR 생성
   → ⑤ 리뷰 (수정 요청 오면 ②로 복귀) → ⑥ CI 통과 → ⑦ 병합 + 브랜치 삭제
```

main은 리뷰와 테스트를 통과한 코드만 받는 보호 구역이 된다.

PR을 형식 절차로 보면 안 되는 이유 — 결함 조기 발견, 지식 공유("그 부분은 A만 안다" 리스크 감소), 컨벤션 자연 전파.

리뷰 태도: 리뷰어는 **사람이 아니라 코드의 문제**를 지적하고, 작성자는 방어 대신 **의도를 설명**한다. PR은 리뷰 가능한 크기(수백 줄 이내)로 작게.

## 7. 막혔던 지점 / 메모

- **`gh auth status`가 미인증**이면 push 이전 단계가 전부 막힌다. `gh auth login` → GitHub.com → HTTPS → 브라우저 인증 순서로 먼저 해결해야 함.
- Windows에서는 `~/TIL`이 `C:\Users\MSI\TIL`로 매핑된다. 다만 **저장소 내부 경로는 `2026/08/2026-08-05.md` 형식 그대로** 유지해야 GitHub raw URL이 깨지지 않는다.
- `.gitignore`에 넣을 것: `venv/`, `__pycache__/`, `.env`, `*.log` 같은 **생성물·환경·비밀정보**.
  넣으면 안 되는 것: 소스 코드, `requirements.txt` 같은 **재현에 필요한 파일**.
- 토큰/비밀번호는 저장소 안에 평문으로 절대 쓰지 않는다. `.env`는 gitignore, 값은 별도 관리.
