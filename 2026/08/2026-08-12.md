# 12강. 커스텀 인터페이스 정의

## 1. 표준 메시지로 안 되는 순간

`Twist`, `LaserScan` 같은 표준을 쓰는 게 언제나 1순위다. 다른 팀·다른 로봇과 그대로 붙으니까. 그런데 "장애물 목록"처럼 **개수가 매번 달라지는 데이터**를 담을 표준은 없다. 이럴 때 직접 정의한다.

이번 강의는 노드를 만드는 게 아니라 **노드들이 주고받을 데이터 양식 자체**를 설계하는 내용이다.

## 2. 세 가지 파일 형식

통신 방식에 따라 파일이 갈리고, 구분선 `---` 개수로 구획을 나눈다.

| 파일 | 통신 | 구획 |
|---|---|---|
| `.msg` | Topic | 필드 목록 하나 |
| `.srv` | Service | `---` 1개 → 요청 / 응답 |
| `.action` | Action | `---` 2개 → 목표 / 결과 / 피드백 |

필드는 **타입 + 이름**이 전부다.

- 기본형: `bool`, `int32`, `float32`, `string`
- 배열: `float32[] ranges`(가변), `float32[4] quat`(고정)
- 중첩: `geometry_msgs/Point position` — 다른 메시지를 그대로 품는다

장애물 목록을 예로 들면 이렇게 두 단계로 쪼갠다.

```
# Obstacle.msg — 장애물 하나
geometry_msgs/Point position
float32 radius
float32 confidence
```

```
# ObstacleArray.msg — 목록
std_msgs/Header header
Obstacle[] obstacles
int32 count
```

**하나짜리를 먼저 정의하고 그걸 배열로 담는다.** 위치 x·y·z를 평평하게 늘어놓지 않는 이유는, 관련 있는 값은 함께 다녀야 나중에 쓰기 편하기 때문이다.

## 3. Header를 관례적으로 넣는 이유

`std_msgs/Header`에는 타임스탬프와 `frame_id`(좌표계 이름)가 들어 있다. 처음엔 그냥 붙이는 관례인 줄 알았는데, **이게 없으면 14강 TF2가 동작할 수 없다.**

- 타임스탬프 → "언제 측정한 값인가" → 시간 동기화
- `frame_id` → "어느 좌표계 기준인가" → 좌표 변환

즉 Header는 12강에서 심어두고 14강에서 꺼내 쓰는 장치다.

## 4. 설계 원칙 — 한번 배포하면 못 바꾼다

인터페이스는 여러 노드가 동시에 의존하므로 나중에 고치기가 어렵다.

- **의미 단위로 묶기** — 좌표는 `Point`로
- **표준 재사용** — 위치는 `geometry_msgs/Point`, 자세는 `Pose`
- **단위를 주석으로 명시** — `float32 distance  # meters`. m와 mm, rad와 deg를 헷갈리면 로봇에서는 사고가 된다
- **지우기보다 더하기** — 필드 삭제는 기존 노드를 깨뜨린다

## 5. rosidl — 정의 하나가 두 언어로

`.msg` 하나를 쓰면 `colcon build` 때 **rosidl**이 Python 클래스와 C++ 헤더를 **동시에** 만들어 낸다. rclpy 노드와 rclcpp 노드가 같은 타입으로 통신할 수 있는 게 이 덕분이다.

```python
from my_interfaces.msg import ObstacleArray
```

```cpp
#include "my_interfaces/msg/obstacle_array.hpp"
```

**이름 규칙이 바뀌는 데 주의.** `.msg`의 `ObstacleArray`(파스칼)가 C++ 헤더에서는 `obstacle_array.hpp`(스네이크)가 된다. 자동 변환이라 헤더 이름을 파스칼로 쓰면 못 찾는다.

## 6. 인터페이스는 별도 패키지로

실무에서는 `my_interfaces` 같은 전용 패키지로 뺀다. 인지·제어·로깅 노드가 전부 같은 `ObstacleArray`를 쓰는데, 인터페이스가 인지 패키지 안에 있으면 **제어 패키지가 인지 패키지 전체에 딸려 들어간다.**

```
my_interfaces/          ← 가볍고 안정적
├── msg/ObstacleArray.msg
├── CMakeLists.txt      ← rosidl_generate_interfaces(...)
└── package.xml

perception_pkg/ → my_interfaces 에만 의존
control_pkg/    → my_interfaces 에만 의존
```

`CMakeLists.txt`에는 중첩해 쓴 표준 메시지의 패키지를 `DEPENDENCIES`로 적어줘야 한다.

```bash
colcon build --packages-select my_interfaces
source install/setup.bash
ros2 interface show my_interfaces/msg/ObstacleArray
```

원칙으로 정리하면 — **많은 것이 의존하는 것일수록 가볍고 잘 안 바뀌어야 한다.**

# 13강. QoS 정책과 DDS

## 1. DDS — 중앙 관리자가 없다

ROS2의 통신은 **DDS**라는 산업 표준 미들웨어 위에서 돈다. 가장 중요한 성질은 **분산 디스커버리** — 노드들이 네트워크에서 서로를 알아서 찾아 직접 연결한다.

ROS1에는 `roscore`가 있어서 그게 죽으면 통신 전체가 마비됐다. 단일 장애점이었다. ROS2는 그 자리를 아예 없앴다. 한 노드가 죽어도 나머지는 그대로 돈다.

같은 네트워크에 있기만 하면 **다른 컴퓨터의 노드와도 코드 수정 없이** 붙는다. 이게 엣지와 클라우드를 나눠 쓸 수 있는 근거였다.

## 2. QoS 세 가지 — 데이터마다 요구가 정반대다

10강에서 발행자·구독자 마지막 인자에 넣던 `10`이 사실은 QoS의 큐 깊이 하나였다.

카메라 영상은 몇 프레임 빠져도 되지만 최신이어야 하고, 비상 정지는 한 번도 놓치면 안 된다. **하나의 통신 방식으로 둘 다 만족시킬 수 없어서** 데이터마다 성격을 지정한다.

| 정책 | 선택지 | 언제 |
|---|---|---|
| **Reliability** | Reliable — 유실 시 재전송 | 명령, 목표 지점 |
| | Best-Effort — 유실 허용, 최신 우선 | 카메라, LiDAR |
| **Durability** | Volatile — 접속 후 것만 | 대부분의 스트림 |
| | Transient Local — 늦게 온 구독자에게도 마지막 값 전달 | `/map`, `/robot_description` |
| **History** | Keep Last(N) — 최근 N개 | 보통 이것 |
| | Keep All — 자원 한도까지 | 드묾 |

Best-Effort가 "대충 보낸다"는 뜻이 아니다. **늦게 도착할 옛 프레임을 재전송하느니 버리는 게 센서에는 맞다**는 판단이다.

Transient Local은 지도처럼 **한 번 발행되고 잘 안 바뀌지만 나중에 뜬 노드도 반드시 알아야 하는** 데이터에 쓴다.

## 3. 프로파일 — 외울 건 두 개뿐

매번 조합하기 번거로우니 용도별 묶음이 준비돼 있다.

```python
from rclpy.qos import qos_profile_sensor_data

self.sub = self.create_subscription(
    LaserScan, '/scan', self.on_scan, qos_profile_sensor_data)
```

**센서 구독은 Sensor Data, 명령은 Default(Reliable).** 이 둘만 기억해도 대부분 맞는다.

## 4. ⚠️ 토픽도 타입도 같은데 연결이 안 될 때

초심자가 가장 많이 걸린다는 함정. 원인은 십중팔구 QoS 불일치다.

규칙은 하나다 — **구독자가 발행자보다 까다로우면 연결되지 않는다.**

| 발행자 | 구독자 | 결과 |
|---|---|---|
| Best-Effort | Reliable | ❌ 연결 안 됨 |
| Reliable | Best-Effort | ✅ 연결됨 |

구독자가 "반드시 재전송해달라"고 요구하는데 발행자에게 그럴 능력이 없으면 성립하지 않는다. 반대로 구독자가 덜 까다로운 건 문제없다.

**가장 흔한 실수**: 센서 노드를 Best-Effort로 발행해 놓고, 구독자는 기본값(Reliable)으로 만드는 것. 데이터는 흐르는데 내 노드만 못 받는다.

```bash
ros2 topic info /scan --verbose
```

발행자·구독자의 QoS를 나란히 보여준다. "토픽은 맞는데 안 온다"의 절반 이상이 이 한 줄로 풀린다고 한다.

# 14강. TF2 좌표 변환

## 1. 좌표계가 여러 개일 수밖에 없는 이유

LiDAR가 "전방 2.3m에 장애물"이라고 알려준다. 그런데 이 **전방은 LiDAR 기준**이다. 로봇 몸체 기준으로는? 지도 기준으로는?

- LiDAR는 자기 위치를 원점으로 거리를 잰다
- 카메라는 렌즈 중심 기준으로 픽셀을 본다
- 바퀴 제어는 몸체 중심 기준
- 경로 계획은 방 전체 기준

이걸 하나로 통일할 수 없다. 대신 **각자 좌표계를 두고 그 사이의 변환 관계를 관리**한다. 그 일을 하는 게 TF2다.

## 2. 표준 계층 — 트리로 관리한다

각 프레임은 부모를 하나 갖고, 부모에 대한 자기 위치·자세를 갖는다.

```
map          전역 고정 (SLAM 이 보정)
 └─ odom     주행 기준 (엔코더가 추정)
     └─ base_link      로봇 몸체
         ├─ lidar_link     ┐
         ├─ camera_link    ├ 고정 장착
         └─ imu_link       ┘
```

**왜 map과 odom을 굳이 나누나** — 이게 오늘 제일 흥미로웠다.

| | 성질 | 문제 |
|---|---|---|
| `odom` | 엔코더 기반, **부드럽다** | 미끄러짐 등으로 오차가 쌓인다 |
| `map` | SLAM 보정, **정확하다** | 보정 순간 위치가 툭 튄다(불연속) |

그래서 **제어는 부드러운 odom을, 경로 계획은 정확한 map을** 쓴다. 2강에서 나온 "빠른 것과 정확한 것을 분리한다"가 좌표계 설계에도 그대로 나타난 셈이다.

## 3. 정적 변환과 동적 변환

| 종류 | 예 | 발행 |
|---|---|---|
| **정적** | `base_link → lidar_link` | 한 번만 |
| **동적** | `odom → base_link` | 매 주기 |

로봇이 1m 앞으로 가면 `odom → base_link`는 갱신되지만 `base_link → lidar_link`는 그대로다. **센서가 몸에 나사로 박혀 함께 움직이니까.** 이 둘을 구분해야 매 주기 보낼 것과 한 번만 보낼 것이 갈린다.

정적 변환은 `StaticTransformBroadcaster`로 한 번 발행하면 `/tf_static`에 남아 **나중에 뜬 노드도 받는다.** 13강의 Transient Local과 같은 발상이다.

## 4. broadcast와 lookup

TF2는 두 동작으로 돌아간다.

**broadcast** — 아는 변환을 `/tf`(동적)·`/tf_static`(정적)에 발행한다. 채울 건 네 가지뿐이다.

```python
t = TransformStamped()
t.header.stamp = self.get_clock().now().to_msg()   # 언제
t.header.frame_id = 'odom'                          # 부모
t.child_frame_id = 'base_link'                      # 자식
t.transform.translation.x = msg.x                   # 병진
t.transform.rotation.z = math.sin(msg.theta / 2.0)  # 회전은 쿼터니언
t.transform.rotation.w = math.cos(msg.theta / 2.0)
self.br.sendTransform(t)
```

회전은 오일러 각이 아니라 **쿼터니언으로 넣어야 한다.** 2D 로봇처럼 z축 회전만 있으면 위처럼 `z`·`w` 두 성분으로 끝난다.

**lookup** — "A에서 B로 가는 변환이 뭐야?"를 물으면 TF2가 트리를 따라 중간 변환을 자동으로 곱해준다.

```python
transform = tf_buffer.lookup_transform(
    'map',           # 어디로
    'lidar_link',    # 어디서
    rclpy.time.Time())
```

`lidar_link → base_link → odom → map`을 손으로 연쇄할 필요가 없다. **프레임 이름 두 개만 대면 된다.** 프레임이 10개든 20개든 마찬가지다. 이게 TF2의 핵심 가치로 보인다.

## 5. 눈에 안 보이니 도구가 필요하다

```bash
ros2 run tf2_tools view_frames          # TF 트리를 PDF 로
ros2 run tf2_ros tf2_echo map base_link # 두 프레임 변환 실시간 출력
```

RViz2(16강)에서 3D로 띄우면 좌표계가 로봇과 함께 어떻게 움직이는지 직접 볼 수 있다고 한다.

# 세 강의를 관통하는 것

따로 배운 것 같은데 실은 한 줄로 이어져 있었다.

```
12강  Header 를 메시지에 심는다     (타임스탬프 + frame_id)
        ↓
13강  그 메시지를 QoS 골라 보낸다   (센서는 Best-Effort, 명령은 Reliable)
        ↓
14강  frame_id 로 좌표를 변환하고,
      타임스탬프로 "그때의 변환" 을 찾는다
```

**Header가 세 강의를 꿰는 실**이었다. 12강에서 "관례적으로 넣는다"고 배운 게 14강에서 왜 필수인지 드러난다. 카메라 영상이 0.1초 전 것이면 **지금이 아니라 촬영 시점의 변환**을 써야 정확한데, 그러려면 메시지에 시각이 박혀 있어야 한다.

강의 자료가 서로를 계속 참조하는 것도 이 때문인 듯하다 — 12강이 14강을, 14강이 13강을 가리킨다.

## 막혔던 지점 / 메모

- **`.srv`와 `.action`의 구분선 개수가 헷갈린다.** `---` 1개면 서비스(요청/응답), 2개면 액션(목표/결과/피드백). 구획이 몇 개 필요한지로 세면 안 헷갈릴 듯하다.

- **C++ 헤더 이름이 파스칼이 아니라 스네이크다.** `ObstacleArray` → `obstacle_array.hpp`. rosidl 자동 변환 규칙이라 그대로 쓰면 못 찾는다.

- **QoS 호환 방향을 반대로 외우기 쉽다.** "구독자가 더 까다로우면 실패"로 기억한다. 구독자가 재전송을 요구하는데 발행자가 못 하면 성립이 안 되는 것.

- **회전을 오일러 각으로 넣으면 안 된다.** TF2는 쿼터니언을 받는다. 2D면 `z = sin(θ/2)`, `w = cos(θ/2)` 두 개만 채우면 된다. 왜 쿼터니언인지는 20강에서 다룬다는데, 짐벌락 때문일 것 같다(18강).

- **인터페이스를 별도 패키지로 빼는 이유가 처음엔 과해 보였다.** 그런데 제어 패키지가 인지 패키지 전체에 의존하게 된다는 설명을 보고 납득했다. 의존성은 한 방향으로, 그리고 가벼운 쪽을 향해야 한다.

- 표준 메시지가 있으면 **무조건 표준 먼저**. 커스텀은 정말 담을 표준이 없을 때만. 호환성을 잃는 대가가 크다.
