# 2026-08-14 TIL — ROS 디버깅 도구 총정리

> ROS 기초의 마지막 강. 새 개념보다 이미 써본 도구들을 하나씩 제대로 뜯어본 날이다. RViz2 설정, rosbag2로 데이터 기록/재생, 로그 레벨 설계에 초점을 뒀다.

## 1. ROS 디버깅 도구 여섯 가지

개발하다 보면 결국 "지금 이 노드가 뭘 하고 있는지"를 들여다봐야 한다. ROS는 이걸 보는 도구를 여러 갈래로 나눠서 제공한다. 크게 **시각화용**과 **기록용**으로 갈린다.

| 도구 | 성격 | 쓰는 상황 |
|---|---|---|
| ROS CLI | 시각화(터미널) | `topic echo`, `topic list`, `node list`로 빠르게 확인 |
| RViz2 | 시각화(3D) | 로봇 형상·센서 데이터를 눈으로 |
| RQT graph | 시각화(구조) | 노드끼리 어떤 방향으로 통신 중인지 |
| rosbag2 | 기록 | 토픽 데이터를 주기마다 저장 |
| pytest / gtest | 검증 | 단위 테스트 |

CLI는 이미 손에 익었다. `topic hz`로 주기를 보고, `topic info`로 타입을 확인하고, 일회성으로 토픽을 직접 쏴보기도 했다. RQT graph는 노드가 없으면 아무것도 안 뜨는데, 예제를 켜두면 통신 방향이 화살표로 그려진다.

기록용 두 개(rosbag2)는 시각화 도구와 결이 다르다. **화면에 그리는 게 아니라 나중에 다시 볼 수 있게 남기는 것**이다.

## 2. RViz2 뜯어보기

RViz2는 Qt라는 GUI 프레임워크로 만들어졌다. 그래서 URDF 튜토리얼에서 봤던 조인트 슬라이더, Nav2나 MoveIt의 이상한 버튼들이 전부 Qt로 만든 커스텀 위젯이었다. 필요하면 직접 버튼을 만들 수도 있는데, 그건 나중 얘기다.

### 카메라 뷰

오른쪽에서 뷰 방식을 고른다. 종류는 많지만 실무에서는 **Orbit(3D 궤도)** 와 **Top-down(위에서)** 두 개면 충분하다고 한다. Target Frame을 로봇으로 지정하면 카메라가 로봇을 자동으로 따라간다.

### Fixed Frame — 오늘 가장 헷갈렸던 부분

처음엔 "맵이 원점"이라고 고정된 값인 줄 알았는데, 아니었다. **Fixed Frame은 내가 시점을 어디에 고정할지 정하는 값**이고, 기본값이 `map`일 뿐이다. 맵이 없는 상황에서는 `map`을 그대로 두면 아무것도 안 뜬다. 이럴 땐 `base_footprint`나 `odom` 같은, 실제로 살아있는 프레임으로 바꿔줘야 한다.

- map이 있으면: `map` → `odom` → 로봇 순으로 위계가 잡힌다
- odom은 **추정치**라서 실제 하드웨어 위치와 선으로 이어져 계속 움직인다

### Displays 추가와 Topic 지정

보고 싶은 데이터는 `Add`로 하나씩 붙인다. 로봇 모델, TF, LaserScan, Odometry, Path 등을 각각 추가하고 토픽을 지정해줘야 한다.

- 토픽 칸(항목 아래 빈 공간)을 클릭하면 **현재 살아있는 토픽 목록**이 드롭다운으로 뜬다
- 타입이 안 맞으면 안 보인다. 예를 들어 Odometry를 보려는데 Scan 토픽을 지정하면 절대 안 그려진다
- Queue depth(필터 사이즈)를 크게 주면 데이터가 쌓여 보인다. Pose는 보통 일회성이라 depth를 1만 개쯤 주면 화살표가 계속 남아서 **경로처럼** 보인다 — 디버깅에 유용

### 설정을 파일로 저장

토픽을 매번 손으로 추가하는 건 번거롭다. TurtleBot만 해도 TF, 스캔, 맵을 다 띄워야 한다. 그래서 RViz 설정을 `.rviz` 파일로 미리 저장해두면 켜자마자 한 번에 뜬다. 왼쪽 위에서 config로 저장할 수 있고, 예제 저장소의 `rviz/` 폴더를 보면 이 설정이 다 들어 있다.

## 3. rosbag2로 데이터 기록·재생

rosbag2는 토픽으로 흐르는 데이터를 파일로 저장한다. 코드에 남기는 로그와 달리 **센서 데이터 그 자체**(예: 라이다 스캔값)를 주기마다 통째로 저장한다.

### 기록

```bash
ros2 bag record /scan       # 특정 토픽만
ros2 bag record -a -o <이름>  # 전체 토픽, 출력 폴더 이름 지정
```

`-o`를 안 주면 현재 위치에 저장된다. `Ctrl+C`를 누르면 그 시점까지만 저장하고 종료된다. 저장이 끝나면 폴더가 생기는데, 안에는 실제 데이터가 담긴 `.db3` 데이터베이스 파일과 `metadata.yaml`이 들어 있다.

```bash
cat metadata.yaml   # 개요만 — 실제 데이터가 아니라 언제부터 무슨 값이 들어왔는지
```

메타데이터는 말 그대로 개요다. 실제 데이터를 보려면 재생해야 한다.

### 재생과 확인

```bash
ros2 bag play <폴더명>   # 저장한 데이터 재생
ros2 bag info <폴더명>   # 토픽별 메시지 개수 확인
```

`info`를 보면 각 토픽이 몇 번 기록됐는지 나온다. 예를 들어 스캔은 86번, IMU는 3400번처럼. 60Hz로 보내는 데이터라면 그만큼 줄 수가 쌓인다.

**재생 동작이 바뀐 점**: 예전에는 play를 하면 터미널에서 바로 데이터가 보였는데, 지금은 재생 시 **토픽으로 다시 퍼블리시**된다. 그래서 로봇을 안 켰는데도 `ros2 topic list`에 토픽이 뜨고, `ros2 topic echo /scan`으로 값을 확인하거나 RViz2에 띄워서 볼 수 있다. 재생된 데이터를 보려면 echo를 따로 띄우거나 RViz에서 봐야 한다.

일시정지 상태에서 스페이스바로 메시지를 하나씩 넘겨볼 수 있고, loop 옵션을 주면 무한 반복 재생된다. 실무에서는 이 `.db3` 파일 자체를 넘겨서 분석하거나, 로봇이 이상 동작으로 멈췄을 때 **어디서부터 뻗었는지** 로그로 되짚는 데 쓴다.

## 4. 로그 레벨 설계

`print` 대신 ROS가 제공하는 로거를 쓴다. 파이썬이면 `get_logger().info(...)` 식으로 터미널에 로그를 남긴다. 로그를 많이 남긴다고 성능이 크게 떨어지지 않으므로, **최대한 세세하게 남기는 걸 습관화**하라는 게 핵심이었다.

중요한 건 아무거나 다 같은 등급으로 찍지 않는 것이다. 목적에 따라 레벨을 나눈다. 로봇이든 다른 분야든 마찬가지다.

| 레벨 | 언제 |
|---|---|
| DEBUG | 개발 중 확인용 (인지 거리, 이미지 등) |
| INFO | 정상 상태 — 노드 실행됨, 센서 감지됨, 모드 전환됨 |
| WARN | 소프트웨어로 아직 수습 가능한 상태 (배터리 20% 이하, 응답 지연) |
| ERROR | 기능이 실패한 상태 (센서 데이터 멈춤, 통신 끊김) |
| FATAL | 하드웨어가 스스로 복구 못 하는 치명 상태 (전복, 배터리 5% 이하, USB 단선) |

미니 과제로 "내 로봇의 로그를 레벨별로 나눠보기"를 했다. 정리하면서 잡은 감:

- **상태(state)는 대부분 INFO**로 간다. "배터리 상태"처럼 뭉뚱그리지 말고, "배터리가 특정 값 이하일 때만 WARN"처럼 **조건을 구체화**해야 한다.
- 같은 "모터 제어 불가"도 일시적 통신 끊김(ERROR)과 물리적 선 단선(FATAL)을 나누는 게 좋다.
- **하드웨어가 스스로 해결할 수단이 있느냐**가 WARN/ERROR/FATAL을 가르는 기준이다. 예를 들어 렌즈가 이물질로 가려졌을 때, 와이퍼나 후진 같은 복구 동작이 있으면 WARN, 그런 수단이 없으면 바로 정지(ERROR 이상)로 간다. 뒤집혀도 복구 구조가 없는 로봇이면 곧장 정지해야 한다.

드론·로봇에는 흔히 **페일세이프**가 있다. 배터리가 정해둔 값 이하로 떨어지면 무조건 정지하거나 충전 스테이션으로 복귀시키고, GPS 초기 위치가 안 잡히면 시동 자체를 막는 식이다. 이런 건 FATAL 레벨에 대응된다.

## 5. 단위 테스트

로그로 문제를 잡는 것과 별개로, 코드 단위로 미리 검증하는 방법도 있다.

- **파이썬**: `pytest`로 단위 테스트. ROS 없이 수식 검증 같은 것도 가능하다.
- **C++**: `gtest`. 예를 들어 모터 드라이버 계산 로직을 C++로 짰다면, 로봇을 실제로 굴려보기 전에 gtest로 먼저 검증할 수 있다.

문법은 실제 로봇이 도착했을 때 같이 해볼 예정이라, 오늘은 "이런 기능이 있다" 정도만 짚었다.

## 7. 막혔던 지점 / 메모

- **Gazebo를 안 띄우고 RViz만 켜면 아무것도 안 뜬다.** Gazebo를 먼저 실행해야 로봇이 스폰되고, 그래야 토픽이 살아난다. 둘 다 띄워야 한다.
- 워크스페이스 경로가 꼬여서 빌드가 안 될 땐 `install`/`build`/`log` 폴더를 지우고 **클린 빌드** 후 `source` → `setup.bash` 순으로 다시 잡아야 했다.
- RViz에서 데이터가 다 0으로 나온 건 빈(empty) 월드로 띄웠기 때문이다. 반환 데이터가 없으면 그렇게 나온다 — 버그가 아니다.
- rosbag2 재생 동작이 **터미널 직접 출력 → 토픽 퍼블리시**로 바뀐 것을 몰라서 한참 헤맸다. play 후에는 echo나 RViz로 봐야 한다.
- Gazebo가 그래픽/`libgazebo_ros_factory.so` 문제로 로봇을 못 띄우는 경우가 있다. 이럴 땐 Gazebo 초기화가 답이었다. 스폰 실패 로그를 읽어보니 SDF 파일을 못 불러온 게 원인이었다 — **로그를 끝까지 읽는 습관**이 디버깅의 시작이다.
