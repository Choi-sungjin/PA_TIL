## 1. Lifecycle Node — 켜자마자 도는 게 문제인 경우

일반 노드는 실행되는 즉시 일을 시작한다. 그런데 로봇에서는 **"준비는 됐지만 아직 움직이지는 마"** 라는 상태가 필요하다. 센서 드라이버가 하드웨어에 연결만 해두고, 모든 노드가 준비된 걸 확인한 뒤에 일제히 시작하고 싶은 것이다.

```
Unconfigured  ──configure()──▶  Inactive  ──activate()──▶  Active
                                    ▲                         │
                                    └──── deactivate() ───────┘
```

핵심은 가운데 **Inactive**다. 센서 연결·메모리 같은 자원은 이미 잡았지만 데이터를 발행하거나 처리하지는 않는 대기 상태.

이게 푸는 문제 세 가지:

- **시작 순서** — 전부 `configure`해 두고, 준비가 확인되면 순서대로 `activate`. "센서가 아직인데 제어가 먼저 도는" 사고를 막는다
- **죽이지 않고 멈추기** — 문제가 생긴 노드를 `deactivate`로 세웠다가 다시 `activate`. 프로세스는 살아 있다
- **자원 관리** — `on_configure`, `on_activate` 같은 전이 콜백마다 할 일이 명확히 나뉜다

Nav2(자율주행 스택)가 이 구조로 짜여 있어서 주행 스택 전체를 한꺼번에 기동·정지할 수 있다고 한다.

## 2. Composition — 프로세스를 합쳐서 복사를 없앤다

9강까지는 노드 하나가 프로세스 하나였다. 프로세스가 나뉘어 있으면 하나가 죽어도 나머지가 살아남지만, **통신할 때마다 데이터를 복사하고 직렬화한다.** 카메라 영상처럼 초당 수백 MB가 오가면 이 비용이 크다.

Composition은 노드 여러 개를 **한 프로세스에 같이 올리는** 방식이다. 그러면 같은 메모리 공간이라 복사 없이 포인터만 넘기면 된다(8강의 `shared_ptr`가 여기서 쓰인다).

| | 프로세스 분리 (기본) | Composition |
|---|---|---|
| 하나가 죽으면 | 나머지는 산다 | 같이 죽는다 |
| 통신 비용 | 복사·직렬화 | 메모리 공유 (제로 카피) |
| 쓸 곳 | 대부분의 노드 | 큰 데이터를 주고받는 묶음 |

**둘 중 하나가 옳은 게 아니라 맞바꾸는 것이다.** 카메라→인지처럼 데이터가 크고 성능이 중요하면 합치고, 안전 관련처럼 독립성이 중요하면 따로 둔다.

## 3. colcon — 순서대로 빌드하고, 소싱해야 보인다

패키지 여러 개를 모아둔 게 워크스페이스고, 그걸 빌드하는 도구가 `colcon`이다. 7강의 CMake와 5강의 `setup.py`를 **의존성 순서대로 불러주는** 상위 도구다.

```
ros2_ws/
├── src/       ← 내 패키지 소스
├── build/     ← 중간 산출물
├── install/   ← 설치 결과 ★
└── log/
```

```bash
cd ~/ros2_ws
colcon build                                # 전체 (순서 자동)
colcon build --packages-select control_pkg  # 하나만
source install/setup.bash                   # 이걸 해야 ros2 run 이 찾는다
```

`my_interfaces`(12강)를 먼저 빌드해야 그걸 쓰는 `perception_pkg`를 빌드할 수 있는데, 이 순서를 `package.xml`의 의존성 선언을 읽고 알아서 정한다.

### ⚠️ "빌드는 됐는데 노드를 못 찾겠다"

거의 항상 **`source install/setup.bash` 누락**이다. 빌드 결과는 `install/`에 놓이는데, 소싱을 해야 그 경로가 환경변수에 등록된다.

ROS2를 apt로 깔아도 터미널은 아직 ROS2를 모른다. 소싱이 채워주는 건 세 가지다.

| 변수 | 역할 |
|---|---|
| `AMENT_PREFIX_PATH` | 패키지를 어디서 찾을지 |
| `PYTHONPATH` | 노드 모듈 import 경로 |
| `LD_LIBRARY_PATH` | 공유 라이브러리 경로 |

```bash
source /opt/ros/humble/setup.bash   # ~/.bashrc 에 넣어두면 매번 안 쳐도 된다
export ROS_DOMAIN_ID=42             # 같은 망의 남의 노드와 안 섞이게 (13강)
```

내 워크스페이스를 소싱하면 설치본 위에 겹쳐 올라가고, 같은 이름이면 **나중에 소싱한 쪽이 이긴다.** `ros2 pkg prefix <패키지>`로 어느 쪽이 잡혔는지 확인할 수 있다.

### 빌드가 꼬였을 때 순서대로 볼 것

| 증상 | 원인 | 대처 |
|---|---|---|
| `Package 'x' not found` | 소싱 안 함 / 빌드 실패 | 소싱 확인 → 빌드 로그 **첫 에러**부터 |
| 빌드는 성공, `ros2 run`이 실행 파일 못 찾음 | `entry_points`·`install(TARGETS)` 누락 | `ros2 pkg executables <패키지>` |
| 코드를 고쳤는데 예전 동작 | `--symlink-install` 없이 빌드 | 옵션 붙여 재빌드 |
| 원인 불명 실패가 계속 | 빌드 캐시 오염 | `rm -rf build install log` 후 재빌드 (최후 수단) |

빌드 에러는 **첫 번째 것부터** 봐야 한다. 뒤엣것들은 앞의 실패에서 파생된 경우가 많다.

## 4. launch — 로봇 켜는 법을 파일로 남긴다

노드가 수십 개인데 터미널을 수십 개 열 수는 없다. `launch`는 여러 노드와 파라미터를 **한 파일로 선언해 한 번에 띄운다.** ROS2는 주로 Python으로 쓴다 — 조건이나 반복 같은 로직을 넣을 수 있어서.

```python
# robot.launch.py
def generate_launch_description():
    return LaunchDescription([
        Node(package='camera_pkg', executable='camera_node'),
        Node(package='perception_pkg', executable='perception_node',
             parameters=[{'min_confidence': 0.7}]),
        Node(package='control_pkg', executable='control_node',
             parameters=['config/control.yaml']),
    ])
```

```bash
ros2 launch robot_bringup robot.launch.py
```

얻는 것:

- **재현 가능** — "이 로봇 켜는 법"이 파일로 문서화된다. 누가 켜도 같은 시스템이 뜬다
- **파라미터 분리** — 실내용/실외용 YAML만 갈아끼우면 된다. 코드는 그대로
- **조합** — launch 파일이 다른 launch를 포함할 수 있어 "센서 묶음", "제어 묶음"으로 쌓는다

### 네임스페이스 — 코드는 한 벌, 이름만 가른다

로봇이 두 대거나 같은 센서가 둘이면 토픽 이름이 부딪힌다. `namespace`를 주면 그 노드의 토픽 앞에 접두사가 붙는다.

```python
Node(package='sensor_pkg', executable='state_node', namespace='robot1'),
Node(package='sensor_pkg', executable='state_node', namespace='robot2'),
```

```
/robot1/state
/robot2/state    ← 같은 코드인데 갈렸다
```

다만 `/global_topic`처럼 **앞에 `/`를 붙여 절대 이름으로 선언한 토픽에는 네임스페이스가 안 붙는다.** "이 토픽이 로봇마다 따로인지, 시스템 전체에 하나인지"를 정해서 상대/절대 이름을 고르는 게 설계 포인트다.

### 파라미터는 YAML로 빼둔다

코드나 launch에 값을 박아두면 바꿀 때마다 파일을 고쳐야 한다. YAML로 빼면 **재빌드 없이** 값만 바꿔 돌린다.

```yaml
# config/params.yaml
/**:                      # 모든 노드에 적용 (노드 이름을 적으면 그 노드만)
  ros__parameters:
    publish_rate: 10.0
    warn_distance: 3.0
```

```bash
ros2 param get /state_node publish_rate   # 주입된 값 확인
```

## 5. C++ 패키지 CMakeLists — 네 줄이 다 있어야 한다

찾고 → 만들고 → 연결하고 → 설치한다.

```cmake
find_package(rclcpp REQUIRED)                          # 1) 의존 패키지 찾기
add_executable(state_node src/state_node.cpp)          # 2) 실행 파일 정의
ament_target_dependencies(state_node rclcpp std_msgs)  # 3) 헤더·라이브러리 연결
install(TARGETS state_node DESTINATION lib/${PROJECT_NAME})  # 4) install/ 로 설치
```

`ament_target_dependencies`가 7강의 `include_directories` + `target_link_libraries`를 한 번에 해준다.

**4번을 빼먹으면 빌드는 성공하는데 `ros2 run`이 실행 파일을 못 찾는다.** Python 패키지에서 `setup.py`의 `entry_points`를 빠뜨리는 것과 정확히 같은 실수다. 빌드 성공이 실행 가능을 뜻하지 않는다.

## 6. 12강부터 여기까지가 한 사이클이었다

```
.msg 정의 (12강)
   ↓
colcon build          인터페이스 → 노드 순으로
   ↓
source install/setup.bash
   ↓
ros2 launch           여러 노드 일괄 기동
```

앞선 강의들이 조각이었고 15강이 그걸 굴리는 방법이다. 12강에서 인터페이스를 별도 패키지로 빼라고 한 이유가 여기서 다시 나온다 — **colcon이 의존성 순서로 빌드하려면 그 경계가 명확해야** 하기 때문이다.

## 8. 막혔던 지점 / 메모

- **`source install/setup.bash`를 안 하면 아무것도 안 된다.** 빌드 성공 ≠ 실행 가능. 터미널을 새로 열 때마다 다시 해야 한다는 것도 잊기 쉽다. `~/.bashrc`에 넣어두는 게 맞다.

- **`install(TARGETS ...)` 누락이 특히 고약하다.** 빌드가 성공하니 문제없어 보이는데 `ros2 run`만 실패한다. 에러 메시지가 원인을 안 가리켜서 헤맬 것 같다. `ros2 pkg executables <패키지>`로 등록 이름을 먼저 확인하는 습관을 들이자.

- **Composition은 좋기만 한 게 아니다.** 제로 카피가 매력적이지만 **한 노드가 죽으면 같이 죽는다.** 안전 관련 노드를 성능 때문에 합치면 안 된다.

- **네임스페이스에서 절대 이름(`/`로 시작)은 안 붙는다.** 로봇 두 대를 띄웠는데 한 토픽만 계속 충돌한다면 이걸 의심해야 할 듯.

- `colcon build` 후 뭔가 이상하면 **로그의 첫 번째 에러부터** 본다. 뒤에 쏟아지는 건 대개 앞의 실패에서 파생된 것이다.

- 빌드 캐시를 지우는 `rm -rf build install log`는 최후 수단이다. 전체 재빌드라 오래 걸린다.
