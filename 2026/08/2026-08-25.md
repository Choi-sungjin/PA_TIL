## 1. WSL2를 고른 이유 — Windows에도 sshd는 올라간다

과제가 `sudo apt install openssh-server` 로 시작하길래 이걸 Windows에서 그대로 할 수 있는지부터 확인했다. 결론은 "된다, 다만 다른 경로로 된다"였다.

- Windows 자체에 SSH 서버를 올리려면 `apt` 가 아니라 선택적 기능이다. `Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0` 뒤에 `Start-Service sshd`.
- 하지만 과제가 원한 건 "온보드 컴퓨터를 대신할 리눅스"다. 그래서 WSL2에 Ubuntu 22.04를 따로 깔고 그 안에 sshd를 올렸다.

선택 기준을 정리하면 이렇다.

| 목적 | 맞는 선택 |
|---|---|
| 리눅스 명령·개발 환경이 필요하다 | WSL2 |
| 다른 PC가 내 Windows에 SSH로 붙어야 한다 | Windows OpenSSH Server |
| 외부 PC가 WSL 안 Ubuntu에 직접 붙어야 한다 | WSL2 + 포트 포워딩·방화벽 추가 작업 |

ROS 2 Jazzy가 들어 있는 24.04는 건드리지 않고 과제용 22.04를 새로 깔아 환경을 분리했다. 이게 뒤에서 한 번 발목을 잡는다(9번).

## 2. sshd를 올리고 "진짜 원격 세션"임을 증명하기

서버가 살아 있는지는 두 층에서 확인해야 한다. 서비스가 떠 있는 것과 포트를 실제로 듣고 있는 것은 다른 이야기다.

```bash
sudo systemctl status ssh
sudo ss -tlnp | grep ':22'
```

접속한 세션이 로컬 터미널이 아니라 원격 세션이라는 증거도 남겨야 했다.

```bash
who                    # pts/N 으로 잡히면 유사 터미널 = 원격
echo $SSH_CONNECTION   # 출발지 IP·포트 / 도착지 IP·포트
```

로컬 콘솔이면 `tty1` 처럼 잡히고 `$SSH_CONNECTION` 은 비어 있다. 두 값이 모두 채워져야 원격 접속이 맞다.

## 3. 키 쌍 — 서버에 올라가는 쪽은 공개키다

```bash
ssh-keygen -t ed25519 -C "chsjh@PA12"
ssh-copy-id chsjh@localhost
ssh -o BatchMode=yes -o PasswordAuthentication=no chsjh@localhost 'echo PUBLIC_KEY_LOGIN_OK'
```

`ssh-copy-id` 가 하는 일은 내 `~/.ssh/id_ed25519.pub`(공개키)를 상대 서버의 `~/.ssh/authorized_keys` 에 덧붙이는 것뿐이다. **개인키 `id_ed25519` 는 내 손을 떠나지 않는다.**

그렇게 나눠도 안전한 이유: 서버는 공개키로 "이 개인키를 가진 사람만 풀 수 있는 문제"를 내고, 클라이언트가 개인키로 서명해서 답한다. 공개키가 통째로 유출돼도 그것만으로는 서명을 만들 수 없다. 그래서 공개키는 공개해도 되고 개인키만 지키면 된다.

검증할 때 `BatchMode=yes -o PasswordAuthentication=no` 를 붙인 게 좋았다. 비밀번호 입력 경로를 아예 막아버리니, 통과하면 진짜 키로 붙은 것이 확실해진다.

## 4. 남의 PC에 붙어보다 실패한 데서 배운 것

같은 실습망의 다른 PC(`10.2.16.x`)에 접속해 `name.txt` 에 이름을 남기는 미션이 있었는데 계속 튕겼다.

```text
pa@10.2.16.x: Permission denied (publickey,password).
```

여기서 착각한 게 두 가지다.

- **네트워크 도달과 인증은 다른 층위다.** 호스트 지문을 물어보고 `known_hosts` 에 추가됐다는 건 이미 22번 포트까지 닿았다는 뜻이다. 방화벽이나 IP 문제가 아니라 로그인 단계에서 떨어진 것이다.
- **인증 정보는 상대 계정의 것이다.** 내 `chsjh` 비밀번호를 넣고 있었다. 애초에 상대 PC에 그 계정이 있는지부터가 문제였고, 상대에게 `whoami` 와 `hostname -I` 를 물어봤어야 했다.

그리고 `sudo systemctl status ssh` 로 확인한 건 상대가 아니라 **내 쪽** 서버 상태였다. 남의 서버 상태를 내 터미널에서 볼 수는 없다. 내 IP는 `hostname -I` 로 `10.2.16.200` 이었는데, WSL이 mirrored 네트워킹이라 Windows와 같은 대역을 쓴다.

## 5. 파일 만들다 낸 실수 — mkdir과 touch, `>` 와 `>>`

```bash
mkdir sungjin.txt   # 이름만 .txt 인 '디렉터리'가 생긴다
```

`.txt` 를 붙여도 `mkdir` 은 디렉터리를 만든다. 리눅스에서 확장자는 그냥 이름의 일부일 뿐이고, 무엇인지는 `ls -la` 맨 앞 글자로 판단해야 한다(`d` 면 디렉터리, `-` 면 일반 파일). 빈 파일이 필요하면 `touch`, 내용까지 넣으려면 리다이렉션이다.

```bash
printf '%s\n' 'sungjin' > ~/ssh_practice/send/name.txt
scp ~/ssh_practice/send/name.txt chsjh@localhost:~/ssh_practice/received/
```

여러 사람이 함께 쓰는 파일에 이름을 남길 때는 `>` 가 아니라 `>>` 여야 한다. `>` 는 기존 내용을 통째로 날린다. 앞사람 이름을 지우고 내 이름만 남기는 사고가 여기서 난다.

## 6. 가상 센서 두 개 만들기 — losetup

실물 라이다·IMU가 없으니 파일을 블록 장치처럼 붙여서 대신했다.

```bash
mkdir -p ~/fake_sensors && cd ~/fake_sensors
truncate -s 10M lidar.img imu.img
sudo losetup -f --show lidar.img   # /dev/loop0
sudo losetup -f --show imu.img     # /dev/loop1
losetup -a
```

`-f` 는 비어 있는 loop 번호를 알아서 고르고 `--show` 는 그 번호를 출력한다. 즉 **번호는 내가 정하는 게 아니라 붙이는 순서가 정한다.** 이게 바로 다음 절에서 udev가 필요해지는 이유다.

장치 속성은 이렇게 확인했다.

```bash
sudo udevadm info --attribute-walk /dev/loop0
cat /sys/class/block/loop0/loop/backing_file
```

WSL의 `udevadm` 은 `--attribute-walk` 목록에서 `backing_file` 을 빼먹어서, 결국 `/sys` 아래를 직접 읽어야 값이 나왔다. 출력이 길어 화면 아래에 `(END)` 가 뜨면 `q` 로 빠져나온다.

## 7. udev 규칙으로 장치 이름 고정하기

문제는 단순하다. 오늘은 라이다가 `loop0` 인데 내일 붙이는 순서가 바뀌면 `loop1` 이 된다. 코드에 번호를 박아두면 그날부터 엉뚱한 장치로 명령이 나간다. 그래서 "이런 특징을 가진 장치가 붙으면 이 이름의 링크를 만들어라"를 규칙 파일로 적는다.

`/etc/udev/rules.d/99-robot-sensor.rules`:

```udev
# Virtual LiDAR
SUBSYSTEM=="block", KERNEL=="loop*", ATTR{loop/backing_file}=="/home/chsjh/fake_sensors/lidar.img", SYMLINK+="robot_lidar", MODE="0660", GROUP="disk"

# Virtual IMU
SUBSYSTEM=="block", KERNEL=="loop*", ATTR{loop/backing_file}=="/home/chsjh/fake_sensors/imu.img", SYMLINK+="robot_imu", MODE="0660", GROUP="disk"
```

실물 USB 센서용으로 배운 규칙을 그대로 가져다 쓰면 링크가 하나도 안 생긴다. loop 장치에는 `idVendor` 같은 USB 속성 자체가 없기 때문이다. 대응 관계를 표로 놓으니 정리가 됐다.

| 실제 USB 규칙 | 가상 loop 규칙 |
|---|---|
| `SUBSYSTEM=="tty"` | `SUBSYSTEM=="block"` |
| `KERNEL=="ttyUSB*"` | `KERNEL=="loop*"` |
| `ATTRS{idVendor}` / `ATTRS{idProduct}` | 쓰지 않음 |
| `ATTRS{serial}` (장치 고유값) | `ATTR{loop/backing_file}` (이미지 경로) |
| `GROUP="dialout"` | `GROUP="disk"` |

**가상 센서에서는 이미지 파일 경로가 시리얼 번호 역할을 한다**는 게 핵심이었다. 그리고 `ATTR{}` 는 그 장치 자신의 속성만 보고 `ATTRS{}` 는 부모 장치까지 거슬러 올라가며 찾는다. loop는 자기 속성이라 `ATTR{}` 을 쓴다.

적용과 확인:

```bash
sudo udevadm control --reload-rules
sudo udevadm trigger --action=change --subsystem-match=block
sudo udevadm settle
ls -l /dev/robot_lidar /dev/robot_imu
```

검증은 **일부러 번호를 뒤집어서** 했다. 둘 다 떼고 라이다부터 다시 붙이면 `loop0` 과 `loop1` 이 서로 바뀐다.

```bash
sudo losetup -d /dev/loop0
sudo losetup -d /dev/loop1
sudo losetup -f --show lidar.img   # 이번엔 loop0 이 라이다
sudo losetup -f --show imu.img
sudo udevadm settle
```

번호가 바뀌었는데도 `/dev/robot_lidar` 가 여전히 `lidar.img` 를 가리키면 규칙이 제대로 도는 것이다. 이 상태가 통과 기준이었다.

## 8. C++ 빌드 체계 — 한 줄 명령에서 CMake까지

과제 2의 앞단. 제동 거리 계산부터 시작했다. 평지에서 타이어와 노면의 마찰만으로 감속한다고 보면

```math
d = \frac{v^2}{2\mu g}
```

$v = 10\,\mathrm{m/s}$, $\mu = 0.8$, $g = 9.81$ 이면 $6.371\,\mathrm{m}$ 가 나온다. 입력은 속도 0 이상, 마찰계수 0 초과만 받도록 막았다. 환경은 g++ 11.4.0 / CMake 3.22.1 / Make 4.3, 표준은 C++17.

빌드를 네 단계로 쪼개서 봤다.

```bash
g++ -Wall -std=c++17 stop_distance.cpp -o stop_distance   # 1) 한 줄에 다 하기
g++ -Wall -std=c++17 -c motor.cpp -o motor.o              # 2) 컴파일만
g++ -Wall -std=c++17 -c main.cpp -o main.o
g++ -Wall -std=c++17 main.o motor.o -o motor_app          #    링크
g++ -Wall -std=c++17 main.o -o motor_app                  # 3) 일부러 실패시키기
```

3번에서 나온 게 `undefined reference to Motor::set_rpm(double)` 이다. 여기서 컴파일 에러와 링크 에러가 갈린다.

- `main.cpp` 는 `motor.hpp` 의 **선언**만 보면 되므로 컴파일은 성공한다.
- 링크 단계에서 실제 **정의**가 들어 있는 `motor.o` 가 빠지면 심볼을 해결하지 못한다.

"선언만 있으면 컴파일은 통과한다"가 핵심이다. 헤더만 고쳐놓고 구현을 안 붙였을 때 나는 에러가 정확히 이것이다.

CMake는 별도 `build/` 를 만들어 out-of-source로 구성했다.

```bash
mkdir -p build && cd build
cmake .. && make VERBOSE=1
```

가장 인상 깊었던 건 증분 빌드다. `motor.cpp` 의 출력 문구만 고치고 다시 `make` 를 돌렸더니

```text
make[2]: Nothing to be done for 'CMakeFiles/stop_distance.dir/build'.
[ 60%] Building CXX object CMakeFiles/motor_app.dir/motor.cpp.o
[ 80%] Linking CXX executable motor_app
```

`main.cpp.o` 는 다시 컴파일되지 않았고, 바뀐 `.o` 를 쓰는 `motor_app` 만 다시 링크됐다. `stop_distance` 는 의존 파일이 안 바뀌어서 손도 대지 않았다. Make가 **의존 그래프와 파일 수정 시각**으로 다시 만들 대상을 고른다는 말이 화면으로 확인됐다.

## 9. WSL2에서 ROS 2 GUI 띄우기

RViz2를 Windows 바탕화면에 띄우는 것까지 확인했다. 찾아본 설치 글에는 X 서버를 따로 깔고 `DISPLAY` 를 손으로 잡는 단계가 있었는데, 지금 WSL2에서는 필요 없었다.

- 요즘 WSL2에는 **WSLg가 내장**돼 X11/Wayland GUI와 GPU 가속을 기본 지원한다(이 PC: WSL 2.7.11 / WSLg 1.0.73.2, `DISPLAY=:0`).
- 글을 그대로 따라 `wsl --install` 이나 스토어 재설치를 다시 밟으면 멀쩡한 배포판만 건드릴 위험이 있다.
- 실제로 RViz2가 RTX 5060의 D3D12 경로로 OpenGL 4.6 가속을 받아 떴다.

걸린 건 하나였다. `wsl` 만 치면 ROS가 없는 22.04가 열린다(1번에서 과제용으로 새로 깐 그것). 기본 배포판을 바꿔서 해결했다.

```bash
wsl --set-default Ubuntu-24.04
wsl -d Ubuntu-24.04 -- bash -ic "rviz2"
```

**오래된 설치 글을 그대로 따라 하지 말고 지금 내 환경부터 확인할 것.** 오늘 가장 실용적인 교훈이었다.

## 11. 막혔던 지점 / 메모

- **`Permission denied (publickey,password)` 는 네트워크 문제가 아니다.** 호스트 지문을 물어봤다는 것 자체가 이미 서버에 닿았다는 증거다. 그다음은 계정명과 비밀번호를 의심해야 한다.
- **`systemctl status ssh` 는 언제나 내 쪽 서버를 본다.** 상대 서버 상태를 여기서 확인하려다 시간을 썼다.
- **WSL의 `udevadm --attribute-walk` 출력에는 `backing_file` 이 안 나온다.** `/sys/class/block/loopN/loop/backing_file` 을 직접 읽거나 `udevadm info --query=property` 로 `ID_LOOP_BACKING_FILENAME` 을 봐야 한다.
- **`ATTR{}` 와 `ATTRS{}` 는 다르다.** 앞은 그 장치 자신, 뒤는 부모 쪽까지 거슬러 올라간다. USB용 예시를 그대로 베끼면 loop 장치에는 하나도 안 맞는다.
- **`mkdir sungjin.txt`** — 이름 뒤에 확장자를 붙여도 디렉터리가 만들어진다. `ls -la` 첫 글자로 확인하는 습관을 들이자.
- **loop 번호는 붙이는 순서가 정한다.** 그래서 코드에 `/dev/loop0` 을 박으면 안 되고 `/dev/robot_*` 을 써야 한다. 실물 USB에서 `ttyUSB0` 을 박으면 안 되는 이유와 정확히 같다.
- `truncate` 로 만든 10MB 이미지는 파일시스템도 없는 빈 껍데기다. 오늘 과제는 "장치로 인식되고 서로 구분되는가"까지가 목적이라 포맷은 하지 않았다.
